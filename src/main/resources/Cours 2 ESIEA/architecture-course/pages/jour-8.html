Architecture des données

1. Architecture des données — Au-delà de la base de données

MidSenior

🧸 Analogie — Le fleuve et ses bras

Dans une université, les données coulent comme un fleuve : sources multiples (inscriptions, notes, prêts, paiements), bras dérivés (reporting, analytics, ML), et une mer finale (data warehouse). L'architecture des données décide comment creuser ce réseau de canaux, qui peut y puiser, et comment s'assurer que l'eau y est propre.

L'architecture des données est distincte de l'architecture applicative mais en est inséparable : les décisions de découpage (Database per Service) ont des conséquences directes sur comment les données sont agrégées pour le reporting et l'analytics.

1.1 Lambda vs Kappa — Deux architectures de traitement

📐 Architecture Lambda — Batch + Streaming

Sources de données
  ├── Batch Layer (Spark) → traite TOUT l'historique → vues exactes (lentes)
  └── Speed Layer (Flink) → traite données récentes → vues approchées (rapides)
                          ↓
             Serving Layer → merge batch + speed → réponse query

❌ Problème : deux codebases à maintenir (batch + streaming)

📐 Architecture Kappa — Streaming uniquement

Sources de données
  └── Streaming Layer (Kafka + Flink) → TOUT est traité comme stream
                          ↓
           Serving Layer → projections en temps réel

✅ Une seule codebase. Rejeu via Kafka si correction nécessaire.
⚠️ Exige une rétention longue du stream (mois voire années)
CritèreArchitecture LambdaArchitecture Kappa
Complexité opérationnelleÉlevée (2 moteurs)Plus simple (1 moteur)
Précision des donnéesExacte (batch) + approchée (stream)Exacte avec rétention suffisante
LatenceBatch : heures. Stream : secondesSecondes à minutes
Coût rejeu historiqueBatch rebuildable facilementDépend de la rétention Kafka
Adopter quandBatch critique (reporting réglementaire mensuel)Streaming suffit pour tous les cas d'usage

🎯 Quel modèle choisir ?

  • Lambda : utile si vous avez un reporting batch légal mensuel obligatoire (par exemple en finance) qui exige une exactitude absolue, et que vous tolérez la double codebase.
  • Kappa : à privilégier dans 90 % des cas modernes — Kafka + Flink suffisent. Choix par défaut aujourd'hui.
  • Aucun des deux : pour la plupart des PME, un Postgres + un cron de reporting nocturne fait largement l'affaire.

🏛️ Règle — Polyglot Persistence

Ne pas choisir un seul store "qui fait tout". Chaque service choisit le store adapté à ses patterns d'accès. Le coût de cohérence entre les stores est payé par des événements et des projections — c'est acceptable et préférable à un store universel qui excelle dans rien.

Architecture décentralisée des données

2. Data Mesh — Appliquer les microservices aux données

Senior

📖 Définition — Data Mesh (Zhamak Dehghani, 2019)

Architecture de données décentralisée qui applique les principes DDD et microservices aux données analytiques. Chaque domaine possède et publie ses données comme des produits — plutôt que de les centraliser dans un data warehouse ou un data lake unique géré par une équipe centrale.

❌ Modèle centralisé — Data Warehouse monolithique
  • Équipe data centrale = goulot d'étranglement
  • Schéma global difficile à faire évoluer
  • Domaines producteurs déresponsabilisés de la qualité
  • Pipeline ETL fragile et couplé
  • Time-to-insight : semaines
✅ Data Mesh — Décentralisé par domaine
  • Chaque équipe publie ses Data Products
  • Ownership de la qualité dans le domaine
  • Évolution indépendante des schémas
  • Plateforme data self-service
  • Time-to-insight : jours

2.1 Les 4 principes du Data Mesh

🏠 Ownership décentralisé

  • Chaque domaine possède ses données analytiques
  • catalog-team publie son Data Product "books-analytics"
  • loan-team publie "loans-analytics"
  • Fin du data team central omniscient

📦 Data as a Product

  • Les données ont un SLA, une documentation, un versioning
  • Découvrables via un catalogue de données
  • Consommables sans demander à l'équipe productrice
  • Qualité mesurée (fraîcheur, complétude, précision)

🛠️ Plateforme self-service

  • Infrastructure data partagée gérée centralement
  • Templates pour publier un Data Product
  • Découverte, accès, monitoring automatisés
  • L'équipe domaine se concentre sur la valeur, pas l'infra

🔒 Gouvernance fédérée

  • Règles globales sur la sécurité, RGPD, nommage
  • Implémentation locale par chaque domaine
  • Policy as Code (OPA)
  • Équilibre autonomie locale / cohérence globale

⚠️ Data Mesh : un investissement architectural majeur

Data Mesh n'est pas une technologie — c'est un changement organisationnel et culturel. Il requiert des équipes matures, une plateforme data self-service construite, et une gouvernance de données existante. Pour une organisation de moins de 5 équipes data, un data warehouse bien maintenu est souvent plus efficace.

🎯 Quand passer en Data Mesh ?

  • 10+ domaines métier autonomes et une équipe data centrale débordée.
  • Pétabytes de données et besoins analytiques très différents par domaine.
  • Maturité data élevée (catalogue, gouvernance, plateforme self-service en place).
  • Si vous avez moins de 5 équipes, un data warehouse bien tenu reste plus efficace — Data Mesh est un investissement organisationnel majeur.

🏢 Adoption Data Mesh en pratique

  • Zalando : pionnier (où Zhamak Dehghani a formalisé le concept). 200+ Data Products publiés par les équipes domaines.
  • Netflix : chaque équipe (recommandation, billing, content, playback) publie ses données analytiques.
  • JPMorgan, HSBC : adoption progressive pour casser les silos data historiques.
  • Intuit : a créé une plateforme data interne qui sert d'exemple de référence pour la self-service.
Organisation & Architecture

3. Team Topologies — L'organisation comme décision architecturale

Senior

🧸 Analogie — La cuisine d'un restaurant étoilé

Un restaurant étoilé ne met pas tout le monde à faire tout à la fois. Il y a des équipes spécialisées (saucier, pâtissier) et une brigade qui livre les plats aux autres. Si le pâtissier doit toujours demander au chef de mettre le four en marche, tout ralentit. Team Topologies, c'est dessiner une cuisine où chacun peut travailler sans attendre les autres.

📖 Définition — Team Topologies (Skelton & Pais, 2019)

Framework prescriptif pour concevoir les structures d'équipes de façon à optimiser le flux de valeur et réduire la charge cognitive. La topologie des équipes détermine directement l'architecture du système (Inverse Conway Maneuver).

3.1 Les 4 types d'équipes fondamentaux

🚀 Stream-Aligned

Mission : Livrer de la valeur utilisateur en continu sur un flux de travail (bounded context).

  • Propriétaire d'un service de bout en bout
  • Minimiser les dépendances externes
  • Ex : loan-team, catalog-team

C'est le type d'équipe principal — toutes les autres existent pour les servir.

🔧 Platform

Mission : Fournir aux Stream-Aligned des capacités self-service (infra, CI/CD, observabilité).

  • Traite les Stream-Aligned comme ses clients
  • Réduit la charge cognitive infra
  • Ex : DevOps Platform team

Risque : devenir un goulot d'étranglement au lieu d'un accélérateur.

🔬 Enabling

Mission : Aider les Stream-Aligned à acquérir de nouvelles compétences, puis se retirer.

  • Mode coach / consultatif
  • Temporaire par nature
  • Ex : équipe DDD, equipe sécurité

N'est pas un gestionnaire de dépendance permanente.

💎 Complicated Subsystem

Mission : Gérer un composant nécessitant une expertise spécialisée rare.

  • Expertise profonde dans un domaine technique
  • Fournit un service aux Stream-Aligned
  • Ex : moteur ML de recommandation

Utilisé avec parcimonie — risque de silos d'expertise.

3.2 Les 3 modes d'interaction

ModeNatureDuréeExemple campus_library
Collaboration Deux équipes travaillent ensemble activement, frontières floues Courte (sprint à sprint) loan-team + enabling-DDD-team pour modéliser le domaine
X-as-a-Service Une équipe consomme un service d'une autre avec peu d'interaction Permanente catalog-team consomme le service de notification de platform-team
Facilitating Une équipe aide une autre à se débloquer sur une compétence Courte (1–4 semaines) Security-enabling-team forme loan-team sur Zero Trust pendant 3 semaines

3.3 L'Inverse Conway Maneuver

🏛️ Stratégie — Concevoir l'organisation pour obtenir l'architecture voulue

Plutôt que de laisser l'organisation existante dicter l'architecture (Conway's Law), l'Inverse Conway Maneuver consiste à d'abord définir l'architecture cible, puis à structurer les équipes en conséquence.

Exemple : si on veut une architecture microservices avec 4 services autonomes (catalog, loan, student, notification), constituer 4 équipes Stream-Aligned autonomes — une par service. L'architecture suit l'organisation voulue, pas l'inverse.

🎯 Reconnaître les anti-patterns Team Topologies

  • "Equipe Backend monolithique" : un Stream-Aligned déguisé qui fait 10 services → cassez en plusieurs SA.
  • "Equipe DBA centrale" : devient un goulot d'étranglement → transformer en Platform Team self-service ou en Enabling temporaire.
  • "Equipe DevOps" : malheureusement souvent un Platform mal positionné qui devient ticket-driven → clarifier que les SA sont autonomes.
  • "Equipe sécurité qui dit non" : doit être Enabling (former, fournir des templates), pas un gatekeeper bloquant.
Mesurer l'architecture

4. Architecture Fitness Functions — Mesurer ce qui importe

Senior

🧸 Analogie — L'indicateur de santé

Un médecin ne dit pas "ce patient est en bonne santé" sans mesures : tension, glycémie, cholestérol... Des seuils sont définis, des alertes déclenchées si un indicateur dépasse. Une Fitness Function fait pareil pour l'architecture : elle mesure objectivement si une qualité architecturale est encore respectée.

📖 Définition — Fitness Function (Building Evolutionary Architectures, 2017)

Toute fonction qui donne un score objectif d'intégrité de l'architecture sur un axe de qualité donné. Elle peut être un test automatisé, une métrique collectée en production, ou une règle vérifiée en CI.

4.1 Fitness Functions atomiques vs holistiques

🔬 Atomiques — Un aspect à la fois

  • Test unitaire : "aucun service ne dépend directement de la DB d'un autre service"
  • Linter architectural : "couche domain ne dépend pas de couche web"
  • Test de latence : "P99 de l'endpoint /loans < 400ms"
  • Vérification de couplage : "pas de shared library entre loan et catalog"

🌐 Holistiques — Interaction du système

  • Test de charge globale : scalabilité de bout en bout
  • Chaos test : "le système répond en mode dégradé si catalog est down"
  • Security scan : "aucune CVE critique dans les images Docker"
  • Compliance : "tous les accès aux données PII sont loggés"

📐 Fitness Functions — campus_library en CI/CD

🧱 Architecture
  • ArchUnit : no layer violations
  • Dependency-check : no DB coupling
  • Package cycle : no circular deps

✅ Exécuté à chaque PR

⚡ Performance
  • GET /books : P99 < 200ms
  • POST /loans : P99 < 500ms
  • 1000 users simultanés : 0 erreur

✅ Nightly en staging

🔐 Sécurité
  • OWASP ZAP : 0 critical
  • Trivy : 0 CVE critique image
  • DAST sur endpoints auth

✅ Chaque release

📊 Observabilité
  • Tous services exposent /health
  • Tous services exposent /metrics
  • Trace ID propagé sur tous appels

✅ Gate de déploiement

🛡️ Résilience
  • Chaos: kill catalog → fallback OK
  • Latency injection 2s → CB activé
  • SLO: 99.9% uptime sur 30j

✅ Mensuel en prod

📋 Compliance
  • PII loggés uniquement si nécessaire
  • Chiffrement at-rest vérifié
  • Audit trail complet prêts

✅ Audit trimestriel

✅ Règles d'or des Fitness Functions

  1. Automatiser : une Fitness Function manuelle est une checklist négligée
  2. Intégrer en CI/CD : elle doit bloquer un déploiement si elle échoue
  3. Correspondre aux décisions ADR : chaque ADR doit avoir sa Fitness Function associée
  4. Éviter la complaisance : réviser les seuils périodiquement

🏢 Exemples de Fitness Functions en production

  • ThoughtWorks (origine du concept) : leurs projets clients ont systématiquement un "fitness function dashboard" partagé.

  • Goldman Sachs : tests de chaos automatisés mensuels sur les plateformes de trading critiques.
  • Booking.com : tout déploiement passe par 50+ vérifications automatisées avant d'atteindre la production.
Migration progressive

5. Architecture évolutive — Migrer sans Big Bang

MidSenior

5.1 Strangler Fig Pattern — La migration incrémentale

📖 Définition — Strangler Fig Pattern (Martin Fowler)

Pattern de migration d'un système legacy vers une nouvelle architecture, inspiré du figuier étrangleur qui pousse autour d'un arbre hôte jusqu'à le remplacer complètement. Le nouveau système coexiste avec l'ancien, en interceptant progressivement des fonctionnalités, jusqu'à ce que l'ancien puisse être éteint.

📐 Strangler Fig — Migration campus_library legacy → microservices

Phase 1
Façade (API Gateway) entre les clients et le monolithe. Tout le trafic passe par la façade — le monolithe reçoit toujours 100%.
Phase 2
Extraire catalog-service. La façade route /catalog/* vers le nouveau service. Le monolithe gère encore prêts + étudiants.
Phase 3
Extraire loan-service. La façade route /loans/* vers le nouveau service. Le monolithe ne gère plus que les étudiants.
Phase N
Monolithe éteint. Tous les domaines ont leur service. La migration est complète sans aucun Big Bang.

Feature Toggle MigrationActiver le nouveau comportement par flagTrès faibleChangement de comportement testable progressivement

🏢 Migrations Strangler Fig célèbres

  • Amazon : passage du monolithe Obidos vers les microservices via Strangler sur plusieurs années (2002-2006).
  • Etsy : migration progressive du monolithe PHP vers une architecture polyglotte, sans jamais arrêter le site.
  • Shopify : a "modulariser" son monolithe Rails en bounded contexts puis extrait progressivement les modules en services.
  • The Guardian : migration du CMS legacy vers une architecture moderne avec un proxy en frontal pendant 18 mois.
  • ⚠️ Contre-exemple : Netscape a tenté un Big Bang Rewrite en 1998 — projet 3 ans, perte de 50% des parts de marché. Devenu cas d'école dans "Things You Should Never Do" de Joel Spolsky.
Économie du cloud

6. FinOps — L'architecture comme décision économique

MidSenior

📖 Définition — FinOps (Cloud Financial Operations)

Pratique culturelle et opérationnelle qui réunit ingénierie, finance et business pour optimiser les coûts cloud tout en maximisant la valeur. L'objectif n'est pas de dépenser le moins possible, mais de dépenser de façon intentionnelle et mesurée.

🧸 Analogie — La note de restaurant partagée

Quand tout le monde commande sans regarder le prix et que la note est partagée équitablement, personne n'optimise. FinOps, c'est comme donner à chaque personne sa propre note — la visibilité individuelle crée la responsabilité. En cloud : chaque équipe voit son coût.

6.1 Les décisions architecturales qui coûtent le plus

6.2 Patterns architecturaux d'économie cloud

⚡ Scale to Zero

  • Services dormants : 0 instance, 0 coût
  • Scale up au premier appel (cold start acceptable)
  • Outils : KEDA, Knative, Cloud Run, Fargate
  • Idéal : batch jobs, services dev/staging

🏷️ Spot / Preemptible Instances

  • Instances interruptibles jusqu'à 90% moins chères
  • Requiert stateless + graceful shutdown
  • Idéal : jobs Spark, rendering, CI workers
  • Ne pas utiliser pour : DB prod, services critiques

📦 Reserved Instances

  • Engagement 1–3 ans = 30–60% de réduction
  • Pour les workloads stables (base load)
  • Combiner : baseline reserved + pic on-demand
  • Analyser 3 mois de métriques avant de réserver

🗄️ Data Tiering

  • Données chaudes : SSD rapide (coût élevé)
  • Données tièdes : HDD (coût moyen)
  • Données froides : Glacier/Archive (coût <0.01$/GB/mois)
  • Automatiser les transitions avec lifecycle policies

💰 Règle FinOps : chaque équipe doit voir son coût cloud quotidien. La visibilité crée la responsabilité. Un dashboard coût par service est une Fitness Function économique.

🎯 3 décisions FinOps qui font économiser 50%+

Revue & soutenance

7. Défendre son architecture — La revue comme dialogue

JuniorMidSenior

🧸 Analogie — Défendre un permis de construire

Un architecte ne dit pas "faites-moi confiance". Il présente les plans, explique pourquoi le couloir est là (facilité d'accès pompiers), pourquoi la cuisine est orientée nord (lumière), et quelles contraintes il a respectées (séisme, PLU). La revue d'architecture, c'est pareil : expliquer le raisonnement, pas juste montrer le résultat.

7.1 Structure d'une revue d'architecture

① Contexte

Contraintes métier, équipe, délai, budget disponible

② Qualités prioritaires

Disponibilité ? Performance ? Maintenabilité ? Coût ? Sécurité ?

③ Décisions

Choix effectués + ADR associés + alternatives rejetées

④ Trade-offs

Ce qu'on a sacrifié. Ce qu'on a mesuré. Ce qu'on surveille.

⑤ Risques résiduels

Ce qui pourrait mal tourner. Mitigation prévue ou acceptée.

7.2 Les questions difficiles — et comment y répondre

Question de revueCe que l'examinateur testeStructure de réponse attendue
"Pourquoi des microservices et pas un monolithe ?" Que vous ne suivez pas la mode mais le contexte Contexte (taille équipe, besoins de scalabilité) → décision → trade-off accepté
"Que se passe-t-il si Kafka tombe ?" Que vous avez pensé aux pannes de l'infrastructure même Mode dégradé prévu + fallback synchrone temporaire + RTO Kafka
"Comment vous assurez-vous que l'architecture reste cohérente dans 1 an ?" Que vous avez une gouvernance, pas juste un design ADR + Fitness Functions en CI + revues d'architecture régulières
"Quel est le coût mensuel de votre architecture ?" Que les décisions techniques ont une dimension économique Estimation par service + justification par SLA vs coût
"Si vous deviez tout refaire, que changeriez-vous ?" Votre capacité d'autocritique et d'apprentissage Identifier une vraie faiblesse + leçon architecturale tirée

🎤 Template de réponse type en revue d'architecture

"Nous avons choisi [décision] parce que notre contexte était [contraintes]. Les alternatives que nous avons considérées étaient [alternatives], mais elles posaient le problème de [raison du rejet].

Cette décision nous apporte [bénéfices concrets] mais nous oblige à accepter [trade-offs explicites]. Nous surveillons ces risques via [métriques / Fitness Functions]. Si nos hypothèses changent, nous serions prêts à reconsidérer parce que [condition de révision]."

Les 10 principes qui traversent le module

① Décision explicite

Toute structure qui sera difficile à changer doit être décidée consciemment et documentée (ADR).

② Trade-offs, pas silver bullet

Chaque pattern (microservices, CQRS, EDA) résout un problème en créant d'autres. Le contexte décide.

③ Conway's Law est réel

L'architecture suit l'organisation. Aligner les deux est un projet architectural à part entière.

④ Mesurer, pas supposer

Une qualité architecturale non mesurée se dégrade silencieusement. Fitness Functions > bonne volonté.

⑤ Design for Failure

Tout tombera. La question est de savoir comment le système se comporte quand ça tombe.

⑥ Migration progressive

Strangler Fig > Big Bang Rewrite. Toujours. Sans exception valable.

⑦ Complexité = coût

Chaque composant, chaque pattern ajouté doit payer sa dette en valeur délivrée. FinOps s'applique aussi à la complexité technique.

⑧ L'organisation est un artefact

Team Topologies : structurer les équipes est une décision architecturale aussi importante que les patterns techniques.

⑨ Observer avant d'optimiser

Instrumenter en premier. Décider sur données. Jamais sur intuitions non mesurées.

⑩ Justifier ses choix

Un architecte qui ne peut pas expliquer pourquoi a fait un choix par défaut, pas par décision.

"En 8 jours, vous avez parcouru l'architecture logicielle de ses fondements (Jour 1) jusqu'aux pratiques industrielles avancées (Jour 8). Vous avez vu que l'architecture n'est pas un diagramme — c'est un ensemble de décisions difficiles à changer, prises explicitement, dans un contexte donné.

Vous savez maintenant raisonner en trade-offs. Vous pouvez concevoir un système, le documenter, le mesurer, le faire évoluer sans le casser, et défendre vos choix face à un jury ou une équipe.

La prochaine fois que quelqu'un vous proposera une technologie "parce que tout le monde le fait", vous saurez poser les bonnes questions : quel problème ça résout ? dans quel contexte ? au prix de quel trade-off ? et comment on le mesure ?

C'est ça, la maturité architecturale."

Évaluation finale

9. Quiz final du module

1. Quelle est la différence fondamentale entre un Data Warehouse centralisé et un Data Mesh ? Dans quel contexte organisationnel choisir l'un ou l'autre ?

Voir la réponse

Data Warehouse centralisé : une équipe data centrale ingère, transforme et publie les données de tous les domaines. Simple à gouverner, mais devient un goulot d'étranglement à grande échelle. Les équipes producteurs ne sont pas responsables de la qualité.
Data Mesh : chaque équipe domaine publie ses propres Data Products avec leur SLA et leur documentation. Scalabilité organisationnelle, ownership de la qualité distribué, mais requiert une maturité data élevée et une plateforme self-service.
Choisir Data Warehouse si : moins de 5 équipes data, organisation centralisée, maturité data faible. Choisir Data Mesh si : multiple équipes autonomes, volume de données élevé, besoins analytiques très différents par domaine.

2. Expliquez l'Inverse Conway Maneuver. Donnez un exemple concret appliqué à campus_library.

Voir la réponse

L'Inverse Conway Maneuver consiste à définir l'architecture cible en premier, puis à structurer les équipes pour qu'elles reflètent cette architecture — au lieu de laisser l'organisation existante dicter l'architecture (Conway's Law naturelle).
Exemple campus_library : on veut 4 microservices autonomes (catalog, loan, student, notification). On constitue donc 4 équipes Stream-Aligned correspondantes, chacune propriétaire de son service de bout en bout (dev + DB + déploiement + ops). Une Platform Team fournit le CI/CD et l'observabilité en self-service. L'architecture microservices devient naturelle car les équipes ne se bloquent plus mutuellement.

3. Qu'est-ce qu'une Architecture Fitness Function ? Donnez deux exemples — un atomique et un holistique — pour campus_library.

Voir la réponse

Une Fitness Function est toute fonction automatisée qui mesure objectivement si une qualité architecturale est respectée. Elle bloque un déploiement si elle échoue, comme un test unitaire bloque une PR.
Atomique : test ArchUnit vérifiant qu'aucune classe du package domain n'importe une classe du package infrastructure (règle de Clean Architecture). Exécuté à chaque PR.
Holistique : test de chaos injectant une panne de catalog-service et vérifiant que loan-service retourne un fallback en moins de 2 secondes, que le taux d'erreur reste sous 0.5%, et que les logs de corrélation sont présents. Exécuté en staging avant chaque release majeure.

4. Décrivez le Strangler Fig Pattern. Pourquoi est-il supérieur au Big Bang Rewrite dans presque tous les contextes ?

Voir la réponse

Le Strangler Fig consiste à poser une façade (API Gateway ou proxy) devant le système legacy, puis à extraire progressivement des fonctionnalités vers le nouveau système. La façade route graduellement le trafic vers le nouveau code. Quand tout est migré, le legacy est éteint.
Supérieur au Big Bang car : le système legacy continue de fonctionner pendant toute la migration (zéro downtime) ; chaque extraction est testée sur du vrai trafic avant la suivante ; en cas de problème, rollback immédiat vers le legacy ; l'équipe apprend progressivement le nouveau paradigme sans pression de "reecrire tout d'un coup". Le Big Bang Rewrite échoue souvent car le legacy contient un "knowledge" implicite (règles métier non documentées) que la réécriture oublie.

5. Donnez 3 décisions architecturales qui ont un impact coût significatif en cloud. Comment les FinOps aident-elles à arbitrer ?

Voir la réponse

Multi-région pour 99.99% SLA : coût ×6 minimum. FinOps : calculer le coût du downtime (si < coût multi-région, rester single-région).
Logs non filtrés à haute volumétrie : 100GB/jour × prix ingestion Elasticsearch = budget conséquent. FinOps : log sampling, debug off en prod, lifecycle policy vers archive.
Instance always-on pour service à trafic variable : payé 100% du temps pour 10% d'utilisation. FinOps : autoscaling to zero (KEDA), ou reserved instance pour la base + on-demand pour les pics.
Les FinOps aident en rendant le coût visible par équipe (tagging par service), en liant les décisions d'architecture aux budgets, et en créant une culture où l'ingénierie arbitre explicitement entre SLA et coût plutôt que de choisir la haute disponibilité "par défaut".
