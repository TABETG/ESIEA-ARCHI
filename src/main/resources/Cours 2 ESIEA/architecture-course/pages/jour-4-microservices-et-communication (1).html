Fondamentaux

Principes des microservices

JuniorMid

Le microservice n'est pas "un petit projet Spring Boot". C'est une unité de déploiement et d'évolution autonome centrée sur une capacité métier unique. Sam Newman (auteur de référence) le définit comme un service qui peut être déployé indépendamment.

🤔 Problème

Comment faire évoluer des parties du système indépendamment, sans casser les autres ?

💬 À dire aux étudiants

Commencez par un modular monolith. Passez aux microservices quand la douleur est réelle, pas par mode.

🔑 Mots-clés

Déploiement indépendant · Database per Service · Conway's Law · Bounded Context

⚠️ Pré-requis

CI/CD mature · Observabilité · Container orchestration · On-call équipe

🧸 Analogie — La cuisine spécialisée

Au lieu d'une seule grande cuisine qui fait tout (entrées, plats, desserts), on a plusieurs cuisines spécialisées avec chacune son équipe et ses outils. Si la cuisine des desserts est en panne, les plats chauds continuent d'être servis.

Monolithe vs Microservices — en un coup d'œil

Monolithe
1 seule application
1 seule base de données
1 seul déploiement
Tout le code ensemble
✅ Simple à développer et déboguer
❌ Impossible de scaler une partie seule
❌ Un bug peut tout casser
Microservices
Plusieurs applications indépendantes
1 base PAR service
Déploiement indépendant
Communication via API/événements
✅ Scaler indépendamment chaque service
✅ Équipes autonomes par domaine
❌ Complexité réseau + ops × 10

🎓 Mode pro

Les microservices cherchent à réduire la coordination entre équipes (Conway's Law), aligner code et domaine métier, et permettre un scaling différencié. Ils ne sont rentables qu'avec une maturité d'exploitation suffisante : CI/CD mature, observabilité, on-call, container orchestration.

Les 5 caractéristiques d'un vrai microservice

  1. Déployable indépendamment — sans coordination avec d'autres équipes.
  2. Responsabilité unique — centré sur une seule capacité métier.
  3. Propriétaire de ses données — sa propre base de données (Database per Service).
  4. Communicant via API explicite — jamais via une base partagée.
  5. Résilient aux pannes des voisins — dégradation gracieuse si un service est down.

⚠️ Microservices ne convient pas à tout le monde

Un monolithe bien structuré (Modular Monolith) est souvent le bon choix pour une startup ou une équipe réduite. Les microservices doublent la complexité opérationnelle. Migrez vers les microservices quand la douleur du monolithe est réelle, pas par mode.

📌 À retenir — Déployabilité

  • Un service = un repo = une pipeline CI/CD
  • Déploiement sans coordination externe
  • Versionnement d'API pour la rétrocompatibilité

📌 À retenir — Conway's Law

  • Architecture ≈ structure des équipes
  • 2 à 8 personnes par service (Two-Pizza Team)
  • Réduire les dépendances inter-équipes

Domain-Driven Design

Découpage fonctionnel — Domain-Driven Design

MidSenior

Le découpage est la décision la plus critique en microservices. Un mauvais découpage crée un Distributed Monolith — le pire des deux mondes. On utilise le Bounded Context de DDD comme unité naturelle de découpage.

Bounded Context — Définition

Un Bounded Context est une frontière logique dans laquelle un modèle de domaine est cohérent et non ambigu. Le même mot peut avoir une signification différente dans deux contextes différents.

Exemple : le mot "Book" :

  • Dans le Catalog Context : titre, auteur, ISBN, disponibilité physique.
  • Dans le Loan Context : exemplaire emprunté, date de retour, état.
  • Dans le Billing Context : prix de location, pénalités de retard.

Chaque contexte a son propre modèle — ne les fusionnez pas !

❌ Mauvais découpage — par couche technique

user-controller-service     ← controller pour tout
user-repository-service     ← data pour tout
notification-repository-svc
business-logic-service

→ Couplage fort, impossible de déployer indépendamment.

✅ Bon découpage — par capacité métier

catalog-service      ← tout sur les livres
loan-service         ← tout sur les emprunts
identity-service     ← auth + profil étudiant
notification-service ← emails, push, SMS

→ Chaque service = une équipe = un domaine = une base.

Heuristiques de découpage (règles pratiques)

  • Single Responsibility : "Ce service fait une chose et la fait bien."
  • Taille d'équipe : une équipe de 2 à 8 personnes peut posséder un service (Two-Pizza Team).
  • Faible couplage : si changer un service force à changer un autre, ils sont trop liés → fusionnez ou redécoupez.
  • Forte cohésion : les données et comportements qui changent ensemble restent ensemble.
  • Strangler Fig : migrez un monolithe progressivement, service par service, sans tout réécrire d'un coup.

🎤 Script oral — Présentation en cours

"Imaginez une bibliothèque universitaire. Le catalogue des livres change quand un nouveau livre arrive. La gestion des prêts change quand les règles métier évoluent. Ce ne sont pas les mêmes rythmes, les mêmes équipes, les mêmes contraintes. Donc ce sont des services séparés."

"La règle d'or : si vous ne pouvez pas modifier et déployer un service sans toucher les autres, ce n'est pas un vrai microservice."

Communication synchrone

Communication synchrone — OpenFeign

JuniorMidSenior

OpenFeign permet à un service d'appeler un autre service via HTTP comme si c'était une méthode Java locale. Au lieu d'écrire du code HTTP bas niveau (URL, headers, parsing JSON…), on déclare une interface Java et Feign génère tout le code HTTP automatiquement.

🧸 Analogie — Le téléphone avec annuaire automatique

Sans Feign, pour appeler un collègue dans un autre bureau, tu dois chercher son numéro, composer, attendre, décoder sa réponse… Avec Feign, tu dis juste "appelle catalog-service et demande la disponibilité du livre" — Feign s'occupe du reste : il trouve l'adresse (Eureka), passe l'appel (HTTP), et te retourne la réponse en objet Java.

Comment ça marche — le flux complet

🟣 loan-service veut vérifier un livre

Le code appelle catalogClient.getAvailability(bookId) — comme une méthode Java normale

Feign génère l'appel HTTP
🟡 Eureka (Service Discovery)

Feign demande à Eureka : "Où se trouve catalog-service ?" → Eureka répond avec l'adresse IP + port

GET /internal/books/{id}/availability
🔵 catalog-service répond

Retourne { "available": true, "copies": 3 } — Feign le convertit en objet Java AvailabilityResponse

Si erreur ou timeout
🔴 Fallback (Circuit Breaker)

Si catalog-service est DOWN → Feign appelle automatiquement la classe Fallback → réponse dégradée sans planter

1. Dépendance Maven

Ajouter spring-cloud-starter-openfeign

2. @EnableFeignClients

Activer sur la classe principale

3. Interface @FeignClient

Déclaratif — Feign génère le client HTTP

4. Fallback

Réponse dégradée si le service est indisponible

Étape 3 — Interface déclarative
// ═══════════════════════════════════════════════════════════════
// CLIENT FEIGN : loan-service appelle catalog-service via HTTP
// ═══════════════════════════════════════════════════════════════
// On déclare une interface Java — Feign génère le code HTTP pour nous.
// C'est comme écrire un @Repository pour JPA : on décrit, Spring implémente.
@FeignClient(
    name     = "catalog-service",           // Nom du service dans Eureka (Service Discovery)
    path     = "/internal",                  // Préfixe commun à tous les endpoints internes
    fallback = CatalogClientFallback.class   // Classe appelée si le Circuit Breaker est OPEN
)
public interface CatalogClient {

    // Vérifie si un livre est disponible — réponse immédiate requise (sync)
    @GetMapping("/books/{bookId}/availability")
    AvailabilityResponse getAvailability(@PathVariable UUID bookId);

    // Réserve un exemplaire du livre — opération d'écriture
    @PutMapping("/books/{bookId}/reserve")
    void reserveBook(@PathVariable UUID bookId,
                     @RequestBody ReservationRequest request);

    // Libère la réservation (compensation en cas d'annulation de la Saga)
    @PutMapping("/books/{bookId}/release")
    void releaseBook(@PathVariable UUID bookId);
}

// ═══════════════════════════════════════════════════════════════
// FALLBACK : réponse dégradée quand catalog-service est DOWN
// ═══════════════════════════════════════════════════════════════
// Implémente la même interface que le client Feign.
// Spring l'utilise automatiquement quand le Circuit Breaker est OPEN
// ou quand catalog-service ne répond pas dans le timeout.
@Component
public class CatalogClientFallback implements CatalogClient {

    @Override
    public AvailabilityResponse getAvailability(UUID bookId) {
        // Stratégie conservative : on dit "indisponible" plutôt que de bloquer l'UX.
        // En prod, on pourrait retourner une réponse cachée (Redis/local cache).
        log.warn("catalog-service unavailable, returning cached/default response");
        return new AvailabilityResponse(false, 0, "UNKNOWN");
    }

    @Override
    public void reserveBook(UUID bookId, ReservationRequest request) {
        // On ne peut pas réserver → on publie un événement Kafka pour retry plus tard.
        // C'est le pattern "async retry" : on ne perd pas la demande.
        compensationPublisher.publish(new ReservationFailedEvent(bookId));
    }

    @Override
    public void releaseBook(UUID bookId) {
        // Cas critique : la libération a échoué → le livre reste "réservé" à tort.
        // → Alerte pour intervention manuelle (PagerDuty, Slack, etc.)
        log.error("Could not release book {} — manual intervention needed", bookId);
    }
}

⚙️ Expert — Intercepteur Feign pour propager les headers

Quand loan-service appelle catalog-service, on veut que le token JWT et le Trace ID soient transmis automatiquement — sans que chaque développeur doive y penser.

// ═══════════════════════════════════════════════════════════════
// INTERCEPTEUR FEIGN : s'exécute AVANT chaque appel HTTP sortant
// ═══════════════════════════════════════════════════════════════
// Problème : quand un utilisateur appelle loan-service, son JWT
// est dans le header HTTP. Mais quand loan-service appelle
// catalog-service via Feign, le JWT est perdu. Cet intercepteur
// le récupère et le transmet automatiquement.
@Bean
public RequestInterceptor feignRequestInterceptor() {
    return requestTemplate -> {
        // Récupérer la requête HTTP entrante actuelle (celle du client → loan-service)
        HttpServletRequest currentRequest = ((ServletRequestAttributes)
            RequestContextHolder.currentRequestAttributes()).getRequest();

        // ── 1. Propager le JWT ──
        // Le token du client est dans "Authorization: Bearer xxx"
        // On le copie dans la requête sortante Feign → catalog-service
        String authHeader = currentRequest.getHeader(HttpHeaders.AUTHORIZATION);
        if (authHeader != null) {
            requestTemplate.header(HttpHeaders.AUTHORIZATION, authHeader);
        }

        // ── 2. Propager le Trace ID (distributed tracing) ──
        // Permet de suivre une requête à travers tous les services
        // Indispensable pour déboguer en production !
        String traceId = MDC.get("traceId");
        if (traceId != null) {
            requestTemplate.header("X-Trace-Id", traceId);
        }

        // ── 3. Identifier l'appelant ──
        // catalog-service sait que c'est loan-service qui l'appelle (audit, logs)
        requestTemplate.header("X-Caller-Service", "loan-service");
    };
}

Communication asynchrone

Communication asynchrone — Kafka en profondeur

MidSeniorExpert

Apache Kafka est un log distribué immuable et persistant. Comprendre ses mécanismes internes est essentiel pour construire des systèmes fiables à grande échelle.

🧸 Analogie — Le cahier, la page et la ligne

Imaginez Kafka comme un ensemble de cahiers dans un bureau de poste géant où les messages ne sont jamais effacés :

  • Topic = un cahier dédié à un sujet. Exemple : le cahier "emprunts", le cahier "réservations".
  • Partition = une page dans ce cahier. Kafka écrit sur plusieurs pages en parallèle pour aller plus vite. La clé du message (ex : loanId) détermine sur quelle page on écrit : hash(loanId) % nb_pages.
  • Offset = le numéro de ligne sur la page. Chaque message reçoit un numéro unique et croissant (0, 1, 2, 3…). On ne peut pas modifier ni supprimer une ligne déjà écrite.
  • Consumer Group = une équipe de lecteurs. Chaque équipe a sa propre photocopie du cahier et lit à son propre rythme. L'équipe "notifications" peut en être à la ligne 5, pendant que l'équipe "analytics" en est à la ligne 3.
  • Broker = le meuble qui stocke physiquement les cahiers. On a plusieurs meubles pour la redondance.
  • Ack = l'accusé de réception. Quand on écrit un message, on peut demander : aucune confirmation (rapide mais risqué), confirmation du meuble principal, ou confirmation de tous les meubles (le plus sûr).

🗄️ Brokers et réplication — Pourquoi plusieurs serveurs ?

Un broker est un serveur Kafka. Un cluster Kafka est composé de plusieurs brokers (typiquement 3 en production). Chaque partition est stockée sur un broker, mais copiée sur d'autres brokers pour survivre aux pannes.

🧸 Analogie — Les coffres-forts dans 3 banques différentes

Imagine que tu as un document important. Tu le mets dans un coffre-fort à la banque A (c'est le leader). Mais si la banque A brûle, tu perds tout. Alors tu fais 2 copies dans les coffres des banques B et C (ce sont les followers). Si la banque A brûle, la banque B devient le nouveau leader — aucun document n'est perdu. C'est ça le replication-factor=3.

Réplication en action — Topic loan.created avec replication-factor=3

Chaque partition a 1 leader + 2 followers répartis sur des brokers différents
Broker 1
LP0 Leader — reçoit les écritures
FP1 Follower — copie de B2
FP2 Follower — copie de B3
Broker 2
FP0 Follower — copie de B1
LP1 Leader — reçoit les écritures
FP2 Follower — copie de B3
Broker 3
FP0 Follower — copie de B1
FP1 Follower — copie de B2
LP2 Leader — reçoit les écritures
L = Leader (reçoit les écritures et lectures) · F = Follower (copie synchronisée automatiquement). Kafka distribue les leaders sur des brokers différents pour équilibrer la charge.

Que se passe-t-il si un broker tombe ?

🟢 État normal — 3 brokers en ligne

P0 Leader sur Broker 1 · P1 Leader sur Broker 2 · P2 Leader sur Broker 3. Tout fonctionne, chaque partition a 2 copies de secours.

Broker 2 plante !
🟡 Élection automatique — en quelques secondes

P1 a perdu son leader (Broker 2). Kafka élit automatiquement le follower sur Broker 1 ou Broker 3 comme nouveau leader de P1. Aucune intervention humaine, aucune perte de données.

Broker 2 revient
🟢 Rattrapage — Broker 2 se resynchronise

Broker 2 redémarre, récupère les messages manqués depuis les autres brokers, et redevient follower. Éventuellement, Kafka peut lui redonner le rôle de leader pour P1 (preferred leader election).

⚠️ Pourquoi replication-factor=1 est dangereux en production

Avec replication-factor=1, chaque partition n'existe que sur un seul broker. Si ce broker plante (crash disque, panne réseau), les données de cette partition sont PERDUES jusqu'au retour du broker. En production, toujours utiliser replication-factor=3 avec min.insync.replicas=2.

Consommateur robuste avec Dead Letter Queue
// ═══════════════════════════════════════════════════════════════
// DEAD LETTER QUEUE (DLT) : où vont les messages impossibles à traiter
// ═══════════════════════════════════════════════════════════════
// Problème : un message arrive mais le traitement échoue (bug, data corrompue...).
// Sans DLT, le consumer retente à l'infini et BLOQUE toute la partition.
// Solution : après N retries, envoyer le message dans un topic ".DLT"
// pour analyse manuelle, et continuer avec les messages suivants.
@Configuration
public class KafkaConsumerConfig {

    @Bean
    public DefaultErrorHandler errorHandler(KafkaTemplate<String, Object> template) {
        // Le "recoverer" envoie le message échoué dans un topic DLT dédié
        // Ex : "loan.created" → "loan.created.DLT"
        DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(
            template,
            (record, ex) -> new TopicPartition(
                record.topic() + ".DLT",   // Topic de destination = nom original + ".DLT"
                record.partition()          // Garder la même partition pour le debug
            )
        );

        // Backoff exponentiel : 1s → 2s → 4s → 8s — puis abandon → DLT
        // Pourquoi exponentiel ? Si le service distant est surchargé,
        // on lui laisse de plus en plus de temps pour récupérer.
        ExponentialBackOffWithMaxRetries backOff =
            new ExponentialBackOffWithMaxRetries(4);  // 4 tentatives max
        backOff.setInitialInterval(1_000);   // 1ère attente : 1 seconde
        backOff.setMultiplier(2.0);          // Chaque retry attend 2x plus longtemps

        DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);

        // ⚠️ Ne PAS retenter les erreurs de désérialisation (le message est corrompu,
        // retenter ne changera rien → envoi direct en DLT)
        handler.addNotRetryableExceptions(JsonParseException.class);

        return handler;
    }
}

    @KafkaListener(topics = "loan.created", groupId = "notification-service")
    public void onLoanCreated(
            @Payload LoanCreatedEvent event,                       // Le contenu du message (JSON → objet Java)
            @Header(KafkaHeaders.RECEIVED_PARTITION) int partition, // N° de partition (page) d'où vient le msg
            @Header(KafkaHeaders.OFFSET) long offset,              // N° de ligne dans la partition
            Acknowledgment ack) {                                   // Pour commit manuel de l'offset

        log.info("Processing [loanId={}, partition={}, offset={}]",
            event.loanId(), partition, offset);

        try {
            // ── Traitement métier ──
            notificationService.sendConfirmation(event.studentId(), event.loanId());

            // ── COMMIT de l'offset ──
            // On ne fait ack QU'APRÈS le traitement réussi.
            // Si le service crash AVANT cette ligne, le message sera re-traité au redémarrage.
            ack.acknowledge();

            // Compteur Prometheus pour monitoring (Grafana dashboard)
            registry.counter("kafka.consumed", "topic", "loan.created", "status", "ok")
                    .increment();

        } catch (Exception e) {
            registry.counter("kafka.consumed", "topic", "loan.created", "status", "error")
                    .increment();
            // ⚠️ On NE fait PAS ack → Kafka va retenter (backoff exponentiel)
            // Si max retries atteint → le message part en DLT (Dead Letter Topic)
            throw e;
        }
    }

    // ═══════════════════════════════════════════════════════════════
    // CONSUMER DLT : surveille les messages qui ont échoué N fois
    // ═══════════════════════════════════════════════════════════════
    // En production, ce consumer crée des alertes (PagerDuty, Slack)

    @KafkaListener(topics = "loan.created.DLT", groupId = "notification-dlq")
    public void onLoanCreatedDlt(@Payload LoanCreatedEvent event) {
        log.error("DEAD LETTER: failed to process loan.created for loanId={}",
            event.loanId());
        alertingService.createAlert("Kafka DLT message", event);
    }

⚙️ Expert — Transactions Kafka (Exactly-Once Semantics)

Le problème : on veut que l'emprunt soit sauvegardé en base ET publié dans Kafka de manière atomique. Si on persiste en base puis que le publish Kafka échoue, on a un emprunt en base sans notification. Si Kafka réussit mais la base échoue, on a une notification sans emprunt. La transaction coordonnée résout ce problème.

// ═══════════════════════════════════════════════════════════════
// TRANSACTION MANAGER : coordonne la BDD et Kafka dans une seule transaction
// ═══════════════════════════════════════════════════════════════
// Principe : les deux opérations (INSERT en base + SEND Kafka) sont
// dans la MÊME transaction. Si l'une échoue, l'autre est annulée.
@Configuration
public class KafkaTransactionConfig {

    @Bean
    public KafkaTransactionManager<String, Object> kafkaTransactionManager(
            ProducerFactory<String, Object> pf) {
        // Ce bean permet à Spring de coordonner transactions JPA + Kafka
        return new KafkaTransactionManager<>(pf);
    }
}

// ═══════════════════════════════════════════════════════════════
// SERVICE APPLICATION : crée un emprunt de manière atomique
// ═══════════════════════════════════════════════════════════════
@Service
public class LoanApplicationService {

    private final LoanRepository loanRepo;
    private final KafkaTemplate<String, LoanCreatedEvent> kafka;

    // @Transactional("kafkaTransactionManager") :
    // Spring ouvre une transaction Kafka ET une transaction JPA.
    // Les deux sont committées ensemble, ou rollbackées ensemble.
    @Transactional("kafkaTransactionManager")
    public Loan createLoan(CreateLoanRequest request) {

        // ── Étape 1 : persister l'emprunt en base de données ──
        Loan loan = loanRepo.save(Loan.from(request));

        // ── Étape 2 : publier l'événement dans Kafka ──
        // Clé = loanId → garantit que tous les événements du même emprunt
        // arrivent dans la même partition → ordre préservé
        kafka.send("loan.created",
            loan.getId().toString(),   // clé de partitionnement
            new LoanCreatedEvent(      // payload JSON
                loan.getId(),
                request.studentId(),
                request.bookId(),
                Instant.now()
            ));

        return loan;
        // ✅ Si tout réussit → commit BDD + commit Kafka (atomique)
        // ❌ Si commit Kafka échoue → rollback BDD automatique
        // ❌ Si commit BDD échoue → le message Kafka n'est jamais visible
        //    (car isolation.level=read_committed côté consommateur)
    }
}

La combinaison enable.idempotence=true côté producteur + isolation.level=read_committed côté consommateur garantit l'Exactly-Once Semantics (EOS) de bout en bout. Sans EOS, un crash après l'envoi Kafka mais avant le commit de l'offset peut causer un message dupliqué.

Résilience

Circuit Breaker — Résilience4j

MidSenior

Le Circuit Breaker est le pattern de résilience le plus important des microservices. Inspiré du disjoncteur électrique, il coupe automatiquement les appels vers un service défaillant pour éviter la propagation des pannes (Cascading Failure).

🧸 Analogie — Le disjoncteur de la maison

Quand un appareil provoque un court-circuit, le disjoncteur coupe le courant pour protéger toute l'installation. Sans lui, un seul appareil défectueux pourrait faire griller toute la maison.

C'est pareil en microservices : si catalog-service est down, on ne veut pas que loan-service se bloque à attendre la réponse pendant 30 secondes à chaque requête. Le Circuit Breaker coupe immédiatement et retourne une réponse dégradée (fallback).

Les 3 états du Circuit Breaker

🟢 CLOSED — Circuit fermé (normal)

Les appels passent normalement. On surveille le taux d'erreurs. Si ≥ 50% des derniers 20 appels échouent → passage à OPEN.

Taux d'erreurs ≥ seuil
🔴 OPEN — Circuit ouvert (protection)

Tous les appels sont court-circuités immédiatement — pas d'appel réseau, le fallback est retourné instantanément. Attente de 30s avant de tester.

Après waitDuration (30s)
🟡 HALF-OPEN — Test de récupération

On laisse passer 5 appels de test. Si ≥ 50% réussissent → retour à CLOSED. Si échec → retour à OPEN.

// UTILISATION DU CIRCUIT BREAKER — 2 approches
// ═══════════════════════════════════════════════════════════════
@Service
@RequiredArgsConstructor
public class CatalogService {

    private final CatalogClient catalogClient;

    // ── Approche 1 : par annotation (la plus simple) ──
    // L'ordre des annotations est important : TimeLimiter → CircuitBreaker → Retry
    @CircuitBreaker(name = "catalog-service", fallbackMethod = "getAvailabilityFallback")
    @Retry(name = "catalog-service")        // Retry d'abord, puis CB si tous échouent
    @TimeLimiter(name = "catalog-service")  // Coupe si la réponse dépasse le timeout
    public AvailabilityResponse getAvailability(UUID bookId) {
        return catalogClient.getAvailability(bookId);
    }

    // Fallback : appelé quand le CB est OPEN ou quand tous les retries échouent.
    // RÈGLE : même signature que la méthode originale + Throwable en dernier paramètre.
    private AvailabilityResponse getAvailabilityFallback(UUID bookId, Throwable ex) {
        log.warn("CB fallback for bookId={}, cause={}", bookId, ex.getMessage());
        // Stratégie conservative : on dit "indisponible" plutôt que de planter
        return new AvailabilityResponse(false, 0, "DEGRADED");
    }

    // ── Approche 2 : programmatique (plus de contrôle) ──
    // Utile quand on veut des fallbacks différents selon le type d'erreur
    public AvailabilityResponse getAvailabilityProgrammatic(UUID bookId) {
        CircuitBreaker cb = circuitBreakerRegistry.circuitBreaker("catalog-service");

        // "Décorer" l'appel avec le CB : chaque appel passe par le CB
        Supplier<AvailabilityResponse> decoratedSupplier = CircuitBreaker
            .decorateSupplier(cb, () -> catalogClient.getAvailability(bookId));

        return Try.ofSupplier(decoratedSupplier)
            // Si CB est OPEN → réponse spécifique "CB_OPEN"
            .recover(CallNotPermittedException.class,
                ex -> new AvailabilityResponse(false, 0, "CB_OPEN"))
            // Si autre erreur → réponse générique
            .recover(Exception.class,
                ex -> new AvailabilityResponse(false, 0, "ERROR"))
            .get();
    }
}

            "failedCalls": 1            // 1 seul échec sur 5
          },
          "status": "UP"                // Le service est considéré sain
        }
      }
    }
  }
}

L'ordre d'application des décorateurs Resilience4j compte :

TimeLimiter → CircuitBreaker → Retry → Bulkhead

  2. CircuitBreaker : couper si trop d'échecs.
  3. Retry : retenter si erreur transitoire.
  4. Bulkhead : limiter la concurrence (thread pool isolation).

        // Priorité 1 : utiliser l'API Key du header (pour les clients API)
        String apiKey = exchange.getRequest()
            .getHeaders()
            .getFirst("X-Api-Key");
        if (apiKey != null) {
            return Mono.just(apiKey);  // Chaque API Key a son propre compteur

        // Priorité 2 : utiliser l'adresse IP (pour les navigateurs)
        InetSocketAddress remoteAddress = exchange.getRequest()
            .getRemoteAddress();
        return Mono.just(
            remoteAddress != null ? remoteAddress.getHostString() : "anonymous"
        );
    };

Transactions distribuées

Transactions distribuées — Pattern Saga

SeniorExpert

Dans un monolithe, une transaction ACID locale garantit la cohérence. Dans les microservices, chaque service a sa propre base : une transaction distribuée bloquante (2PC) est trop coûteuse et fragile. Le pattern Saga découpe la transaction en étapes avec des transactions compensatoires en cas d'échec.

🧸 Analogie — La réservation de vacances

Réserver des vacances implique 3 étapes : réserver l'avion, réserver l'hôtel, réserver la voiture. Si l'hôtel refuse (complet), on doit annuler l'avion déjà réservé. C'est une transaction compensatoire. La Saga fait exactement ça : elle exécute les étapes dans l'ordre, et si une étape échoue, elle défait les étapes précédentes en sens inverse.

🎯 Orchestration

Un orchestrateur central (Saga Manager) dicte les étapes à chaque service. Chaque service répond "succès" ou "échec".

✅ Flux visible et centralisé.
✅ Facile à auditer et à déboguer.
⚠️ Single point of complexity.

🔄 Chorégraphie

Chaque service réagit aux événements et publie les siens. Pas de chef d'orchestre.

✅ Découplage maximal.
✅ Naturellement scalable.
⚠️ Flux difficile à visualiser.

// ═══════════════════════════════════════════════════════════════
// ÉTATS DE LA SAGA : machine à états pour tracer la progression
// ═══════════════════════════════════════════════════════════════
// Chaque état est persisté en base → on peut reprendre après un crash
public enum LoanSagaState {
    STARTED,              // Saga initiée, rien encore fait
    BOOK_RESERVED,        // Étape 1 OK : le livre est réservé
    STUDENT_VALIDATED,    // Étape 2 OK : l'étudiant est validé
    LOAN_CONFIRMED,       // Étape 3 OK : le prêt est confirmé
    COMPENSATING_BOOK,    // En train d'annuler la réservation du livre
    COMPENSATING_STUDENT, // En train d'annuler la validation étudiant
    FAILED,               // Saga échouée (compensation effectuée)
    COMPLETED             // Saga terminée avec succès
}

// ═══════════════════════════════════════════════════════════════
// ORCHESTRATEUR : exécute les étapes dans l'ordre
// ═══════════════════════════════════════════════════════════════
// C'est le "chef d'orchestre" qui coordonne catalog, identity et loan.
@Component
@RequiredArgsConstructor
public class CreateLoanSaga {

    private final CatalogClient catalogClient;     // Appel sync → catalog-service
    private final IdentityClient identityClient;   // Appel sync → identity-service
    private final LoanRepository loanRepo;         // Accès BDD locale
    private final KafkaTemplate<String, Object> kafka;  // Publication d'événements

    @Transactional
    public LoanSagaResult execute(CreateLoanCommand cmd) {
        // ── Créer et persister l'état initial de la saga ──
        LoanSaga saga = LoanSaga.builder()
            .id(UUID.randomUUID())
            .loanId(cmd.loanId())
            .bookId(cmd.bookId())
            .studentId(cmd.studentId())
            .state(LoanSagaState.STARTED)  // État initial
            .build();
        sagaRepository.save(saga);  // Persister pour survie au crash

        try {
            // ── Étape 1 : réserver le livre ──
            // Si le livre est indisponible → BookNotAvailableException
            catalogClient.reserveBook(cmd.bookId(),
                new ReservationRequest(cmd.loanId()));
            saga.setState(LoanSagaState.BOOK_RESERVED);  // Succès étape 1

            // ── Étape 2 : valider l'étudiant ──
            // Vérifie : compte actif, quota d'emprunts non dépassé, pas de retards
            identityClient.validateStudentForLoan(cmd.studentId());
            saga.setState(LoanSagaState.STUDENT_VALIDATED);  // Succès étape 2

            // ── Étape 3 : confirmer le prêt en base locale ──
            Loan loan = loanRepo.findById(cmd.loanId()).orElseThrow();
            loan.confirm(Instant.now().plus(30, ChronoUnit.DAYS));  // Retour dans 30 jours
            loanRepo.save(loan);
            saga.setState(LoanSagaState.LOAN_CONFIRMED);  // Succès étape 3

            // ── Publier l'événement de succès ──
            kafka.send("loan.created", new LoanCreatedEvent(cmd.loanId(),
                cmd.studentId(), cmd.bookId(), Instant.now()));

            saga.setState(LoanSagaState.COMPLETED);
            return LoanSagaResult.success(cmd.loanId());

        // ── COMPENSATIONS en cas d'échec ──

        } catch (BookNotAvailableException e) {
            // Échec étape 1 → pas de compensation nécessaire (rien n'a été fait)
            saga.setState(LoanSagaState.FAILED);
            return LoanSagaResult.failure("Book not available");

        } catch (StudentSuspendedException e) {
            // Échec étape 2 → il faut compenser l'étape 1 (libérer le livre)
            saga.setState(LoanSagaState.COMPENSATING_BOOK);
            compensateBookReservation(cmd.bookId(), saga);
            saga.setState(LoanSagaState.FAILED);
            return LoanSagaResult.failure("Student account suspended");

        } catch (Exception e) {
            // Échec inattendu → compenser TOUTES les étapes effectuées
            compensateAll(cmd, saga);
            saga.setState(LoanSagaState.FAILED);
            return LoanSagaResult.failure("Unexpected error: " + e.getMessage());

        } finally {
            sagaRepository.save(saga);  // Toujours persister l'état final
        }
    }

    // ── Compensation : annuler la réservation du livre ──
    // ⚠️ La compensation elle-même peut échouer ! Il faut gérer ce cas.
    private void compensateBookReservation(UUID bookId, LoanSaga saga) {
        try {
            catalogClient.releaseBook(bookId);
        } catch (Exception e) {
            // Si même la compensation échoue → alerte critique (intervention humaine)
            log.error("COMPENSATION FAILED for bookId={}", bookId, e);
            saga.addCompensationFailure("book-release", e.getMessage());
            alertingService.criticalAlert("Saga compensation failure", saga);
        }
    }
}

// ═══════════════════════════════════════════════════════════════
// CHORÉGRAPHIE : chaque service réagit aux événements des autres
// ═══════════════════════════════════════════════════════════════
// Pas d'orchestrateur central. Chaque service :
//   1. Écoute les événements qui le concernent
//   2. Fait son travail
//   3. Publie un nouvel événement pour le prochain service
// C'est comme un relais : chaque coureur passe le bâton au suivant.

// ═══ loan-service (initie le processus) ═══
@Service
public class LoanApplicationService {

    @Transactional
    public UUID initiateLoan(CreateLoanRequest request) {
        // Créer un emprunt en statut PENDING (pas encore confirmé)
        Loan loan = new Loan(request.studentId(), request.bookId());
        loan.setStatus(LoanStatus.PENDING);
        loanRepo.save(loan);

        // Publier une INTENTION (pas un fait accompli !)
        // "J'aimerais emprunter ce livre" → catalog-service va vérifier
        kafka.send("loan.initiation-requested",
            new LoanInitiationRequestedEvent(
                loan.getId(), request.bookId(), request.studentId()
            ));

        return loan.getId();  // Réponse immédiate au client (async derrière)
    }

    // ── Écoute la réponse de catalog-service ──
    // Si le livre a été réservé avec succès → passer à l'étape suivante
    @KafkaListener(topics = "book.reservation-confirmed")
    public void onBookReserved(BookReservationConfirmedEvent event) {
        Loan loan = loanRepo.findById(event.loanId()).orElseThrow();
        loan.setStatus(LoanStatus.BOOK_RESERVED);  // Mise à jour du statut
        loanRepo.save(loan);

        // Publier la PROCHAINE ÉTAPE : valider l'étudiant
        kafka.send("student.validation-requested",
            new StudentValidationRequestedEvent(event.loanId(), loan.getStudentId()));
    }

    // ── Écoute le REFUS de catalog-service ──
    // Le livre n'est pas disponible → fin de la saga, pas de compensation
    @KafkaListener(topics = "book.reservation-rejected")
    public void onBookReservationRejected(BookReservationRejectedEvent event) {
        Loan loan = loanRepo.findById(event.loanId()).orElseThrow();
        loan.setStatus(LoanStatus.REJECTED);
        loan.setRejectionReason("Book not available: " + event.reason());
        loanRepo.save(loan);

        // Informer les autres services que l'emprunt est annulé
        kafka.send("loan.rejected",
            new LoanRejectedEvent(event.loanId(), event.reason()));
    }
}

// ═══ catalog-service (réagit à la demande) ═══
// Ce service ne sait PAS qu'il fait partie d'une saga.
// Il réagit simplement aux événements qui le concernent.
@KafkaListener(topics = "loan.initiation-requested")
public void onLoanInitiationRequested(LoanInitiationRequestedEvent event) {
    boolean available = bookRepository.isAvailable(event.bookId());

    if (available) {
        // Le livre est dispo → le réserver et confirmer
        bookRepository.reserve(event.bookId(), event.loanId());
        kafka.send("book.reservation-confirmed",
            new BookReservationConfirmedEvent(event.loanId(), event.bookId()));
    } else {
        // Le livre est pris → refuser
        kafka.send("book.reservation-rejected",
            new BookReservationRejectedEvent(event.loanId(), "No copies left"));
    }
}

Pièges à éviter

Anti-patterns microservices

JuniorSenior

Les microservices mal conçus sont pires qu'un monolithe. Vous avez la complexité du réseau ET la perte de la cohérence locale. Voici les 5 erreurs les plus fréquentes vues en production.

🧸 Le test ultime

Posez-vous cette question : "Est-ce que je peux éteindre ce service sans impacter les autres ?" Si la réponse est non → vous avez un Distributed Monolith, pas des microservices.

Les 5 anti-patterns en un coup d'œil

1. Distributed Monolith Services séparés mais couplés → déploiement coordonné obligatoire
2. Shared Database Plusieurs services lisent la même table → couplage au schéma
3. Chatty N+1 N appels réseau au lieu d'1 seul → latence × N
4. Nano-services 1 service par entité → coût ops exorbitant
5. Sync Chain A→B→C→D synchrone → latence = somme, fiabilité = produit

🔴 1. Distributed Monolith

Services techniquement séparés mais si fortement couplés qu'ils doivent être développés, testés et déployés ensemble. On a la complexité du distribué sans les bénéfices de l'autonomie.

Symptômes : "On ne peut pas déployer A sans déployer B." — Appels synchrones en chaîne : A→B→C→D. — Base de données partagée.

// ❌ ANTI-PATTERN : chaîne d'appels synchrones
// loan-service → catalog-service → catalog-service → identity-service
// Problème : si identity-service est down, TOUT échoue (cascade de pannes)
// Latence = somme : 50ms + 80ms + 120ms = 250ms minimum
@GetMapping("/loans/{id}/details")
public LoanDetailsDto getDetails(@PathVariable UUID id) {
    Loan loan = loanRepo.findById(id).orElseThrow();
    Book book = catalogClient.getBook(loan.getBookId());           // appel réseau 1
    Author author = catalogClient.getAuthor(book.getAuthorId());   // appel réseau 2
    Student student = identityClient.getStudent(loan.getStudentId()); // appel réseau 3
    // 3 appels réseau synchrones = 3 points de panne possibles !
    return new LoanDetailsDto(loan, book, author, student);
}
// ✅ SOLUTION : CQRS + Vue matérialisée locale (read model)
// loan-service maintient une COPIE LOCALE des données dont il a besoin.
// Les données sont mises à jour via des événements Kafka (async).

// Étape 1 : écouter les changements de catalog-service
@KafkaListener(topics = "book.updated")

🔴 2. Shared Database

Plusieurs microservices lisent/écrivent les mêmes tables. Impossible de migrer, scaler ou redéployer indépendamment.

// ❌ ANTI-PATTERN : notification-service accède DIRECTEMENT à la table "loans"
// Problème : si loan-service change son schéma (renomme une colonne, change un type),
// notification-service CASSE sans prévenir. Les deux services sont couplés par la BDD.
@Repository
public class NotificationRepository {
    @Query("SELECT * FROM loans WHERE due_date < :date AND notified = false")
    List<Loan> findOverdue(LocalDate date);  // Requête sur la table d'un AUTRE service !
}

// ✅ SOLUTION : notification-service écoute les événements Kafka
// loan-service publie "loan.overdue" quand un emprunt est en retard.
// notification-service réagit sans connaître le schéma de loan-service.
@KafkaListener(topics = "loan.overdue")
public void onLoanOverdue(LoanOverdueEvent event) {
    // L'événement contient exactement les données dont on a besoin
    // Pas de couplage au schéma SQL de loan-service
    notificationService.sendOverdueNotice(event.studentId(), event.loanId(),
        event.dueDate());
}

🔴 3. Chatty Communication (N+1 distribué)

Trop d'appels réseau pour un seul cas d'usage. Chaque appel ajoute de la latence et de la fragilité. C'est le SELECT N+1 de JPA, mais en version réseau — 100x plus lent.

// ❌ ANTI-PATTERN : N+1 en distribué
// Pour afficher 20 emprunts avec les infos du livre, on fait 20 appels HTTP !
// Latence = 20 × 50ms = 1 seconde minimum, plus les risques de panne
for (UUID bookId : loanedBookIds) {
    Book book = catalogClient.getBook(bookId);  // 1 appel réseau par livre !
}

// ✅ SOLUTION : API de batch — 1 seul appel pour N livres
@FeignClient(name = "catalog-service")
public interface CatalogClient {
    // Endpoint qui accepte une LISTE d'IDs → 1 seul appel réseau
    @PostMapping("/internal/books/batch")
    List<BookDto> getBooksBatch(@RequestBody List<UUID> bookIds);
}
// 20 livres = 1 appel de ~2ms au lieu de 20 appels de 50ms = 40x plus rapide

🔴 4. Nano-services

Découpage trop fin : un service pour chaque entité ou chaque opération. Le coût opérationnel explose (monitoring, déploiement, debug) et la latence réseau ruine les performances. Si votre service n'a qu'un ou deux endpoints, il est probablement trop petit.

// ❌ Nano-services (chaque attribut est un service séparé !)
// → 4 repos, 4 pipelines CI/CD, 4 bases, 4 instances à monitorer
// → Pour afficher un livre : 4 appels réseau en cascade
BookTitleService           ← juste le titre
BookAuthorService          ← juste l'auteur
BookISBNService            ← juste l'ISBN
BookAvailabilityService    ← juste le stock

// ✅ Un service par DOMAINE COHÉRENT
// → 1 repo, 1 pipeline, 1 base, 1 instance
// → Tout ce qui concerne les livres est au même endroit
catalog-service  ← titre + auteur + ISBN + stock + recherche

🔴 5. Synchronous Chain (couplage temporel)

Toute la chaîne tombe si un seul service est lent ou indisponible. La latence totale est la somme de toutes les latences. Plus la chaîne est longue, plus le risque de panne augmente exponentiellement.

🧸 Résumé des anti-patterns — La règle d'or

Si vous devez coordonner le déploiement de plusieurs services, ou si la panne d'un service cascade sur les autres, vous avez probablement un Distributed Monolith. Posez-vous la question : "Est-ce que je peux éteindre ce service sans impacter les autres ?" Si non, il faut repenser le découplage.

Stratégie de tests dans les microservices

MidSenior

La pyramide des tests traditionnelle s'adapte aux microservices. L'objectif : détecter les bugs au plus tôt, le plus localement possible, sans dépendre des autres services à chaque exécution.

🧸 Analogie — Tester une voiture

Tests unitaires = tester chaque pièce isolément (le moteur tourne, les freins serrent). Tests d'intégration = vérifier que le moteur + la transmission + les roues fonctionnent ensemble. Contract tests = vérifier que le volant contrôle bien les roues (interface entre composants). Tests E2E = conduire la voiture sur route (coûteux, lent, mais nécessaire pour les scénarios critiques).

Service Mesh — Introduction à Istio

Expert

Un Service Mesh déplace les préoccupations réseau (mTLS, Circuit Breaker, retry, observabilité) hors du code et dans l'infrastructure, via des proxies sidecar injectés automatiquement dans chaque pod.

🧸 Analogie — Le garde du corps invisible

Imaginez que chaque service a un garde du corps personnel (le proxy Envoy) qui intercepte toutes ses communications. Ce garde chiffre les messages (mTLS), coupe la ligne si le correspondant ne répond pas (Circuit Breaker), retente automatiquement, et note tout dans un carnet (tracing). Le service lui-même ne sait même pas que le garde existe — il parle normalement.

Politique de retry et Circuit Breaker — VirtualService + DestinationRule Istio

# ═══════════════════════════════════════════════════════════════
# VIRTUALSERVICE : configure le routage et les retries
# ═══════════════════════════════════════════════════════════════
# Équivalent de la config Resilience4j, mais dans l'infra YAML
# → pas besoin de modifier le code Java !
apiVersion: networking.istio.io/v1alpha3
kind: VirtualService
metadata:
  name: catalog-service
spec:
  hosts:
    - catalog-service     # S'applique aux appels vers catalog-service
  http:
    - retries:
        attempts: 3        # 3 tentatives max (comme Resilience4j maxAttempts)
        perTryTimeout: 2s  # Timeout par tentative (comme readTimeout Feign)
        retryOn: connect-failure,refused-stream,503   # Quand retenter

      # ── Chaos Engineering : injecter des pannes volontairement ──
      # En production simulée, on injecte 5% de latence pour tester la résilience
      fault:
        delay:
          percentage:
            value: 5       # 5% des requêtes reçoivent un délai artificiel
          fixedDelay: 2s    # 2 secondes de délai
---
# ═══════════════════════════════════════════════════════════════
# DESTINATIONRULE : configure le Circuit Breaker côté infrastructure
# ═══════════════════════════════════════════════════════════════
apiVersion: networking.istio.io/v1alpha3
kind: DestinationRule
metadata:
  name: catalog-service-cb
spec:
  host: catalog-service
  trafficPolicy:
    outlierDetection:                  # = Circuit Breaker d'Istio
      consecutive5xxErrors: 5          # 5 erreurs 5xx consécutives → éjecter l'instance
      interval: 30s                    # Évaluer toutes les 30 secondes
      baseEjectionTime: 1m            # Instance éjectée pendant 1 minute minimum
      maxEjectionPercent: 50           # Ne jamais éjecter plus de 50% des instances
                                        # (garder un minimum de capacité)

✅ Avantages du Service Mesh

  • mTLS automatique : chiffrement entre services sans modifier le code.
  • Observabilité gratuite : traces, métriques, logs sans instrumentation.
  • Circuit Breaker infrastructure : pas de Resilience4j dans le code.
  • Chaos Engineering : injecter des pannes via YAML.

⚠️ Inconvénients

  • Complexité opérationnelle accrue — réservé aux équipes DevOps matures.
  • Overhead latence du proxy sidecar (~1-5ms par hop).
  • Courbe d'apprentissage : Kubernetes + Istio + Envoy à maîtriser.
  • Debug plus complexe : la config réseau est hors du code.

Quiz de fin — Jour 4

1. Pourquoi une base de données partagée nuit-elle à l'autonomie des microservices ?

Voir la réponse

Elle crée un couplage fort au niveau du schéma. Si une équipe modifie la base, elle peut casser un autre service sans le savoir, ce qui empêche les déploiements indépendants. La solution est le pattern Database per Service couplé à la communication par événements.

2. Quelle différence entre orchestration et chorégraphie dans les Sagas ?

Voir la réponse

En orchestration, un service central (Saga Manager) dicte les étapes et connaît le flux complet. En chorégraphie, chaque service réagit aux événements et publie les siens sans chef d'orchestre. L'orchestration est plus visible et facile à auditer ; la chorégraphie offre un meilleur découplage mais un flux plus difficile à tracer.

3. Qu'est-ce qu'un "distributed monolith" et comment l'éviter ?

Voir la réponse

Un Distributed Monolith est un anti-pattern où les services sont techniquement séparés mais si fortement couplés (base partagée, appels synchrones en chaîne, déploiement coordonné) qu'ils ont la complexité du distribué sans les avantages de l'autonomie. On l'évite en respectant les bounded contexts, en utilisant une base par service, et en communiquant via API ou événements.

4. Décrivez les 3 états d'un Circuit Breaker et les transitions entre eux.

Voir la réponse

CLOSED : appels normaux. Si le taux d'échecs dépasse le seuil → passe à OPEN. OPEN : appels court-circuités (fallback immédiat). Après un délai d'attente → passe à HALF-OPEN. HALF-OPEN : quelques appels de test passent. Si réussis → CLOSED. Si échoués → OPEN à nouveau.

5. Pourquoi utilise-t-on Testcontainers plutôt que des mocks pour les tests d'intégration ?

Voir la réponse

Les mocks simulent le comportement mais peuvent diverger de l'implémentation réelle. Testcontainers démarre de vraies instances PostgreSQL, Kafka, Redis, etc. dans des conteneurs Docker pendant les tests. On teste ainsi le vrai comportement de la base de données (transactions, contraintes, types), ce qui capture des bugs impossibles à détecter avec des mocks.

6. Qu'est-ce que l'Exactly-Once Semantics (EOS) dans Kafka et comment l'activer ?

Voir la réponse

EOS garantit que chaque message est traité exactement une fois, même en cas de crash ou retry. Il s'active avec enable.idempotence=true côté producteur (évite les doublons) et isolation.level=read_committed côté consommateur (ne lit que les messages committés). L'utilisation de KafkaTransactionManager permet de coordonner atomiquement BDD et Kafka.

7. (Expert) Quels avantages offre un Service Mesh comme Istio par rapport à Resilience4j dans le code ?

Voir la réponse

Istio déplace les préoccupations réseau (mTLS, retry, circuit breaker, tracing) hors du code et dans l'infrastructure via des proxies Envoy sidecar. Avantages : les politiques de résilience sont configurées en YAML sans modifier le code Java, le mTLS est automatique entre tous les services, et l'observabilité (traces, métriques) est fournie sans instrumentation. Inconvénient : complexité opérationnelle accrue — réservé aux équipes avec maturité Kubernetes.

8. Comment éviter le N+1 problem dans un contexte de microservices ?

Voir la réponse

Trois approches : (1) API de batch — exposer un endpoint POST /books/batch qui accepte une liste d'IDs pour un seul appel réseau. (2) Vue matérialisée locale — le service maintient une copie locale des données dont il a besoin, mise à jour via événements Kafka. (3) GraphQL Federation — laisser le client composer la requête pour éviter les appels en cascade côté serveur.
