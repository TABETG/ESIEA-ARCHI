1. Résilience : empêcher la panne locale de devenir globale

JuniorMidSenior

🧸 Analogie — La cantine en panne

Imagine que la cantine ne réponde plus. Sans résilience, tous les élèves restent bloqués à attendre devant la porte fermée — et les cours ne reprennent pas. Avec résilience, la cantine propose un sandwich (fallback) ou dit "reviens dans 10 minutes" (circuit breaker). L'école continue de fonctionner.

Dans un système distribué, un seul service lent peut provoquer une cascade failure : ses appelants s'entassent sur des threads bloqués, ce qui bloque leurs propres appelants, et ainsi de suite jusqu'à l'indisponibilité totale.

Cascade failure — comment une panne se propage

🟢 Client → Service A → Service B (lent/mort)

Le client appelle A, qui appelle B. B ne répond plus.

B ne répond pas
🟡 Les threads de A s'accumulent

A attend B → ses threads sont bloqués. Les nouvelles requêtes s'entassent dans la file.

Pool threads épuisé
🔴 Service A et le Client sont DOWN

A ne peut plus répondre à personne → le client reçoit des erreurs 503. Toute la chaîne est tombée.

MécanismeRôleAnalogieConfig typique
TimeoutCouper l'attente excessiveMinuterie de four500ms – 2s
RetryRetenter un échec transitoireRappeler après une mauvaise ligne2–3 fois, backoff expo

1.1 Timeout & Retry

🟢 Junior

Le timeout abandonne l'attente d'une réponse après un délai défini. Le retry retente automatiquement en cas d'échec transitoire. Ne jamais configurer un retry sans timeout.

# ═══════════════════════════════════════
# TIMEOUT + RETRY — Première ligne de défense
# ═══════════════════════════════════════
resilience4j:
  timelimiter:
    instances:
      catalogService:
        timeout-duration: 1500ms    # Si catalog-service ne répond pas en 1.5s → abandon
                                     # Sans ça, le thread attend indéfiniment (danger !)
        cancel-running-future: true  # Annuler le CompletableFuture si timeout

  retry:
    instances:
      catalogService:
        max-attempts: 3                    # 3 tentatives max (1 initiale + 2 retries)
        wait-duration: 200ms               # Attendre 200ms entre les tentatives
        enable-exponential-backoff: true   # Délais croissants : 200ms → 400ms → 800ms
        exponential-backoff-multiplier: 2  # Chaque retry attend 2× plus longtemps
        # ⚠️ NE PAS retenter les erreurs MÉTIER (le livre n'existe pas = c'est normal)
        ignore-exceptions:
          - com.example.exception.BookNotFoundException

⚠️ Idempotence obligatoire avant tout retry

Ne retenter que les opérations idempotentes (GET, PUT, DELETE). Un retry sur un POST de création peut créer plusieurs fois la même ressource. Toujours vérifier avant d'activer le retry sur une opération d'écriture.

1.2 Circuit Breaker — Les 3 états

🟡 Intermédiaire

Les 3 états du Circuit Breaker

🟢 CLOSED — normal

Appels passent normalement. On compte les erreurs dans une fenêtre glissante.

Taux d'erreur > seuil (50%)
🔴 OPEN — protection activée

Appels rejetés immédiatement — pas d'appel réseau. Fallback retourné. Attente de wait-duration.

Après wait-duration (30s)
🟡 HALF-OPEN — test de récupération

X appels de test autorisés. Si succès → retour CLOSED. Si échec → retour OPEN.

# ═══════════════════════════════════════
# CIRCUIT BREAKER — Disjoncteur intelligent
# ═══════════════════════════════════════
resilience4j:
  circuitbreaker:
    instances:
      catalogService:
        sliding-window-type: COUNT_BASED     # Évalue les N derniers appels (pas par durée)
        sliding-window-size: 10              # Fenêtre de 10 appels
        failure-rate-threshold: 50           # Si 50% échouent → circuit OPEN (disjoncteur déclenché)
        slow-call-rate-threshold: 80         # Si 80% des appels sont trop lents → aussi OPEN
        slow-call-duration-threshold: 1000ms # Un appel est "lent" s'il dépasse 1 seconde
        wait-duration-in-open-state: 30s     # Rester OPEN 30s (laisser le service récupérer)
        permitted-number-of-calls-in-half-open-state: 3  # 3 appels de test en HALF-OPEN
        register-health-indicator: true      # Expose l'état dans /actuator/health
@Service
@Slf4j
public class LoanService {

    // ═══════════════════════════════════════════════════════════════
    // ORDRE D'EXÉCUTION DES PATTERNS (de l'externe vers l'interne) :
    //   TimeLimiter → CircuitBreaker → Retry
    // ═══════════════════════════════════════════════════════════════
    // 1. TimeLimiter : coupe si la réponse dépasse 1.5s
    // 2. CircuitBreaker : si trop d'échecs, court-circuite sans appel réseau
    // 3. Retry : retente 3 fois avec backoff exponentiel
    // ⚠️ Retry est À L'EXTÉRIEUR du CircuitBreaker — sinon chaque retry
    //    compterait comme un échec séparé dans la fenêtre du CB !
    @TimeLimiter(name = "catalogService")
    @CircuitBreaker(name = "catalogService",
                    fallbackMethod = "fallbackAvailability")
    @Retry(name = "catalogService")
    public CompletableFuture<AvailabilityResponse> getAvailability(UUID bookId) {
        // CompletableFuture requis par TimeLimiter (non-bloquant)
        return CompletableFuture.supplyAsync(
            () -> catalogClient.getAvailability(bookId)
        );
    }

    // FALLBACK : appelé quand le CB est OPEN ou tous les retries échouent
    // Règle : même signature que la méthode originale + Throwable en dernier
    private CompletableFuture<AvailabilityResponse> fallbackAvailability(
            UUID bookId, Throwable ex) {
        log.warn("Fallback triggered bookId={} cause={}", bookId, ex.getMessage());
        // Réponse dégradée : on dit "inconnu" au lieu de planter
        return CompletableFuture.completedFuture(
            AvailabilityResponse.degraded(bookId)
        );
    }
}

1.3 Bulkhead & Rate Limiter

🔴 Expert

Le Bulkhead isole les ressources : un service externe lent ne monopolise pas tous les threads. Deux modes possibles :

Sémaphore (même thread, limite de concurrence) 
resilience4j:
  bulkhead:
    instances:
      catalogService:
        max-concurrent-calls: 10   # Max 10 appels simultanés vers catalog-service
                                    # Le 11ème appel est rejeté immédiatement
        max-wait-duration: 10ms    # Attendre max 10ms pour un slot libre
Thread Pool (thread dédié, isolation totale) 
resilience4j:
  thread-pool-bulkhead:
    instances:
      paymentService:
        core-thread-pool-size: 4   # 4 threads dédiés au paymentService
        max-thread-pool-size: 8    # Max 8 threads en pic
        queue-capacity: 20         # 20 requêtes en file d'attente
        # Avantage : si paymentService est lent, il ne monopolise
        # que SES 8 threads, pas ceux des autres services

✅ Ordre recommandé des patterns

De l'externe vers l'interne : Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead. Jamais Retry à l'intérieur du CircuitBreaker : les retries gonfleraient artificiellement la fenêtre d'erreurs et ouvriraient le circuit trop tôt.

🖥️ Live Coding — Cascade failure

  1. Démarrer un slow-service répondant après 3 secondes
  2. Appeler depuis loan-service sans timeout → observer les threads bloqués via /actuator/metrics/jvm.threads.live
  3. Activer le TimeLimiter → les appels reviennent avec fallback en 1,5 s
  4. Activer le CircuitBreaker → après 5 échecs, les appels sont court-circuités immédiatement

2. Observabilité : les 3 piliers

JuniorMidExpert

L'observabilité répond à trois questions fondamentales en production :

📄 Logs

Quoi s'est passé, quand, dans quel contexte. Événements discrets horodatés.

Logback → Elasticsearch → Kibana (ELK)

📊 Métriques

Combien d'événements, quelle latence, quel taux d'erreur. Agrégats dans le temps.

Micrometer → Prometheus → Grafana

🔗 Traces

Où passe la requête entre services. Parcours complet d'une transaction.

OpenTelemetry → Jaeger / Tempo / Zipkin

2.1 Logs structurés et corrélation MDC

🟢 Junior

MDC — Mapped Diagnostic Context

Dictionnaire thread-local de SLF4J. Chaque entrée est automatiquement ajoutée à tous les logs du thread courant, sans avoir à passer les métadonnées explicitement à chaque méthode.

❌ Log sans contexte 
// Impossible de retrouver tous les logs d'un emprunt précis
log.info("Emprunt créé");
log.error("Erreur lors de la création");
✅ Log structuré avec corrélation 
// ═══════════════════════════════════════════════════════════════
// MDC : ajouter du contexte à TOUS les logs du thread courant
// ═══════════════════════════════════════════════════════════════
// Problème : en production, des milliers de requêtes passent en même temps.
// Comment retrouver TOUS les logs d'un emprunt précis ?
// Solution : le MDC ajoute correlationId et studentId à chaque log automatiquement.
@RestController
@Slf4j
public class LoanController {

    @PostMapping("/api/loans")
    public ResponseEntity<LoanDto> createLoan(
            @RequestBody CreateLoanRequest req,
            @RequestHeader("X-Correlation-Id") String correlationId) {

        // Mettre des clés dans le MDC → apparaîtront dans TOUS les logs
        // de ce thread, y compris dans les services appelés via Feign
        MDC.put("correlationId", correlationId);  // ID unique de la requête
        MDC.put("studentId", req.getStudentId().toString());

        try {
            LoanDto loan = loanService.createLoan(req);
            // Ce log contiendra automatiquement correlationId et studentId
            // → facile à chercher dans Kibana : correlationId="abc-123"
            log.info("loan-created loanId={} bookId={}", loan.getId(), loan.getBookId());
            return ResponseEntity.status(201).body(loan);
        } finally {
            MDC.clear(); // ⚠️ TOUJOURS nettoyer — sinon le prochain thread
                         // hérite du contexte précédent (fuite de données)
        }
    }
}
<!-- Logback envoie les logs en JSON → Elasticsearch → Kibana (ELK stack) -->
<!-- Chaque ligne de log contient le correlationId et le studentId du MDC -->
<configuration>
  <appender name="JSON" class="ch.qos.logback.core.ConsoleAppender">
    <encoder class="net.logstash.logback.encoder.LogstashEncoder">
      <!-- Inclure ces clés MDC dans chaque ligne de log JSON -->
      <includeMdcKeyName>correlationId</includeMdcKeyName>
      <includeMdcKeyName>studentId</includeMdcKeyName>
      <!-- Champs fixes ajoutés à chaque log (identifier le service et l'env) -->
      <customFields>{"service":"loan-service","env":"prod"}</customFields>
    </encoder>
  </appender>
  <root level="INFO"><appender-ref ref="JSON"/></root>
</configuration>

2.2 Métriques avec Micrometer

🟡 Intermédiaire
TypeUsageExemple

GaugeValeur instantanée variableEmprunts en cours

// ═══════════════════════════════════════════════════════════════
// MÉTRIQUES MICROMETER : compteurs et timers pour Prometheus/Grafana
// ═══════════════════════════════════════════════════════════════
// Les métriques répondent à "combien ?" et "quelle performance ?"
// Elles sont collectées par Prometheus et affichées dans Grafana.
@Service
public class LoanService {

    private final Counter loansCreated;       // Compteur monotone : ne fait que monter
    private final Counter loansRejected;
    private final Timer loanCreationTimer;    // Mesure la durée + le nombre d'appels

    public LoanService(MeterRegistry registry) {
        // ── Counter : compter les événements ──
        loansCreated = Counter.builder("loans.created")
            .description("Prêts créés avec succès")
            .register(registry);   // Enregistrer dans Prometheus

        loansRejected = Counter.builder("loans.rejected")
            .description("Prêts refusés (quota, indisponibilité)")
            .register(registry);

        // ── Timer : mesurer la durée d'une opération ──
        loanCreationTimer = Timer.builder("loans.creation.duration")
            .description("Durée de création d'un prêt")
            .publishPercentiles(0.5, 0.95, 0.99)   // Publier p50, p95, p99
            // p95 = 95% des requêtes sont plus rapides que cette valeur
            // → C'est LE chiffre à surveiller en prod (pas la moyenne !)
            .register(registry);
    }

    public LoanDto createLoan(CreateLoanRequest req) {
        // record() mesure automatiquement la durée du bloc lambda
        return loanCreationTimer.record(() -> {
            validateQuota(req.getStudentId());
            LoanDto loan = LoanMapper.toDto(loanRepository.save(toLoan(req)));
            loansCreated.increment();  // +1 dans le compteur Prometheus
            return loan;
        });
    }
}

2.3 Traces distribuées avec OpenTelemetry

🔴 Expert

Trace d'une requête — visualisation des spans

POST /api/loans
200ms total
loan-service
validate-quota (5ms)
catalog-service
GET /availability (80ms) ← goulot !
notif-service
POST /notify (15ms async)

Un span est une unité de travail (un appel HTTP, une requête SQL). Une trace est l'arbre de spans partagés via un même traceId, propagé dans le header HTTP traceparent (standard W3C Trace Context). Grâce aux traces, on voit d'un coup d'œil que catalog-service est le goulot d'étranglement (80ms sur 200ms total).

<!-- Dépendances pour le distributed tracing -->
<!-- Micrometer bridge : connecte Spring Boot à OpenTelemetry -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-tracing-bridge-otel</artifactId>
</dependency>
<!-- Exporter les traces vers Zipkin (ou Jaeger, ou Tempo) -->
<dependency>
  <groupId>io.opentelemetry</groupId>
  <artifactId>opentelemetry-exporter-zipkin</artifactId>
</dependency>
management:
  tracing:
    sampling:
      probability: 1.0   # 100% des requêtes tracées en dev
                           # En prod : 0.1 (10%) pour limiter le volume
spring:
  zipkin:
    base-url: http://zipkin:9411   # URL du collecteur de traces
# Bonus : le traceId est automatiquement injecté dans les logs MDC
# → on peut passer de Kibana (logs) à Zipkin (traces) d'un clic
// ═══════════════════════════════════════════════════════════════
// SPAN PERSONNALISÉ : mesurer une opération spécifique dans la trace
// ═══════════════════════════════════════════════════════════════
// Les spans HTTP sont créés automatiquement par Spring.
// Mais pour mesurer une opération MÉTIER (ex: vérification quota),
// il faut créer un span manuellement.
@Service
public class LoanService {

    @Autowired Tracer tracer;  // Injecté par Spring — gère les spans

    public LoanDto createLoan(CreateLoanRequest req) {
        // ── Créer un span pour la vérification du quota ──
        Span span = tracer.nextSpan()
            .name("loan.quota-check")               // Nom affiché dans Zipkin/Jaeger
            .tag("studentId", req.getStudentId().toString())  // Métadonnée pour le debug
            .start();

        try (Tracer.SpanInScope ws = tracer.withSpan(span)) {
            // Tout ce qui s'exécute ici est "dans" le span
            // Si on appelle d'autres services, ils hériteront du traceId
            validateQuota(req.getStudentId());
            return doCreateLoan(req);
        } catch (QuotaExceededException e) {
            span.tag("error", "quota-exceeded");  // Marquer le span comme erreur
            throw e;
        } finally {
            span.end(); // ⚠️ TOUJOURS finir le span — sinon il apparaît comme
                         // "en cours" indéfiniment dans Zipkin
        }
    }
}

✅ Corrélation logs + traces

Micrometer Tracing injecte automatiquement traceId et spanId dans le MDC Logback. Résultat : chaque ligne de log contient le traceId, permettant de passer de Kibana (logs) à Grafana Tempo (traces) d'un seul clic.

3. Monitoring, Health Checks & alerting

JuniorMidExpert

🧸 Analogie — Le contrôle technique

Un service peut "tourner" (le moteur démarre) mais être incapable de répondre (les freins ne marchent pas). Le health check c'est comme un contrôle technique complet — il vérifie si tout fonctionne en profondeur, pas juste si le moteur tourne.

SondeQuestionRéponse KOAction Kubernetes
LivenessLe process est-il vivant ?Deadlock, corruption mémoireRedémarre le pod
ReadinessPeut-il recevoir du trafic ?DB coupée, warm-up en coursRetire du load balancer
StartupA-t-il fini de démarrer ?Init longue (> 30s)Attend avant les autres sondes
 
# ═══════════════════════════════════════
# SPRING ACTUATOR : exposer les sondes et métriques
# ═══════════════════════════════════════
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus,metrics,circuitbreakers
        # ↑ Endpoints exposés via HTTP :
        # /actuator/health      → état de santé (liveness/readiness)
        # /actuator/prometheus  → métriques au format Prometheus
        # /actuator/circuitbreakers → état des Circuit Breakers
  endpoint:
    health:
      probes:
        enabled: true         # Active /actuator/health/liveness et /readiness
                               # → utilisés par Kubernetes pour les probes
      show-details: always    # Montrer les détails des composants (DB, CB, etc.)
                               # ⚠️ En prod, utiliser "when_authorized" pour sécuriser
  metrics:
    export:
      prometheus:
        enabled: true         # Exposer les métriques au format Prometheus
    tags:
      application: loan-service                  # Tag pour identifier dans Grafana
      env: ${SPRING_PROFILES_ACTIVE:dev}         # Tag pour l'environnement
🟡 Intermédiaire 
// ═══════════════════════════════════════════════════════════════
// HEALTH INDICATOR PERSONNALISÉ : vérifier catalog-service
// ═══════════════════════════════════════════════════════════════
// Spring Actuator vérifie automatiquement la BDD, Redis, etc.
// Mais pour vérifier un SERVICE EXTERNE (catalog-service),
// il faut créer un HealthIndicator personnalisé.
@Component
public class CatalogServiceHealthIndicator implements HealthIndicator {

    private final CatalogClient catalogClient;
    private final CircuitBreakerRegistry cbRegistry;

    @Override
    public Health health() {
        // Vérifier l'état du Circuit Breaker d'abord
        CircuitBreaker cb = cbRegistry.circuitBreaker("catalogService");
        if (cb.getState() == CircuitBreaker.State.OPEN) {
            // Si le CB est OPEN → catalog-service est considéré DOWN
            return Health.down()
                .withDetail("circuit-breaker", "OPEN")
                .withDetail("reason", "Trop d'échecs vers catalog-service")
                .build();
        }

        // Si le CB est CLOSED ou HALF-OPEN → tester avec un ping réel
        try {
            catalogClient.ping();  // Appel léger pour vérifier que le service répond
            return Health.up()
                .withDetail("circuit-breaker", cb.getState().name())
                .build();
        } catch (Exception e) {
            return Health.down().withDetail("error", e.getMessage()).build();
        }
    }
}

✅ 4 Golden Signals (Google SRE)

Les 4 métriques que Google surveille sur TOUS ses services. C'est le minimum vital pour savoir si un service fonctionne correctement :

  • Latency — Temps de traitement (p95, p99). "Est-ce rapide ?"
  • Traffic — Volume de requêtes (req/s). "Combien de trafic ?"
  • Errors — Taux d'erreurs 5xx. "Est-ce fiable ?"
  • Saturation — CPU, mémoire, threads, connexions DB. "Est-ce plein ?"

Une alerte Prometheus sur chacun de ces 4 indicateurs est le minimum viable.

🔴 Expert 
# ═══════════════════════════════════════
# ALERTE PROMETHEUS : se déclenche automatiquement si trop d'erreurs
# ═══════════════════════════════════════
# Cette règle surveille le taux d'erreurs 5xx sur les 5 dernières minutes.
# Si > 5% pendant 2 minutes → alerte "critical" → notification PagerDuty/Slack
- alert: HighErrorRate
  expr: |
    rate(http_server_requests_seconds_count{status=~"5.."}[5m])
    /
    rate(http_server_requests_seconds_count[5m]) > 0.05
  for: 2m                         # Attendre 2 min avant de déclencher (éviter les faux positifs)
  labels:
    severity: critical             # Niveau d'urgence (critical = PagerDuty wake-up)
  annotations:
    summary: "Taux d'erreur élevé sur {{ $labels.application }}"
    description: "{{ $value | humanizePercentage }} d'erreurs 5xx détectées"

4. Sécurité inter-services : JWT, OAuth2 / OIDC, RBAC

JuniorMidExpert

🧸 Analogie — Le badge d'entrée

Le JWT c'est comme un badge visiteur tamponné par l'accueil (Keycloak). Il dit qui tu es (nom) et ce que tu peux faire (zones autorisées). Le vigile (Spring Security) vérifie le tampon — s'il est faux ou périmé, l'accès est refusé. Le badge est lisible par tous (pas chiffré), mais infalsifiable grâce au tampon.

4.1 Anatomie d'un JWT

Structure d'un JWT — 3 parties séparées par des points

Un JWT est signé en 3 parties encodées en Base64URL — lisibles, pas chiffrées :

Header
{ "alg": "RS256", "typ": "JWT" }
Algorithme de signature utilisé
Payload (claims)
{ "sub": "user123", "roles": ["LIBRARIAN"], "exp": 1735686000 }
Données utilisateur — lisibles par tous !
Signature
RSASHA256(header + payload, clé_privée)
Vérifié avec la clé publique de l'IdP

⚠️ JWT ≠ chiffrement

Le payload est lisible par n'importe qui (c'est juste du Base64). Ne jamais y mettre de données sensibles (mot de passe, numéro de carte). La signature garantit l'intégrité (pas modifié), pas la confidentialité (pas lisible).

4.2 Flux OAuth2 Authorization Code (OIDC)

Flux OAuth2 — Comment le token arrive jusqu'au service

1. L'utilisateur accède à /loans

Le navigateur est redirigé vers Keycloak (page de login)

2. L'utilisateur se connecte sur Keycloak

Keycloak vérifie les identifiants → retourne un authorization code

3. L'application échange le code contre un JWT

POST /token vers Keycloak → reçoit un access_token (JWT signé)

4. Le JWT est envoyé à chaque requête

Header Authorization: Bearer eyJhbGci... — vérifié par Spring Security

// ═══════════════════════════════════════════════════════════════
// SPRING SECURITY : configurer l'authentification JWT
// ═══════════════════════════════════════════════════════════════
// Ce service est un "Resource Server" : il VÉRIFIE les JWT
// mais ne les ÉMET PAS (c'est le rôle de Keycloak/Auth0).
@Configuration
@EnableWebSecurity
@EnableMethodSecurity  // Active @PreAuthorize sur les méthodes
public class SecurityConfig {

    @Bean
    SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            // ── Désactiver CSRF : API stateless, pas de session navigateur ──
            .csrf(csrf -> csrf.disable())

            // ── Pas de session HTTP : chaque requête contient son JWT ──
            .sessionManagement(s ->
                s.sessionCreationPolicy(STATELESS))

            // ── Règles d'accès par URL ──
            .authorizeHttpRequests(auth -> auth
                // Health checks accessibles sans authentification (pour Kubernetes)
                .requestMatchers("/actuator/health/**").permitAll()
                // Consulter les livres : USER ou LIBRARIAN
                .requestMatchers(GET,  "/api/books/**").hasAnyRole("USER", "LIBRARIAN")
                // Créer un emprunt : LIBRARIAN uniquement
                .requestMatchers(POST, "/api/loans/**").hasRole("LIBRARIAN")
                // Tout le reste : authentification requise
                .anyRequest().authenticated()
            )

            // ── Configurer la validation du JWT ──
            .oauth2ResourceServer(oauth ->
                oauth.jwt(jwt -> jwt.jwtAuthenticationConverter(
                    jwtAuthenticationConverter()))  // Convertir les claims en rôles Spring
            )
            .build();
    }

    // ── Convertisseur : extraire les rôles du JWT ──
    // Keycloak stocke les rôles dans un claim "roles" (pas "authorities")
    // Il faut mapper : claim "roles" → authorities Spring "ROLE_xxx"
    @Bean
    JwtAuthenticationConverter jwtAuthenticationConverter() {
        JwtGrantedAuthoritiesConverter conv = new JwtGrantedAuthoritiesConverter();
        conv.setAuthoritiesClaimName("roles");   // Nom du claim dans le JWT
        conv.setAuthorityPrefix("ROLE_");         // Préfixe Spring Security
        JwtAuthenticationConverter jwtConv = new JwtAuthenticationConverter();
        jwtConv.setJwtGrantedAuthoritiesConverter(conv);
        return jwtConv;
    }
}
// ═══════════════════════════════════════════════════════════════
// RBAC FIN : contrôle d'accès au niveau de chaque méthode
// ═══════════════════════════════════════════════════════════════
@RestController
@RequestMapping("/api/loans")
public class LoanController {

    // L'étudiant ne voit QUE ses propres emprunts (sauf si LIBRARIAN)
    // authentication.name = le "sub" du JWT (identifiant unique de l'utilisateur)
    @GetMapping("/{loanId}")
    @PreAuthorize("""
        hasRole('LIBRARIAN') or
        @loanService.isOwner(#loanId, authentication.name)
    """)
    public LoanDto getLoan(@PathVariable UUID loanId) {
        return loanService.findById(loanId);
    }

    // Seul un bibliothécaire peut créer un emprunt
    @PostMapping
    @PreAuthorize("hasRole('LIBRARIAN')")
    public ResponseEntity<LoanDto> createLoan(
            @RequestBody @Valid CreateLoanRequest req) {
        return ResponseEntity.status(201).body(loanService.createLoan(req));
    }
}

4.3 mTLS — Authentification mutuelle inter-services

🔴 Expert

Mode pro — JWT vs mTLS

  • JWT : identité de l'utilisateur, propagée dans le header Authorization. Validé au niveau applicatif.
  • mTLS : identité du service, négociée au niveau TLS. Validé par le service mesh (Istio, Linkerd), transparent pour l'application.
  • En production on combine les deux : mTLS pour le service-to-service + JWT pour le contexte utilisateur.

❌ Erreur fréquente — Valider le JWT soi-même

Ne jamais implémenter la validation JWT manuellement. Erreurs classiques : oublier de vérifier la signature, ne pas vérifier exp, accepter l'algorithme none. Utiliser une bibliothèque maintenue : spring-security-oauth2-resource-server ou nimbus-jose-jwt.

5. Zero Trust & gestion des secrets

JuniorMidExpert

Zero Trust — "Never trust, always verify"

Aucun segment réseau n'est implicitement fiable, même interne. Chaque accès sensible est vérifié : identité, contexte, droits minimaux. Un attaquant ayant pénétré le périmètre ne peut pas se déplacer librement.

🧸 Analogie — L'aéroport

Même après avoir passé le contrôle de sécurité, tu dois montrer ta carte d'embarquement à chaque porte. Zero Trust c'est pareil : même si un service est "à l'intérieur du réseau", il doit prouver son identité à chaque appel.

5.1 Les 3 règles fondamentales des secrets

❌ Ne jamais faire — secret dans Git

# VAULT : coffre-fort centralisé pour les secrets
# ═══════════════════════════════════════
# Au démarrage, Spring contacte Vault pour récupérer les secrets.

5.3 Dynamic Secrets — Credentials DB éphémères

Vault génère des credentials PostgreSQL à la demande avec une TTL courte (ex. 1h). L'application ne connaît jamais le mot de passe permanent. En cas de compromission, le credential expire automatiquement — pas besoin de rotation manuelle.

# ═══════════════════════════════════════
# DYNAMIC SECRETS : mots de passe temporaires générés par Vault
# ═══════════════════════════════════════
# Au lieu d'un mot de passe permanent (risque si compromis),
# Vault génère un user/password PostgreSQL unique et temporaire.
# Durée de vie typique : 1h. Rotation automatique par Spring Cloud Vault.
spring:
  cloud:
    vault:
      database:
        enabled: true
        role: loan-service-role     # Rôle Vault qui définit les permissions SQL
        backend: database           # Mount path du moteur "database" dans Vault
        # Vault renouvelle automatiquement le lease avant expiration
        # → l'application n'a rien à faire, c'est transparent

  • Aucun secret dans Git (même un commit "révoqué" reste dans l'historique)
  • Rotation des clés JWT tous les 90 jours minimum
  • Moindre privilège : chaque service accède uniquement à ses secrets
  • Audit des accès aux secrets (Vault fournit un audit log)
  • mTLS en production via service mesh (Istio / Linkerd)

Quiz de fin — Jour 5

1. Pourquoi un retry sans timeout peut-il être dangereux ?

Voir la réponse

Un service lent bloque les threads de l'appelant indéfiniment. Les retries s'accumulent sur ces threads déjà bloqués, épuisant le pool et rendant l'appelant lui-même indisponible — c'est la cascade failure. Toujours combiner Retry + TimeLimiter.

2. Quelle différence entre logs, métriques et traces ?

Voir la réponse

Logs : événements discrets textuels (ce qui s'est passé). Métriques : valeurs numériques agrégées dans le temps (combien, quelle durée). Traces : parcours d'une requête à travers les services (où et combien de temps dans chaque hop). Les trois sont complémentaires : métriques → alerte, logs → contexte, traces → localisation du goulot.

3. Quelle différence entre liveness et readiness probe ?

Voir la réponse

La liveness probe détecte un état irrécupérable (deadlock) → Kubernetes redémarre le pod. La readiness probe détecte une indisponibilité temporaire (DB coupée, warm-up) → Kubernetes retire le pod du load balancer sans le redémarrer. Confondre les deux = redémarrages inutiles ou trafic envoyé à un pod non prêt.

4. Pourquoi le réseau interne n'est pas sûr par défaut ? (Zero Trust)

Voir la réponse

Un attaquant ayant pénétré le périmètre (pod compromis, employé malveillant) peut accéder librement à toutes les ressources internes si on leur fait confiance implicitement. Zero Trust impose de vérifier identité et droits à chaque communication, même interne.

5. (Expert) Pourquoi ne pas mettre le Retry à l'intérieur du Circuit Breaker ?

Voir la réponse

Si Retry est à l'intérieur du Circuit Breaker, chaque tentative de retry est comptée comme un appel dans la fenêtre glissante du CB. 3 retries sur 1 appel = 3 échecs dans la fenêtre, ce qui ouvre le circuit trop tôt. Le bon ordre : Retry enveloppe CircuitBreaker — les retries ne sont tentés que si le circuit est encore CLOSED.

6. (Expert) Quelle propriété garantit qu'un JWT n'a pas été modifié en transit ?

Voir la réponse

La signature cryptographique (RS256 ou HS256). Elle est calculée sur base64(header).base64(payload) avec la clé privée de l'IdP. Le Resource Server la vérifie avec la clé publique. Toute modification du payload invalide la signature. En revanche, la signature ne chiffre pas : le payload reste lisible par tous.
