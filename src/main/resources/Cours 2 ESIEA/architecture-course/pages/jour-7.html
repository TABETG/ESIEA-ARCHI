Architecture événementielle

1. Event-Driven Architecture — Une décision de couplage

MidSenior

🧸 Analogie — Le tableau d'affichage de la bibliothèque

Dans une bibliothèque physique, quand un livre est retourné, la bibliothécaire ne court pas prévenir chaque étudiant intéressé un par un (appel synchrone). Elle affiche un avis sur le tableau d'affichage (événement). Chacun consulte le tableau à son rythme (découplage temporel). Personne n'attend personne.

📖 Définition — Event-Driven Architecture

Style architectural dans lequel les composants communiquent via des événements plutôt que des appels directs. Un producteur émet un fait passé ("loan-created"), sans savoir qui l'écoutera ni combien de consommateurs réagiront. Le couplage est réduit au minimum : le producteur ne connaît que le canal, pas les abonnés.

🎯 Quand utiliser EDA en vrai ?

  • Notifications & intégrations : envoyer un email, un SMS, un webhook après une action → le client n'a pas besoin d'attendre.
  • Pipelines de données : indexer dans Elasticsearch, mettre à jour un dashboard analytics, alimenter un data warehouse.
  • Workflows multi-services : un prêt déclenche stock, notification, statistiques, audit — chacun avance à son rythme.
  • Domaines à fort taux d'évolution : ajouter un nouveau consommateur (ex: nouveau service de recommandation) sans toucher au producteur.

🏢 Exemples d'entreprises qui utilisent massivement EDA

  • Uber : chaque course émet des dizaines d'événements (course créée, chauffeur attribué, position mise à jour, course terminée, paiement effectué). Le pricing, le routing, les statistiques et le support en consomment chacun ce qui les intéresse.
  • Netflix : chaque "play", "pause", "seek" devient un événement, alimentant la recommandation, le billing, la détection d'incidents et le contrôle qualité — sans coupler les services entre eux.
  • LinkedIn : Kafka a été créé chez eux pour gérer leurs événements (profile updated, connection accepted, message sent) à grande échelle.

1.2 Taxonomie des événements — 3 types fondamentaux

📢 Event Notification

  • Annonce qu'un fait s'est passé
  • Payload minimal (juste l'ID)
  • Le consommateur va chercher les détails si besoin
  • Ex : {"type":"loan-created","loanId":"abc-123"}

✅ Léger ❌ Chattiness si beaucoup de consommateurs

📦 Event-Carried State Transfer

  • L'événement contient tout l'état nécessaire
  • Consommateur autonome, pas de rappel
  • Ex : {"type":"loan-created","loanId":"abc","bookTitle":"Clean Code","studentName":"Ahmed",...}

✅ Autonomie ❌ Events volumineux, couplage sur le modèle

📜 Domain Event (DDD)

  • Fait métier significatif, immutable
  • Nommé au passé : "LoanCreated", "BookReturned"
  • Versioned (v1, v2)
  • Ex : fait partie du ubiquitous language

✅ Expressivité métier ❌ Discipline DDD requise

🏛️ Règle d'or — Nommer les événements

Un événement est un fait passé et immutable. Il se nomme toujours au passé composé et en langage métier, jamais technique : "LoanCreated" (pas "SaveLoanEvent"), "BookReturned" (pas "UpdateBookStatusEvent"). Si vous hésitez sur le nom, c'est que la frontière de votre bounded context n'est pas claire.

Patterns EDA

2. Patterns EDA — Trois approches architecturales

MidSenior

Référence : Martin Fowler — "What do you mean by 'Event-Driven'?" (2017). Ces trois patterns se combinent mais répondent à des problèmes différents.

2.1 Event Notification — Le signal minimal

📖 Principe

Le producteur envoie un signal léger : "quelque chose s'est passé". Les consommateurs qui veulent les détails rappellent le producteur pour les obtenir. Faible couplage de données, mais génère des appels retour.

⚠️ Quand éviter

Si chaque consommateur rappelle systématiquement le producteur après chaque événement, on reconstitue du couplage synchrone caché. Le bénéfice de l'asynchronisme disparaît.

2.2 Event-Carried State Transfer — L'autonomie maximale

📖 Principe

L'événement contient tout ce dont les consommateurs ont besoin. Chaque service maintient sa propre copie locale des données qui lui sont pertinentes (réplication partielle). Pas de rappel nécessaire → résistance aux pannes des dépendances.

📐 ECST — Réplication locale dans campus_library

catalog-service

Émet BookUpdated event avec le titre complet, l'auteur, le stock. Chaque consommateur reçoit ce qu'il lui faut.

Stocke localement : titre + auteur + mots-clés (pour full-text search autonome)

analytics-service

Stocke localement : catégorie + éditeur (pour statistiques)

2.3 Event Streaming — Le log distribué

🏛️ Principe architectural — Event Stream comme source de vérité

Le stream d'événements est la vérité du système. Les données en base de données ne sont que des projections du stream. Un nouveau consommateur peut rejouer l'historique entier pour construire sa propre vue. C'est le principe fondateur de Kafka et d'Event Sourcing.

Chaque pattern résout un problème différent. Notification = simplicité. ECST = autonomie. Streaming = mémoire et rejeu.

🎯 Choix pratique : quel pattern pour quel besoin ?

  • Event Notification : "déclenche quelque chose, je m'en fiche du détail" → ex: un cron qui réveille un job.
  • Event-Carried State : "je veux fonctionner même si l'autre service tombe" → ex: notification-service garde sa propre vue des prêts.
  • Event Streaming : "je veux pouvoir reconstruire mes données après un bug, ou intégrer un nouveau service rétroactivement" → ex: nouveau dashboard analytics qui replay 6 mois.

✅ Règle de sélection des patterns EDA

Commencer par Event Notification (simple). Passer à ECST quand les consommateurs rappellent trop souvent. Adopter Event Streaming seulement quand l'historique, le rejeu ou la traçabilité complète sont des besoins métier explicites — le coût opérationnel (Kafka) est significatif.

CQRS

3. CQRS — Command Query Responsibility Segregation

MidSenior

🧸 Analogie — La bibliothécaire et le catalogue

Dans une bibliothèque, la bibliothécaire qui enregistre un retour de livre travaille différemment de l'étudiant qui cherche dans le catalogue. L'une modifie une base (write), l'autre consulte un index optimisé pour la recherche (read). CQRS formalise cette séparation : deux modèles distincts, deux chemins distincts.

📖 Définition — CQRS (Greg Young, 2010)

Séparation stricte entre les Commands (opérations qui changent l'état — write) et les Queries (opérations qui lisent l'état — read). Chaque chemin peut avoir son propre modèle de données, son propre store, sa propre scalabilité.

⚠️ CQRS n'est pas toujours la bonne réponse

CQRS introduit de la cohérence éventuelle : entre la commande et la projection mise à jour, il y a un délai. Si l'utilisateur lit immédiatement après avoir écrit, il peut voir un état périmé. Ne pas appliquer CQRS par défaut — seulement quand la scalabilité asymétrique ou l'auditabilité le justifient explicitement.

🎯 Quand CQRS est-il vraiment justifié ?

  • Lectures >> écritures (10:1, 100:1) : un site e-commerce a 1000× plus de visites de fiches produit que de modifications du catalogue.
  • Modèles d'affichage très différents du modèle métier : un dashboard agrège plusieurs aggregates DDD ; sans CQRS, vous faites des jointures complexes à chaque query.
  • Besoin de scalabilité indépendante : votre moteur de recherche (Elasticsearch) doit scaler ×10 sans toucher à la DB transactionnelle.
  • Sources de vérité multiples : la même donnée projetée dans Postgres (transac), Elasticsearch (search), Redis (cache) et S3 (export).

🏢 Exemples concrets de CQRS en production

  • Amazon : la fiche produit que vous voyez n'est PAS lue depuis le catalogue principal. Elle est projetée dans une vue dénormalisée (titre, prix, photos, stock, avis agrégés, recommandations) optimisée pour le rendu.
  • StackOverflow : quand vous postez une réponse (command), votre profil, le tag, la home page et la liste des "active questions" sont mis à jour via projections — vous voyez parfois quelques secondes de décalage.
  • Twitter/X : poster un tweet = command. Votre timeline = projection précalculée et fan-outée vers tous vos abonnés. Sans CQRS, lire votre timeline coûterait une jointure géante à chaque visite.
Event Sourcing

4. Event Sourcing — Le journal comme source de vérité

Senior

🧸 Analogie — Le livre de comptes d'une banque

Une banque ne stocke pas "solde = 1247€". Elle stocke tous les mouvements : "+500€ virement", "-50€ retrait", "+800€ salaire"... Le solde est calculé à partir de l'historique complet. Revenir en arrière, auditer chaque centime, reconstituer l'état à n'importe quel instant : c'est Event Sourcing.

4.1 Principes fondamentaux

🏗️ Principe ES : Ne jamais mettre à jour l'état — toujours ajouter un événement.
L'état courant = rejeu de tous les événements depuis le début (ou depuis le dernier snapshot).

📐 Event Store — Prêt Ahmed / "Clean Code"

# Event Store — loan aggregate "loan-abc-123"
seq:1 LoanCreated {studentId:"ahmed", bookId:"clean-code", date:"2024-09-15"}
seq:2 LoanExtended {newDueDate:"2024-10-15", reason:"exam session"}
seq:3 LoanOverdue {daysLate:3, penaltyAmount:1.5}
seq:4 LoanReturned {returnDate:"2024-10-18", penaltyPaid:true}

# Pour connaître l'état actuel :
Rejouer seq 1→4 → état final : Loan{status:RETURNED, penaltyPaid:true}

# Pour connaître l'état au 16 octobre :
Rejouer seq 1→3 → état partiel : Loan{status:OVERDUE, daysLate:3}

4.2 Trade-offs architecturaux — ES n'est pas gratuit

✅ Avantages

  • Audit complet : chaque changement d'état est tracé
  • Time-travel debugging : état à tout instant
  • Replay : reconstruire une projection après un bug
  • Découplage temporel : ajouter un consommateur rétroactivement
  • Intégration naturelle avec CQRS et DDD

⚠️ Complexité architecturale

  • Snapshots obligatoires : sans eux, rejouer 10M d'events est lent
  • Schéma évolution : comment gérer les événements de la v1 avec du code v3 ?
  • Suppression RGPD : "effacer" une donnée dans un log immutable
  • Cohérence éventuelle : projections pas toujours à jour
  • Courbe d'apprentissage : paradigme très différent du CRUD

⚠️ RGPD et Event Sourcing — le problème de l'immuabilité

Si un utilisateur demande la suppression de ses données (droit à l'oubli), comment effacer des événements dans un log immuable ? Solutions architecturales : Crypto shredding (chiffrer les données personnelles avec une clé détruite lors de la suppression) ou référencer un store externe pour les PII (l'événement stocke un ID, pas la donnée).

🎯 Quand Event Sourcing est-il indispensable ?

  • Audit réglementaire : banque, assurance, santé — la loi exige la traçabilité complète et immutable de chaque opération.
  • Time-travel debugging : "comment était cet utilisateur le 14 mars à 18h ?" — impossible avec un CRUD classique, trivial avec ES.
  • Reconstruction de projections : un bug a corrompu votre dashboard analytics ? Vous rebuildez à partir des events, sans perte.
  • Intégration rétroactive : un nouveau service arrive et veut connaître toute l'histoire passée → il consomme les events depuis le début.

🏢 Domaines où Event Sourcing est massivement utilisé

  • Finance & banking : un solde de compte n'est JAMAIS stocké tel quel. Il est dérivé de la liste des transactions. C'est Event Sourcing depuis 500 ans (livres de comptes).
  • Versioning de code (Git) : Git EST un event store. Chaque commit est un événement immutable. git log = lire les events. git checkout abc123 = reconstruire l'état à un instant T.
  • Blockchain : pure Event Sourcing à l'échelle planétaire — chaque transaction est un event, l'état des wallets est calculé.
  • Walmart, Tesla : suivi des stocks et de la maintenance véhicules — chaque modification est un fait historique.
Systèmes réactifs

5. Reactive Systems — Architecture de la fluidité

Senior

🧸 Analogie — L'eau vs les billes

Des billes dans un tuyau : si le tuyau se bouche, les billes s'entassent et tout s'arrête. De l'eau : elle s'adapte à la pression, accélère dans les goulets, ralentit quand le débit diminue. Un Reactive System se comporte comme l'eau : il s'adapte à la charge plutôt que de bloquer.

5.1 Le Reactive Manifesto — 4 propriétés

⚡ Responsive (Réactif)

  • Répond toujours dans un délai borné
  • Pas de timeout infini, pas de blocage
  • Latence prévisible même en charge

🛡️ Resilient (Résilient)

  • Continue à fonctionner en cas de panne partielle
  • Réplication, containment, isolation
  • Récupération déléguée à un superviseur

📊 Elastic (Élastique)

  • Scale up/down selon la charge
  • Pas de goulot d'étranglement en contention
  • Algorithmes adaptatifs (sharding, load balancing)

💬 Message-Driven

  • Asynchrone + non-bloquant
  • Backpressure explicite
  • Isolation par échanges de messages

5.2 Backpressure — Le mécanisme central

📖 Définition — Backpressure

Mécanisme par lequel un consommateur signale au producteur de ralentir parce qu'il n'arrive plus à traiter les messages à la vitesse de production. Sans backpressure, les messages s'accumulent en mémoire jusqu'à OOM (Out of Memory). Avec backpressure, le producteur s'adapte.

❌ Sans backpressure
Producer: 10 000 events/sec
Consumer: 1 000 events/sec
Buffer : s'accumule → OOM en 10min
Résultat : crash du service
✅ Avec backpressure
Consumer signale : "je peux traiter
  1 000/sec max"
Producer s'adapte → 1 000/sec
Ou drop + alerte, ou buffer borné

"prêt pour 500 de plus" Note over P,C: 🚨 Si le consumer ralentit (DB lente, GC, etc.) C->>C: traitement long (3s) Note over P: Producer ATTEND la demande
aucun message poussé Note over B: Buffer reste vide ou stable
0 OOM, 0 perte C->>P: request(100)
"je suis en surcharge, juste 100" P->>B: pousse 100 B->>C: livre 100 Note over P,C: ⚖️ Le système s'auto-régule
sans crash, sans perte

Le consumer "tire" la quantité qu'il peut traiter. Le producer s'adapte. Sans backpressure, le buffer grossit jusqu'au crash mémoire.

🎯 Où voit-on Reactive Systems en pratique ?

  • Streaming vidéo (Netflix, YouTube) : votre lecteur ne télécharge que ce qu'il peut afficher (pull). Sinon, votre RAM exploserait sur un film 4K.
  • API gateways en pic de charge : Spring WebFlux, Node.js — gérer 100k connexions concurrentes sans 100k threads.
  • Pipelines IoT : un capteur émet 10k mesures/s, mais le serveur d'analyse traite 1k/s — sans backpressure, le serveur tombe en quelques minutes.
  • Trading algorithmique : flux de cotations à très haut débit, où perdre des messages n'est pas une option.

6. Service Mesh — Externaliser les préoccupations transverses

Senior

🧸 Analogie — Le réseau électrique vs l'électronique embarquée

Avant le réseau électrique public, chaque usine gérait sa propre génération d'électricité. Chaque maison avait son générateur. Aujourd'hui, l'électricité est une infrastructure partagée. Un Service Mesh fait pareil avec le réseau entre services : TLS mutuel, retry, circuit breaker, métriques — externalisés dans l'infrastructure, retirés du code applicatif.

📖 Définition — Service Mesh

Couche d'infrastructure dédiée à la communication inter-services. Implémentée via des sidecars proxies (ex: Envoy) injectés automatiquement dans chaque pod. Ces proxies interceptent tout le trafic réseau et appliquent les politiques transverses sans modifier le code applicatif.

🎯 Quand Service Mesh devient nécessaire (et quand pas) ?

  • ✅ Justifié : 10+ services, ops K8s mature, mTLS imposé par réglementation (PCI-DSS, HIPAA), besoin de canary/A-B sans toucher au code.

🏢 Qui utilise un Service Mesh en production ?

  • Google : a inventé le pattern (BNS interne, puis Istio). Des dizaines de milliers de services derrière un mesh.
  • Airbnb : SmartStack puis Envoy/Istio pour gérer la communication entre 1000+ services.
  • Lyft : a créé Envoy pour son propre usage avant de l'open-sourcer (cœur de la plupart des meshes aujourd'hui).
  • Banques européennes : adoption massive d'Istio pour le mTLS systématique exigé par les régulateurs.

7. Chaos Engineering — Tester l'architecture par la destruction

Senior

📖 Définition — Chaos Engineering (Netflix, 2011)

"La discipline de mener des expériences contrôlées sur un système distribué pour construire la confiance dans la capacité du système à résister à des conditions turbulentes en production." — Principles of Chaos Engineering

🏗️ Principe : Provoquer des pannes délibérément, dans un environnement contrôlé, avant que la production ne le fasse à votre place.

7.1 Processus Chaos Engineering

① Définir l'état stable

SLI mesurable : 99.5% requêtes OK, latence P99 < 400ms

② Formuler l'hypothèse

"Si catalog-service tombe, loan-service retourne un fallback en < 2s"

③ Injecter la panne

Tuer le pod catalog, augmenter la latence, saturer la DB

④ Observer

L'état stable est-il maintenu ? Qu'est-ce qui se comporte mal ?

⑤ Corriger

Améliorer l'architecture. Rédiger l'ADR de la décision.

Type d'injectionDescriptionCe que ça teste
Pod killTuer aléatoirement un pod en productionHealth checks, auto-restart, retry clients
Network latencyAjouter 2s de latence sur un serviceTimeouts, circuit breakers
CPU pressureConsommer 90% du CPU d'un nœudAutoscaling, priorité des workloads
Memory leakSimuler une fuite mémoire progressiveOOM killer, graceful restart, alerting
DNS failureBloquer la résolution DNS d'un serviceFallback, cache DNS, service discovery
DB connection poolSaturer les connexions disponiblesPool management, bulkhead, timeouts

✅ Règles d'or du Chaos Engineering

  1. Commencer en staging — jamais en production avant d'avoir la confiance
  2. Avoir un kill switch — pouvoir arrêter l'expérience immédiatement
  3. Informer l'équipe — les expériences ne sont pas des surprises
  4. Minimiser le blast radius — cibler un service à la fois
  5. Documenter les résultats — chaque expérience produit un ADR si elle révèle une faiblesse

8. Quiz de fin de journée

1. Quelle est la différence architecturale entre les trois patterns EDA (Event Notification, ECST, Event Streaming) ? Donnez un exemple de chacun dans campus_library.

Voir la réponse

Event Notification : payload minimal — {"loanId":"abc"}. catalog-service reçoit l'event et rappelle loan-service pour avoir les détails si besoin. Léger, mais chattiness possible.
ECST : {"loanId":"abc","bookTitle":"Clean Code","student":"Ahmed","dueDate":"..."}. notification-service n'a besoin de rien d'autre pour envoyer l'email — autonomie totale.
Event Streaming : Kafka avec rétention 30 jours. analytics-service peut rejouer tous les events depuis 6 mois pour reconstruire ses statistiques après un bug.

2. Pourquoi CQRS introduit-il de la cohérence éventuelle ? Quels problèmes concrets cela cause-t-il pour l'UX ?

Voir la réponse

En CQRS avec stores séparés, après une command, un événement est publié et un projection builder met à jour le Read Store — avec un délai (quelques millisecondes à quelques secondes). Si l'utilisateur relit immédiatement après sa commande, il peut voir l'ancien état.
Exemple : Ahmed crée un prêt (command), la page se recharge (query), mais le prêt n'apparaît pas encore dans sa liste — le projection builder n'a pas encore mis à jour. Solution UX : "read-your-writes" pattern (lire depuis le write store immédiatement après une commande), ou afficher un indicateur "traitement en cours".

3. Comment résoudre le problème RGPD du "droit à l'oubli" dans un système Event Sourcing ?

Voir la réponse

L'Event Store étant immuable (on n'efface pas les événements), deux approches architecturales :
Crypto Shredding : chiffrer toutes les données personnelles dans les événements avec une clé dédiée par utilisateur. Pour effacer un utilisateur, supprimer sa clé → les données deviennent illisibles (équivalent fonctionnel de la suppression).
Référence externe : les événements ne stockent pas les PII directement mais un identifiant pointant vers un store externe (ex: PostgreSQL). La suppression RGPD cible le store externe. L'Event Store ne contient plus que des IDs, qui deviennent des références mortes.

4. Qu'est-ce que le backpressure et pourquoi est-il essentiel dans un Reactive System ?

Voir la réponse

Le backpressure est le mécanisme par lequel un consommateur signale au producteur qu'il est dépassé et doit ralentir. Sans backpressure, le producteur génère plus vite que le consommateur ne traite → buffer croissant → OutOfMemoryError → crash.
Il est essentiel dans un Reactive System car l'élasticité (propriété 3 du Reactive Manifesto) ne peut fonctionner que si chaque maillon de la chaîne peut communiquer sa capacité réelle. Sans backpressure, l'élasticité devient de la sous-charge silencieuse jusqu'au crash brutal.

5. Dans quelles conditions un Service Mesh (Istio) est-il architecturalement justifié ? Quand est-il de l'over-engineering ?

Voir la réponse

Justifié : 10+ services, équipe ops Kubernetes mature, besoin de mTLS systématique (réglementation PCI-DSS, HIPAA), politique de trafic uniforme (canary, shadowing) sans modifier le code, métriques réseau automatiques entre toutes les paires de services.
Over-engineering : équipe de 3-5 développeurs, moins de 6 services, pas de Kubernetes, ou équipe sans expertise ops avancée. Dans ce cas, Resilience4j dans le code + Prometheus/Grafana donnent 80% des bénéfices pour 20% de la complexité.
