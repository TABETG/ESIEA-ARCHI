Un conteneur Docker c'est comme un conteneur maritime standardisé : peu importe ce qu'il y a dedans (Java, Python, Node), il s'emboîte partout de la même façon — sur ton laptop, le serveur du client, le cloud. Plus de "ça marche chez moi mais pas en prod".

1.1 Dockerfile basique vs optimisé

❌ Dockerfile naïf — image inutilement lourde 
# ⚠️ PROBLÈMES :
# 1. Utilise le JDK complet (outils de dev) en PRODUCTION → +300Mo inutiles
# 2. Copie TOUT le projet (y compris .git, tests, docs) → cache invalidé à chaque modif
# 3. Build + runtime dans la même image → surface d'attaque CVE élargie
# 4. Tourne en root par défaut → risque de sécurité
FROM eclipse-temurin:21
COPY . /app
WORKDIR /app
RUN ./mvnw package
CMD ["java", "-jar", "target/catalog-service.jar"]
✅ Dockerfile optimisé — multi-stage build 
# ═══════════════════════════════════════
# STAGE 1 : BUILD — compile le projet (temporaire, pas dans l'image finale)
# ═══════════════════════════════════════
FROM eclipse-temurin:21-jdk AS build
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -q   # Télécharger les dépendances d'abord (cache Docker)
                                    # → si seul le code change, cette couche est cachée
COPY src ./src
RUN mvn package -DskipTests -q     # Compiler le .jar (tests déjà passés dans la CI)

# ═══════════════════════════════════════
# STAGE 2 : RUNTIME — image finale légère (JRE seul, pas de JDK)
# ═══════════════════════════════════════
# L'image finale ne contient QUE le JRE + le .jar → 3x plus petite
FROM eclipse-temurin:21-jre AS runtime

# ── Sécurité : créer un utilisateur non-root ──
# Par défaut Docker tourne en root → si un attaquant pénètre le conteneur,
# il a les pleins pouvoirs. Avec un user dédié, les dégâts sont limités.
RUN addgroup --system appgroup \
 && adduser --system --ingroup appgroup appuser

WORKDIR /app
# Copier UNIQUEMENT le .jar depuis le stage de build
COPY --from=build /build/target/catalog-service.jar app.jar
USER appuser          # Basculer sur l'utilisateur non-root
EXPOSE 8080           # Documenter le port (n'ouvre rien, c'est informatif)

ENTRYPOINT ["java", \
  "-XX:MaxRAMPercentage=75.0", \              # Utiliser max 75% de la RAM du conteneur
  "-Djava.security.egd=file:/dev/./urandom", \ # Éviter le blocage /dev/random dans Docker
  "-jar", "app.jar"]

✅ Checklist Dockerfile production

  • .dockerignore : exclure target/, .git/, *.md
  • Utilisateur non-root (USER appuser)
  • Image de base minimale (JRE != JDK)
  • Jamais de secrets dans le Dockerfile
  • Scan CVE : trivy image catalog-service:latest

2. Kubernetes — Orchestration avancée

MidExpert

🧸 Analogie — Le chef d'orchestre

Kubernetes c'est le chef d'orchestre de tes conteneurs. Tu lui dis "je veux 3 copies de ce service" et il s'en assure en permanence, même si l'un plante — il le remplace automatiquement en quelques secondes. Tu ne gères plus les serveurs, tu déclares l'état souhaité.

2.1 Deployment complet avec sondes et ressources

# ═══════════════════════════════════════════════════════════════
# DEPLOYMENT KUBERNETES — catalog-service en production
# ═══════════════════════════════════════════════════════════════
apiVersion: apps/v1
kind: Deployment
metadata:
  name: catalog-service
  namespace: library            # Isoler par namespace (library = notre projet)
spec:
  replicas: 3                   # 3 instances pour la haute disponibilité
  selector:
    matchLabels:
      app: catalog-service      # K8s utilise ce label pour identifier les pods

  # ── Stratégie de déploiement : Rolling Update ──
  # Remplace les pods un par un, sans downtime
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1  # Au max 1 pod arrêté pendant le déploiement
      maxSurge: 1        # Au max 1 pod supplémentaire (temporaire) pendant la transition

  template:
    metadata:
      labels:
        app: catalog-service
    spec:
      containers:
        - name: catalog-service
          image: registry.example.com/catalog-service:1.2.0  # Image Docker versionnée
          ports:
            - containerPort: 8080

          # ── Ressources : combien de CPU/mémoire pour ce conteneur ──
          resources:
            requests:              # Minimum garanti (K8s réserve ces ressources)
              cpu: "250m"          # 250 millicores = 25% d'un CPU
              memory: "256Mi"      # 256 Mo de RAM minimum
            limits:                # Maximum autorisé (le conteneur est tué si dépassé)
              cpu: "1000m"         # 1 CPU max
              memory: "512Mi"      # 512 Mo max — OOMKill si dépassé

          # ── Secrets : injectés depuis un K8s Secret (pas en clair dans le YAML) ──
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: prod
            - name: DATABASE_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: catalog-db-secret  # Référence au Secret K8s
                  key: password            # Clé dans le Secret

          # ── Sonde STARTUP : attend que le service ait fini de démarrer ──
          # Spring Boot peut mettre 15-30s pour démarrer (JVM warmup, Flyway, etc.)
          # Sans cette sonde, K8s pourrait tuer le pod avant qu'il ait démarré !
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            failureThreshold: 30    # Essayer 30 fois × 10s = 5 minutes max pour démarrer
            periodSeconds: 10

          # ── Sonde LIVENESS : le process est-il vivant ? ──
          # Si KO → K8s REDÉMARRE le pod (deadlock, corruption mémoire)
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            periodSeconds: 20       # Vérifier toutes les 20s
            failureThreshold: 3     # 3 échecs consécutifs → restart

          # ── Sonde READINESS : le pod peut-il recevoir du trafic ? ──
          # Si KO → K8s RETIRE le pod du load balancer (DB coupée, warmup)
          # mais ne le redémarre PAS (contrairement à liveness)
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 10
            failureThreshold: 3

2.2 HPA — Horizontal Pod Autoscaler

# ═══════════════════════════════════════════════════════════════
# HPA : scale automatiquement le nombre de pods selon la charge
# ═══════════════════════════════════════════════════════════════
# Kubernetes surveille les métriques et ajuste le nombre de réplicas.
# Plus de trafic → plus de pods. Moins de trafic → moins de pods.
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: catalog-hpa
  namespace: library
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: catalog-service       # Le Deployment à scaler
  minReplicas: 2                # Jamais moins de 2 pods (haute dispo)
  maxReplicas: 10               # Jamais plus de 10 pods (contrôler les coûts)
  metrics:
    # ── Scale sur le CPU ──
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70  # Si CPU moyen > 70% → ajouter un pod
    # ── Scale sur une métrique custom (Prometheus) ──
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second  # Métrique custom exposée par Micrometer
        target:
          type: AverageValue
          averageValue: "100"   # Si > 100 req/s par pod → scale up

⚠️ Kubernetes Secrets != sécurisés par défaut

Les Secrets sont encodés en base64 dans etcd — pas chiffrés. En production : activer le chiffrement etcd ou utiliser HashiCorp Vault Injector / Sealed Secrets.

🖥️ Live Coding — Rolling update sans downtime

  1. Déployer catalog-service:1.0.0 avec 3 réplicas
  2. Dans un terminal : watch -n1 curl http://catalog/actuator/health
  3. Mettre à jour l'image : kubectl set image deployment/catalog-service catalog-service=registry/catalog-service:1.1.0
  4. Observer : kubectl rollout status deployment/catalog-service
  5. Rollback : kubectl rollout undo deployment/catalog-service

3. Stratégies de déploiement, CI/CD et IaC

MidExpert

La question n'est pas "comment déployer" mais "comment déployer sans risque". Chaque stratégie offre un compromis entre vitesse, sécurité et coût.

PratiqueButAvantageCoût / Risque
RollingRemplacement progressif des podsPas de downtime, simple2 versions en parallèle brièvement
Blue-GreenBascule nette entre 2 environnementsRollback instantanéDouble coût infra
CanaryExposition progressive (5% → 100%)Limite le blast radiusComplexité routing + observabilité
Feature FlagsDécoupler déploiement et activationRollback sans re-déploiementComplexité du code

Blue-Green vs Canary — visuellement

Blue-Green : bascule 100% du trafic d'un coup
Blue v1.0 — production actuelle
3 pods 100% trafic
Green v1.1 — nouvelle version testée
3 pods 0% → 100% en 1 clic
Rollback instantané : rebasculer sur Blue. Coût : double infra.
Canary : exposition progressive, blast radius maîtrisé
Stable v1.0 — 90% du trafic
3 pods production
Canary v1.1 — 10% du trafic
1 pod surveiller métriques
Si les métriques sont bonnes : 10% → 50% → 100%. Si problème : rollback immédiat, seuls 10% des users ont été impactés.

3.1 Pipeline CI/CD avec GitHub Actions

# ═══════════════════════════════════════════════════════════════
# PIPELINE CI/CD : du git push au déploiement en production
# ═══════════════════════════════════════════════════════════════
# Flux : Code → Build → Tests → Analyse qualité → Image Docker → Scan CVE → Staging → Production
name: CI/CD — catalog-service
on:
  push:
    branches: [main, develop]    # Déclencher sur push vers main ou develop
  pull_request:
    branches: [main]             # Déclencher sur PR vers main

env:
  IMAGE: registry.example.com/catalog-service
  JAVA_VERSION: '21'

jobs:
  # ── JOB 1 : Build + Tests ──
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: ${{ env.JAVA_VERSION }}
          distribution: temurin
          cache: maven              # Cache Maven pour accélérer les builds suivants
      - name: Build and tests
        run: mvn verify -q          # Compile + tests unitaires + tests d'intégration
      - name: SonarQube analysis
        env:
          SONAR_TOKEN: ${{ secrets.SONAR_TOKEN }}   # Secret GitHub, jamais en clair
        run: mvn sonar:sonar        # Analyse qualité du code (bugs, code smells, couverture)

  # ── JOB 2 : Build Docker + Scan sécurité ──
  # Ne s'exécute QUE sur la branche main (pas sur les PRs)
  docker-build:
    needs: build-and-test           # Attend que les tests passent
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'   # Uniquement sur main
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        run: docker build -t $IMAGE:${{ github.sha }} .   # Tag = hash du commit (unique)
      - name: Scan CVE (Trivy)
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: ${{ env.IMAGE }}:${{ github.sha }}
          exit-code: '1'            # ⚠️ FAIL le pipeline si vulnérabilité trouvée
          severity: 'CRITICAL,HIGH' # Bloquer uniquement sur les CVE critiques
      - name: Push
        run: |
          echo "${{ secrets.REGISTRY_TOKEN }}" | docker login -u "${{ secrets.REGISTRY_USER }}" --password-stdin registry.example.com
          docker push $IMAGE:${{ github.sha }}

  # ── JOB 3 : Déployer en staging ──
  deploy-staging:
    needs: docker-build
    environment: staging            # Environnement GitHub (variables + secrets séparés)
    runs-on: ubuntu-latest
    steps:
      - name: Rolling update staging
        run: kubectl set image deployment/catalog-service catalog-service=$IMAGE:${{ github.sha }} --namespace=staging
      - name: Smoke test
        run: |
          sleep 30                  # Attendre le rollout
          curl -f https://catalog.staging.example.com/actuator/health   # Vérifier que ça marche

  # ── JOB 4 : Déployer en production (approbation manuelle) ──
  deploy-production:
    needs: deploy-staging
    environment: production         # ⚠️ Approbation manuelle requise dans GitHub
    runs-on: ubuntu-latest
    steps:
      - name: Deploy canary 10%
        run: kubectl set image deployment/catalog-service-canary catalog-service=$IMAGE:${{ github.sha }} --namespace=production

3.2 Infrastructure as Code avec Terraform

# ═══════════════════════════════════════════════════════════════
# TERRAFORM : décrire l'infrastructure en code (IaC)
# ═══════════════════════════════════════════════════════════════
# Au lieu de cliquer dans la console GCP/AWS pour créer un cluster,
# on le décrit dans un fichier .tf. Avantage : reproductible, versionné,
# auditable, destructible et recréable en 1 commande.

terraform {
  required_providers {
    google = { source = "hashicorp/google", version = "~> 5.0" }
  }
  # ── État Terraform stocké dans le cloud (pas en local !) ──
  # Permet à toute l'équipe de travailler sur la même infra
  backend "gcs" {
    bucket = "tfstate-library-prod"    # Bucket Google Cloud Storage
    prefix = "catalog-service"
  }
}

# ── Cluster Kubernetes (GKE) ──
resource "google_container_cluster" "library_cluster" {
  name                     = "library-cluster"
  location                 = "europe-west1"        # Région EU (latence, RGPD)
  remove_default_node_pool = true                   # On crée un pool custom
  initial_node_count       = 1
}

# ── Pool de nœuds (les VMs qui exécutent les pods) ──
resource "google_container_node_pool" "primary_nodes" {
  name       = "primary-pool"
  cluster    = google_container_cluster.library_cluster.name
  location   = google_container_cluster.library_cluster.location
  node_count = 3                   # 3 nœuds (= 3 VMs)
  node_config {
    machine_type = "e2-standard-2" # 2 vCPU, 8 Go RAM par nœud
    disk_size_gb = 50
    labels       = { env = "prod" } # Tags pour le monitoring des coûts
  }
  management {
    auto_repair  = true  # K8s répare automatiquement les nœuds défaillants
    auto_upgrade = true  # K8s met à jour les nœuds automatiquement
  }
}

✅ Bonnes pratiques IaC

  • État Terraform dans un backend remote (GCS, S3) — jamais localement
  • terraform plan dans la PR, terraform apply sur merge main uniquement
  • Modules réutilisables par équipe (principe DRY)
  • Secrets sensibles dans les variables CI, jamais dans terraform.tfvars versionné
  • Tagger toutes les ressources (coût, équipe, environnement)

4. Gouvernance d'API, versioning et ADR

JuniorMid

🧸 Analogie — Le carnet de bord du navire

Un ADR c'est comme le carnet de bord d'un capitaine : on note pourquoi on a choisi cette route, quelles alternatives existaient, et ce qu'on risque. Quand un nouveau capitaine prend le relais 6 mois plus tard, il peut comprendre les décisions sans refaire les mêmes erreurs.

✅ Checklist gouvernance API

  • Nommage cohérent des endpoints (/api/v1/loans, noms au pluriel)
  • Versioning explicite dans l'URL ou le header Accept
  • Contrats OpenAPI publiés dans un portail développeur
  • Dépréciation annoncée avec délai (ex. 6 mois) via header Deprecation
  • Contract testing (Spring Cloud Contract, Pact)
  • ADR pour chaque décision architecturale importante

4.1 Architecture Decision Record (ADR)

🟢 Junior

Qu'est-ce qu'un ADR ?

Un document court qui capture une décision architecturale importante : le contexte, la décision, les alternatives considérées et les conséquences. C'est la mémoire vivante de l'architecture — indispensable quand une équipe grandit ou se renouvelle.

# ADR-003 — Adoption de Resilience4j
# ════════════════════════════════════
# Un ADR = 1 page max. Structure fixe : contexte → décision → conséquences.
# Numéroté séquentiellement. Jamais supprimé : si la décision change,
# on crée un nouvel ADR qui "supersede" l'ancien.

**Date :** 2025-03-15
**Statut :** Accepté    # Proposé → Accepté → Remplacé par ADR-XXX
**Décideurs :** Alice (tech lead), Bob (architecte), Carol (SRE)

## Contexte
# Quel problème résout-on ? Quelle douleur a motivé cette décision ?
loan-service appelle catalog-service de façon synchrone (HTTP).
Des pannes intermittentes provoquent des timeouts en cascade.

## Décision
# Que fait-on concrètement ?
Adopter Resilience4j pour tous les appels inter-services synchrones.

## Alternatives considérées
# Pourquoi les autres options ont été écartées ?
| Alternative     | Raison d'exclusion                       |
|-----------------|-------------------------------------------|
| Netflix Hystrix | Abandonné depuis 2018                     |
| Custom / manuel | Complexité, réinventer la roue            |

## Conséquences
# Quels impacts positifs ET négatifs ?
[+] Circuit breaker, retry, timeout disponibles avec annotations
[+] Intégration native Spring Boot + Actuator + Micrometer
[-] CompletableFuture requis pour TimeLimiter (changement API)
[-] Courbe d'apprentissage sur l'ordre des décorateurs

4.2 Changements rétro-compatibles vs BREAKING

🟡 Intermédiaire

✅ Rétro-compatibles

  • Ajouter un champ optionnel dans la réponse
  • Ajouter un nouveau endpoint
  • Ajouter un paramètre optionnel
  • Déprécier (mais garder) un champ

❌ BREAKING changes

  • Supprimer ou renommer un champ
  • Changer le type d'un champ
  • Changer la sémantique d'un endpoint
  • Rendre obligatoire un champ optionnel
// ═══════════════════════════════════════════════════════════════
// VERSIONING D'API : maintenir v1 et v2 en parallèle
// ═══════════════════════════════════════════════════════════════
// Règle : ne JAMAIS casser les clients existants.
// Quand on ajoute des champs → v2 avec les nouveaux champs.
// v1 reste disponible pendant 6 mois minimum (période de dépréciation).
@RestController
@RequestMapping("/api")
public class LoanController {

    // v1 — structure originale, maintenue pour les anciens clients
    @GetMapping("/v1/loans/{id}")
    @Deprecated  // Marqué comme déprécié dans la Javadoc et l'OpenAPI
    public LoanDtoV1 getLoanV1(@PathVariable UUID id) {
        return LoanMapper.toV1(loanService.findById(id));
    }

    // v2 — nouvelle structure enrichie (nouveaux champs, HATEOAS)
    @GetMapping("/v2/loans/{id}")
    public LoanDtoV2 getLoanV2(@PathVariable UUID id) {
        return LoanMapper.toV2(loanService.findById(id));
    }
}

// V1 — structure minimale (ne change JAMAIS — contrat gelé)
public record LoanDtoV1(UUID id, String bookTitle, String studentName) {}

// V2 — enrichi avec de nouveaux champs
// Les clients V1 ne sont PAS cassés : ils appellent /v1/ et ignorent V2
public record LoanDtoV2(
    UUID id,
    String bookTitle,
    String studentName,
    LocalDate dueDate,       // ← nouveau champ
    LoanStatus status,       // ← nouveau champ
    List<Link> links         // ← HATEOAS : liens vers les actions possibles
) {}

5. Urbanisation SI et choix d'architecture selon le contexte

MidSeniorExpert

🎓 Mode pro

Un bon architecte ne vend pas une architecture "préférée". Il choisit selon le contexte : taille de l'équipe, criticité, budget, maturité ops, charge, réglementation, dette. Il n'y a rarement qu'une seule bonne réponse.

ContexteChoix souvent pertinentPourquoi
Startup / équipe < 5 devMonolithe modulaireVitesse, simplicité, pas d'overhead ops
Domaine stable, fort volumeMonolithe bien structuréCohérence transactionnelle, coût ops faible
Plusieurs équipes autonomesMicroservices ciblésDécouplage organisationnel (Loi de Conway)
Système très événementielEvent-driven architectureDécouplage temporel, scalabilité async
Legacy à moderniserStrangler Fig PatternMigration progressive, sans big bang risqué

5.1 Loi de Conway

🟡 Intermédiaire
"Any organization that designs a system will produce a design whose structure is a copy of the organization's communication structure." — Melvin Conway, 1967

En pratique : si vous avez 3 équipes (catalog, loan, notification), vous aurez naturellement 3 services. Inversement, imposer des microservices à une équipe de 3 personnes crée de la friction sans valeur.

5.2 Strangler Fig Pattern

🔴 Expert

Moderniser un legacy en extrayant progressivement des features vers de nouveaux services, en plaçant un API Gateway devant les deux. À terme, le legacy est entièrement remplacé sans jamais avoir fait de réécriture complète risquée.

Strangler Fig — Migration progressive

Étape 1 : Gateway devant le legacy
API Gateway
100% trafic → Legacy monolithe tout passe encore par l'ancien
Étape 2 : Extraire une feature
Nouveau service A
Feature extraite catalog-service
Legacy monolithe
Reste du système en réduction progressive
Étape N : Legacy entièrement remplacé
Service A
catalog
Service B
loan
Service C
notification
Le legacy a disparu sans réécriture "big bang". Chaque étape est déployable et réversible indépendamment.

Q1 — "Pourquoi les microservices et pas un monolithe ?"

Ce qu'on attend

Une justification contextuelle, pas "parce que c'est mieux". Idéalement : autonomie des équipes, scaling différencié, isolation des domaines. Une réponse honnête incluant les compromis est meilleure qu'une réponse marketing. "Aucune limite connue" est éliminatoire.

Q2 — "Que se passe-t-il si catalog-service est indisponible 1h ?"

Ce qu'on attend

Circuit breaker (évite la cascade), fallback (réponse dégradée), alerte Prometheus, runbook d'incident. Bonus : cache pour servir les données en lecture même si le service est down.

Q3 — "Comment un nouveau dev déploie-t-il en production ?"

Ce qu'on attend

Pipeline CI/CD automatisé : git push → build → tests → scan CVE → image Docker → déploiement Kubernetes. Aucune étape manuelle. Le développeur ne touche pas kubectl en production.

Quiz de fin — Jour 6

1. Quelle est la différence entre Blue-Green et Canary ?

Voir la réponse

Blue-Green : bascule 100% du trafic d'un coup entre 2 environnements complets. Rollback en secondes mais double coût infra. Canary : exposition progressive (5% → 20% → 100%) pour limiter le blast radius. Plus de complexité routing/observabilité mais risque maîtrisé.

2. Pourquoi utiliser un multi-stage build Docker ?

Voir la réponse

Séparer l'environnement de build (JDK + Maven = lourd) du runtime (JRE seul = léger). L'image finale ne contient que le nécessaire à l'exécution : 3x plus petite, surface d'attaque CVE réduite, pull plus rapide.

3. Qu'est-ce qu'un ADR et pourquoi en écrire ?

Voir la réponse

Un Architecture Decision Record capture une décision architecturale : contexte, décision, alternatives, conséquences. Sans ADR, les équipes qui arrivent 6 mois plus tard ne savent pas pourquoi l'architecture est ainsi, et prennent des décisions contradictoires.

4. Qu'est-ce que la Loi de Conway ?

Voir la réponse

La structure d'un système reflète la structure de communication de l'organisation qui le produit. Conséquence : si vous voulez des microservices découplés, organisez vos équipes en squads autonomes par domaine. Imposer des microservices à une équipe unique crée de la complexité sans bénéfice.

5. (Expert) Qu'est-ce que le Strangler Fig Pattern ?

Voir la réponse

Migration progressive d'un legacy : extraction feature par feature vers de nouveaux services, un API Gateway devant les deux systèmes. À terme, le legacy est remplacé sans réécriture complète risquée. À utiliser quand le système est trop important pour être arrêté.
