Panorama des patterns d'architecture

Un pattern d'architecture est une solution connue et éprouvée pour un problème récurrent. Choisir un pattern c'est choisir ses avantages et ses inconvénients — pas de silver bullet.

PatternIdée centraleQuand l'utiliserLimite principale
LayeredCouches techniques empiléesApp simple, équipe débutanteCouplage implicite entre couches
HexagonalDomaine au centre, ports/adaptersTestabilité forte, isolation du métierPlus de fichiers, discipline requise
Clean ArchitectureRègle de dépendance vers l'intérieurLongue durée de vie, métier très richeAbstractions parfois excessives
OnionAnneaux concentriques autour du domaineProche de Hexagonal / CleanPeut sembler théorique au départ
CQRSSéparer lecture et écritureLectures complexes, haute scalabilitéCohérence éventuelle à gérer
MVCModèle / Vue / ContrôleurUI web classiquesInsuffisant seul pour le backend

Mode enfant 🧸

Imagine que tu construis une maison. Tu peux juste empiler des briques (Layered), ou faire un plan précis où chaque pièce a un rôle (Hexagonal), ou diviser en zones avec des règles d'accès strictes (Clean). Le plan dépend de la taille de la maison et de combien de personnes vont y vivre.

Mode pro 🎓 — Comment choisir ?

La complexité architecturale doit être proportionnelle à la complexité métier et à la durée de vie du projet. Un CRUD simple avec 5 tables ne mérite pas une Clean Architecture. Un calcul de risque financier qui durera 10 ans le mérite. Over-engineering et under-engineering sont tous les deux coûteux.

✅ Ce qu’on assume clairement dans ce chapitre

Le support ne montre pas un simple backend “en couches” classique. Il montre déjà une architecture hexagonale légère avec DDD tactique : un domaine métier isolé, une couche application qui orchestre les cas d’usage, et une infrastructure qui implémente les détails techniques. C’est ce choix qui rend le code plus propre, mais aussi un peu plus avancé.

Le titre initial parlait surtout de “patterns et structuration”, alors que l’exemple Java va plus loin : CreateLoanUseCase, LoanRepositoryPort, LoanApplicationService et JpaLoanRepositoryAdapter relèvent déjà d’une organisation hexagonale. Cette version du chapitre l’assume et l’explique explicitement.

Architecture hexagonale — en profondeur

Principe fondamental

Le domaine métier ne dépend de rien — ni de Spring, ni de JPA, ni de Kafka. Il expose des ports (interfaces) et des adapters externes réalisent les détails techniques.

Comment lire cette section : commence par le schéma global, puis ouvre l’arborescence et clique sur les fichiers dans cet ordre : LoanController → CreateLoanUseCase → LoanApplicationService → Loan → LoanRepositoryPort → JpaLoanRepositoryAdapter.

Chaque clic affiche le code complet avec imports, pour éviter de se perdre entre les couches.

Schéma simplifié : les adapters parlent aux ports, et les dépendances de code vont toujours vers l’intérieur.

Clique sur “Agrandir” pour lire le schéma plus confortablement.

Mode enfant 🧸

Ton téléphone (le domaine) ne sait pas comment il reçoit de l'électricité. Il expose juste une prise USB-C (le port). Tu peux brancher un chargeur mural, une batterie externe ou un câble voiture (les adapters). Si tu changes de chargeur, ton téléphone ne change pas.

Comprendre vraiment les ports et les adapters

En architecture hexagonale, on ne raisonne pas d’abord en termes de framework, mais en termes de conversation avec le métier :

Port entrant (inbound port)

C’est ce que l’application sait faire. Un contrôleur REST, une CLI, un test ou un message Kafka entrant appellent ce contrat.

  • CreateLoanUseCase = “créer un prêt”
  • ReturnBookUseCase = “retourner un livre”
  • Le port entrant est souvent une interface de cas d’usage
  • Son implémentation vit généralement dans application/service

Port sortant (outbound port)

C’est ce dont l’application a besoin pour travailler : base de données, bus d’événements, mail, API externe, cache, stockage de fichiers.

  • LoanRepositoryPort = besoin de persistance
  • LoanEventPublisher = besoin de publier un événement
  • Le port sortant est aussi une abstraction
  • Son implémentation vit dans infrastructure/...

Exemple mental simple

Le contrôleur REST n’appelle jamais directement JPA. Il appelle un use case. Ce use case utilise ensuite un port sortant pour sauvegarder les données. Ainsi, si tu remplaces JPA par MongoDB, JDBC, une API distante ou un faux repository de test, le cœur du métier ne change pas.

Qui appartient à quoi ?

Élément Exemple Couche Pourquoi ?

Value Object LoanId domain Exprime le langage métier sans dépendance technique
Port entrant CreateLoanUseCase application.port.in Expose une capacité de l’application
Commande de use case CreateLoanCommand application.port.in Transporte les données d’entrée du cas d’usage

Le cycle complet d’un cas d’usage hexagonal

1. Entrée

  • HTTP arrive dans LoanController
  • Le DTO web est validé
  • Le contrôleur appelle un UseCase

2. Orchestration

  • LoanApplicationService implémente le use case
  • Construit les objets métier
  • Appelle les ports sortants nécessaires

3. Technique

  • L’adapter JPA sauvegarde
  • Un publisher Kafka peut notifier
  • La réponse remonte vers le contrôleur

Le contrôleur connaît le use case. Le use case connaît les ports. Les adapters implémentent les ports. Le domaine, lui, ne connaît jamais la techno concrète.

Erreurs fréquentes à éviter

  • Mettre @Entity, @Repository ou @RestController dans domain/
  • Faire dépendre le domaine de Spring, Hibernate ou d’une API REST externe
  • Appeler directement JpaRepository depuis le contrôleur
  • Transformer le service d’application en énorme classe qui contient tout le métier
  • Confondre port et adapter : le port est le contrat, l’adapter est l’implémentation

Service d'application — implémente le use case

import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
@Transactional
public class LoanApplicationService
        implements CreateLoanUseCase, ReturnBookUseCase {

    private final LoanRepositoryPort   loanRepository;
    private final BookAvailabilityPort bookAvailability;
    private final LoanEventPublisher   eventPublisher;

    @Override
    public LoanId createLoan(CreateLoanCommand command) {
        // 1. Vérifier disponibilité via le port (abstraction)
        if (!bookAvailability.isAvailable(command.bookId())) {
            throw new BookNotAvailableException(command.bookId());
        }
        // 2. Créer l'agrégat — toutes les règles métier sont là
        Loan loan = Loan.create(command.studentId(), command.bookId());
        // 3. Persister et publier
        loanRepository.save(loan);
        bookAvailability.decrementStock(command.bookId());
        eventPublisher.publish(LoanCreatedEvent.of(loan));
        return loan.getId();
    }
}

Adapter JPA — implémente le port sortant

import java.util.List;
import java.util.Optional;
import java.util.UUID;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

@Component
@RequiredArgsConstructor
public class JpaLoanRepositoryAdapter implements LoanRepositoryPort {

    private final SpringDataLoanRepository jpa;
    private final LoanEntityMapper         mapper;

    @Override
    public void save(Loan loan) {
        jpa.save(mapper.toEntity(loan));
    }

    @Override
    public Optional<Loan> findById(LoanId id) {
        return jpa.findById(id.value()).map(mapper::toDomain);
    }

    @Override
    public List<Loan> findActiveByStudent(UUID studentId) {
        return jpa.findByStudentIdAndStatus(studentId, LoanStatus.ACTIVE)
                  .stream().map(mapper::toDomain).toList();
    }
}

✅ Règle de la flèche de dépendance

Les flèches de dépendance pointent toujours vers le domaine. L'infrastructure implémente les ports du domaine. Si vous voyez import org.springframework ou import jakarta.persistence dans votre package domain/, c'est une violation d'architecture.

Inversion de dépendance — le "D" de SOLID appliqué

L'inversion de dépendance (DIP) est le principe qui rend l'hexagonal possible : la logique métier dépend d'abstractions stables, pas d'implémentations instables.

Clique sur “Agrandir” pour lire le schéma plus confortablement.

❌ Sans inversion — couplage direct

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class LoanService {
    // Dépendance concrète JPA !
    @Autowired
    private JpaLoanRepository repo;
    // Changer de BDD → modifier ce service
}

✅ Avec inversion — abstraction

import org.springframework.stereotype.Service;

@Service
public class LoanApplicationService {
    // Abstraction — JPA, Mongo ou InMemory
    private final LoanRepositoryPort repo;
    public LoanApplicationService(
            LoanRepositoryPort repo) {
        this.repo = repo;
    }
}

Mode pro 🎓 — L'impact sur les tests

Avec l'inversion de dépendance, on injecte un repository in-memory dans les tests — zéro base de données, zéro contexte Spring. Un test de domaine s'exécute en millisecondes. Un test d'intégration avec Postgres prend 2–5 secondes. Sur 500 tests : 5 secondes vs 40 minutes.

DDD tactique — les briques du domaine

Le Domain-Driven Design (Eric Evans, 2003) place le domaine métier au cœur de toutes les décisions. Ce n'est pas un pattern d'architecture, mais un ensemble de briques tactiques pour modéliser le domaine de façon riche et expressive.

Mode enfant 🧸

Le DDD, c'est parler le même langage que les experts métier. Si le bibliothécaire dit "prêt", "retour", "prolongation", ton code doit avoir des classes Loan, Return, Extension — pas DataRecord ou ProcessObject.

"The heart of software is its ability to solve domain-related problems for its users." — Eric Evans

Agrégat & Racine d'agrégat

Règles des agrégats

  • On ne modifie jamais un objet interne directement — on passe par la racine.
  • Les transactions ne franchissent jamais les frontières d'un agrégat.
  • Les agrégats communiquent entre eux par identité (UUID), jamais par référence directe.
// Loan est la racine — il contrôle tous ses invariants
public class Loan {
    private final LoanId id;
    private final UUID   studentId;
    private final UUID   bookId;
    private       LoanStatus status;
    private final Instant    createdAt;
    private       Instant    dueDate;
    private       Instant    returnedAt;

    // Factory method — la création valide les règles
    public static Loan create(UUID studentId, UUID bookId) {
        return new Loan(
            LoanId.generate(), studentId, bookId,
            LoanStatus.ACTIVE, Instant.now(),
            Instant.now().plus(21, ChronoUnit.DAYS), // règle : 3 semaines
            null
        );
    }

    // Méthode métier — encapsule la règle de retour
    public void returnBook() {
        if (this.status == LoanStatus.RETURNED)
            throw new BusinessException("Ce prêt est déjà clôturé.");
        if (this.status == LoanStatus.CANCELLED)
            throw new BusinessException("Un prêt annulé ne peut pas être retourné.");
        this.status     = LoanStatus.RETURNED;
        this.returnedAt = Instant.now();
    }

    // Méthode métier — est-il en retard ?
    public boolean isOverdue() {
        return status == LoanStatus.ACTIVE
            && Instant.now().isAfter(dueDate);
    }

    // Prolongation (règle : pas si déjà en retard)
    public void extend(int days) {
        if (status != LoanStatus.ACTIVE)
            throw new BusinessException("Impossible de prolonger un prêt inactif.");
        if (isOverdue())
            throw new BusinessException("Impossible de prolonger un prêt en retard.");
        this.dueDate = dueDate.plus(days, ChronoUnit.DAYS);
    }

    // Getters — PAS de setters publics (encapsulation forte)
    public LoanId     getId()        { return id;        }
    public UUID       getStudentId() { return studentId; }
    public LoanStatus getStatus()    { return status;    }
    public boolean    isActive()     { return status == LoanStatus.ACTIVE; }
}

⚠️ Agrégat anémique — l'anti-pattern le plus répandu

// ❌ ANTI-PATTERN : Agrégat anémique
// (2 fichiers montrés ensemble pour illustrer le problème)

// domain/model/Loan.java — version anémique
public class Loan {
    private LoanStatus status;
    public void setStatus(LoanStatus s) { this.status = s; }
    // → Aucune logique : qui contrôle les règles ?
}

// application/service/LoanService.java — logique éparpillée
public class LoanService {
    public void returnBook(UUID loanId) {
        Loan loan = repo.findById(loanId);
        if (loan.getStatus() == LoanStatus.RETURNED) // règle dupliquée !
            throw new BusinessException("Déjà retourné");
        loan.setStatus(LoanStatus.RETURNED); // violation d'encapsulation
    }
}

Résultat : règles métier dupliquées dans tous les services, invariants non garantis, bugs qui se multiplient.

Service de domaine

Quand une règle métier implique plusieurs agrégats, on crée un service de domaine — pur, sans état, sans framework.

import java.util.List;
import java.util.UUID;

// "Un étudiant ne peut pas emprunter plus de 5 livres simultanément"
public class LoanDomainService {

    public void validateStudentQuota(UUID studentId, List<Loan> activeLoans) {
        long count = activeLoans.stream().filter(Loan::isActive).count();
        if (count >= 5) {
            throw new QuotaExceededException(
                "Quota de 5 emprunts actifs atteint pour l'étudiant " + studentId);
        }
    }
}

Value Objects — des types qui ont du sens métier

Un Value Object est un objet défini uniquement par sa valeur, sans identité propre. Il est immuable — on ne le modifie jamais, on en crée un nouveau.

Mode enfant 🧸

Un billet de 10€ est un Value Object. Deux billets de 10€ sont identiques — ce qui compte c'est la valeur, pas "quel billet précisément". Si tu veux 20€, tu prends deux billets — tu ne modifies pas le premier.

❌ Sans Value Object — types primitifs dangereux

// Un UUID peut être bookId ou studentId...
// Le compilateur ne peut pas détecter l'erreur !
public void save(UUID bookId, UUID studentId) { ... }

// Bug silencieux : arguments inversés
service.save(studentId, bookId); // compile, mais faux !

✅ Avec Value Objects — types expressifs

// domain/model/LoanId.java
package fr.univ.library.domain.model;

import java.util.Objects;
import java.util.UUID;

public record LoanId(UUID value) {
    public LoanId {
        Objects.requireNonNull(value);
    }
    public static LoanId generate() {
        return new LoanId(UUID.randomUUID());
    }
}
// BookId.java et StudentId.java suivent le même pattern
// Résultat : impossible de confondre BookId et StudentId
public void save(BookId bookId, StudentId studentId) { ... }
// save(studentId, bookId) → erreur de compilation !

Value Object métier — ISBN avec validation

import java.util.Objects;
import java.util.regex.Pattern;

public record Isbn(String value) {

    private static final Pattern ISBN_13 =
        Pattern.compile("^97[89]\\d{10}$");

    // Validation à la construction — impossible de créer un ISBN invalide
    public Isbn {
        Objects.requireNonNull(value, "ISBN ne peut pas être null");
        String clean = value.replaceAll("[\\s-]", "");
        if (!ISBN_13.matcher(clean).matches())
            throw new InvalidIsbnException("Format ISBN-13 invalide : " + value);
        value = clean; // normalisation
    }

    @Override public String toString() { return value; }
}

// Usage : la validation est garantie — pas besoin de la répéter ailleurs
Book book = new Book(BookId.generate(), "Clean Code",
                     new Isbn("978-0-13-235088-4")); // valide ou exception

Événements de domaine

Un événement de domaine représente quelque chose d'important qui s'est produit dans le domaine. Nommé au passé, immuable, il exprime le fait accompli.

Règles des événements de domaine

  • Nommé au passé : LoanCreated, BookReturned, StudentBlocked.
  • Immuable — une fois créé, jamais modifié.
  • Contient toutes les informations pertinentes au moment de l'occurrence.
  • POJO pur ou Java record — zéro dépendance framework.
// domain/event/DomainEvent.java
package fr.univ.library.domain.event;

import java.time.Instant;
import java.util.UUID;

public interface DomainEvent {
    UUID    eventId();
    Instant occurredAt();
}
// domain/event/LoanCreatedEvent.java

import java.time.Instant;
import java.util.UUID;

    Instant occurredAt,

        return new LoanCreatedEvent(

Pattern — accumuler et publier les événements

Étape 1 — L'agrégat accumule ses événements :

// domain/model/Loan.java — extrait (ajout de la gestion d'événements)
public class Loan {
    private final List<DomainEvent> domainEvents = new ArrayList<>();

    public static Loan create(UUID studentId, UUID bookId) {
        Loan loan = new Loan(/* ... */);
        loan.domainEvents.add(LoanCreatedEvent.of(loan));
        return loan;
    }

    public List<DomainEvent> pullEvents() {
        List<DomainEvent> events = List.copyOf(domainEvents);
        domainEvents.clear();
        return events;
    }
}

Étape 2 — Le service d'application publie APRÈS persistance :

// application/service/LoanApplicationService.java — extrait
@Override
@Transactional
public LoanId createLoan(CreateLoanCommand cmd) {
    Loan loan = Loan.create(cmd.studentId(), cmd.bookId());
    loanRepository.save(loan);
    // Publié après commit pour cohérence
    loan.pullEvents().forEach(eventPublisher::publish);
    return loan.getId();
}

// infrastructure/messaging/LoanNotificationListener.java
@Component
@RequiredArgsConstructor
public class LoanNotificationListener {

    private final NotificationService notificationService;

    @EventListener
    public void onLoanCreated(LoanCreatedEvent event) {
        notificationService.sendConfirmation(
            event.studentId(), event.loanId());
    }
}

⚠️ Événements intra-service vs inter-services

ApplicationEventPublisher est synchrone et dans le même processus — parfait pour un monolithe. Pour communiquer entre microservices distincts, il faut un broker externe (Kafka, RabbitMQ) — couvert au Jour 4.

CQRS — Command Query Responsibility Segregation

CQRS sépare les opérations d'écriture (Commands) des opérations de lecture (Queries). Les besoins de lecture et d'écriture sont souvent si différents qu'ils justifient des modèles séparés.

Mode enfant 🧸

Dans un restaurant, la commande (ce que tu veux manger) passe par le serveur vers la cuisine. La carte (menu à lire) est conçue pour être consultée rapidement par tout le monde. Ce sont deux flux totalement différents — la cuisine ne gère pas la carte.

// application/cqrs/LoanCommandHandler.java
package fr.univ.library.application.cqrs;

import fr.univ.library.domain.model.*;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

@Service
@RequiredArgsConstructor
public class LoanCommandHandler {

    private final LoanRepositoryPort loanRepo;

    public LoanId handle(CreateLoanCommand cmd) {
        Loan loan = Loan.create(cmd.studentId(), cmd.bookId());
        loanRepo.save(loan);
        return loan.getId();
    }

    public void handle(ReturnBookCommand cmd) {
        Loan loan = loanRepo.findById(cmd.loanId()).orElseThrow();
        loan.returnBook(); // logique dans l'agrégat
        loanRepo.save(loan);
    }
}

Mise à jour de la projection par événement

// infrastructure/projection/LoanSummaryProjector.java
package fr.univ.library.infrastructure.projection;

import lombok.RequiredArgsConstructor;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

@Component
@RequiredArgsConstructor
public class LoanSummaryProjector {

    private final CatalogClient catalogClient;
    private final IdentityClient identityClient;
    private final LoanSummaryRepository loanSummaryRepository;

    @EventListener
    @Transactional
    public void on(LoanCreatedEvent event) {
        String bookTitle   = catalogClient.getBookTitle(event.bookId());
        String studentName = identityClient.getStudentName(event.studentId());

        LoanSummaryEntity view = new LoanSummaryEntity();
        view.setLoanId(event.loanId().value());
        view.setBookTitle(bookTitle);
        view.setStudentName(studentName);
        view.setStatus("ACTIVE");
        view.setDueDate(event.dueDate());
        loanSummaryRepository.save(view);
    }
}

Mode pro 🎓 — Quand utiliser CQRS ?

  • ✅ Les lectures sont beaucoup plus fréquentes que les écritures.
  • ✅ Le modèle de lecture nécessite des jointures complexes ou des données agrégées.
  • ✅ On veut scaler la lecture indépendamment de l'écriture (réplicas en lecture seule).
  • ❌ CRUD simple — CQRS est un over-engineering si les modèles lecture/écriture sont identiques.

MapStruct — mapping sans boilerplate

MapStruct génère les mappers entre objets à la compilation. Zéro réflexion à l'exécution, zéro boilerplate, et les erreurs de mapping sont détectées au build.

Dépendance Maven

<dependency>
    <groupId>org.mapstruct</groupId>
    <artifactId>mapstruct</artifactId>
    <version>1.6.0</version>
</dependency>
<!-- Dans annotationProcessorPaths — après Lombok si utilisé -->
<path>
    <groupId>org.mapstruct</groupId>
    <artifactId>mapstruct-processor</artifactId>
    <version>1.6.0</version>
</path>
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.Named;
import java.util.List;
import java.util.UUID;

@Mapper(componentModel = "spring")
public interface BookMapper {

    // Domaine → DTO de réponse (mapping automatique par nom de champ)
    BookResponse toResponse(Book book);

    // Liste de domaine → liste DTO
    List<BookSummary> toSummaryList(List<Book> books);

    // DTO d'entrée → domaine (id ignoré — généré par le domaine)
    @Mapping(target = "id", ignore = true)
    Book toDomain(CreateBookRequest request);

    // Domaine → Entité JPA (LoanId → UUID)
    @Mapping(source = "id.value", target = "id")
    LoanJpaEntity toEntity(Loan loan);

    // Entité JPA → Domaine (UUID → LoanId)
    @Mapping(source = "id", target = "id",
             qualifiedByName = "uuidToLoanId")
    Loan toDomain(LoanJpaEntity entity);

    @Named("uuidToLoanId")
    default LoanId uuidToLoanId(UUID uuid) { return new LoanId(uuid); }
}

✅ Ce que MapStruct génère à la compilation

// Code généré — ne jamais modifier manuellement
@Component
public class BookMapperImpl implements BookMapper {
    @Override
    public BookResponse toResponse(Book book) {
        if (book == null) return null;
        return new BookResponse(
            book.getId().value(), book.getTitle(),
            book.getAuthor(), book.getStock(),
            book.getIsbn().value(), book.getCreatedAt()
        );
    }
    // ... autres méthodes
}

Si un champ change dans le domaine et n'est pas mappé, le build échoue avec un message précis — vous êtes alerté immédiatement.

⚠️ Pièges classiques avec MapStruct

  • Oublier componentModel = "spring" → le mapper n'est pas un bean Spring.
  • Conflit avec Lombok → mettre le processor MapStruct après Lombok dans annotationProcessorPaths.
  • Mapper des entités JPA avec lazy loading → déclenche des requêtes N+1 pendant la sérialisation.

Tests d'architecture avec ArchUnit

ArchUnit vérifie automatiquement les règles d'architecture dans vos tests. Si quelqu'un viole une règle, le build CI casse — pas besoin de revue de code pour le détecter.

import com.tngtech.archunit.junit.AnalyzeClasses;
import com.tngtech.archunit.junit.ArchTest;
import com.tngtech.archunit.lang.ArchRule;

import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.classes;
import static com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses;
import static com.tngtech.archunit.library.Architectures.layeredArchitecture;

@AnalyzeClasses(packages = "fr.univ.library")
class ArchitectureTest {

    // Le domaine n'importe aucune classe Spring
    @ArchTest
    static final ArchRule domain_no_spring =
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..");

    // Le domaine n'importe aucune classe JPA
    @ArchTest
    static final ArchRule domain_no_jpa =
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("jakarta.persistence..");

    // Les contrôleurs ne touchent pas aux repositories
    @ArchTest
    static final ArchRule controllers_no_repos =
        noClasses()
            .that().resideInAPackage("..web..")
            .should().dependOnClassesThat()
            .resideInAPackage("..persistence..");

    // Les ports entrants sont des interfaces
    @ArchTest
    static final ArchRule ports_in_are_interfaces =
        classes()
            .that().resideInAPackage("..port.in..")
            .should().beInterfaces();

    // Architecture en couches vérifiée globalement
    @ArchTest
    static final ArchRule layered =
        layeredArchitecture()
            .consideringAllDependencies()
            .layer("Web")           .definedBy("..infrastructure.web..")
            .layer("Application")   .definedBy("..application..")
            .layer("Domain")        .definedBy("..domain..")
            .layer("Infra")         .definedBy("..infrastructure..")
            .whereLayer("Web")      .mayNotBeAccessedByAnyLayer()
            .whereLayer("Domain")   .mayOnlyBeAccessedByLayers("Application", "Infra");
}

✅ Pourquoi c'est indispensable en équipe

Un développeur junior peut involontairement injecter un JpaRepository dans le domaine. Sans ArchUnit, cela peut passer en revue de code. Avec ArchUnit, le build CI casse immédiatement avec un message précis. C'est du linting architectural automatisé — les règles implicites deviennent des tests exécutables.

## ADR-001 : Architecture hexagonale plutôt que Layered

Statut : Accepté — 2025-09-15
Contexte : Besoin de testabilité forte du domaine métier et
           préparation à un éventuel découpage en services.
Décision : Hexagonal avec ports et adapters.
Alternatives rejetées :
  - Layered simple : couplage JPA dans le domaine, tests lents
  - Clean Architecture : trop d'abstractions pour une équipe de 3
Conséquences :
  + Tests domaine sans Spring en millisecondes
  + Domaine portable si changement de technologie
  - Plus de fichiers (ports, adapters, mappers)
  - Courbe d'apprentissage initiale

## ADR-002 : MapStruct pour le mapping

Statut : Accepté — 2025-09-15
Contexte : 3 couches d'objets nécessitent du mapping sans boilerplate.
Décision : MapStruct avec génération à la compilation.
Alternatives rejetées :
  - Mapping manuel : verbeux, erreur-prone
  - ModelMapper : réflexion runtime, moins sûr à la compilation

  + Erreurs de mapping détectées au build
  - Syntaxe d'annotation à apprendre

Relire le code dans le bon ordre

Ordre conseillé pour comprendre l’exemple Java

  1. LibraryApplication.java — lance Spring Boot, rien de métier ici.
  2. Loan.java et LoanId.java — cœur métier.
  3. CreateLoanUseCase.java et CreateLoanCommand.java — ce que l’application propose comme action.
  4. LoanApplicationService.java — orchestration du cas d’usage.
  5. LoanRepositoryPort.java — contrat technique attendu.
  6. JpaLoanRepositoryAdapter.java et LoanJpaEntity.java — implémentation JPA.
  7. LoanController.java — point d’entrée REST.

Mode enfant 🧸

Tu peux imaginer ce flux : HTTP → Controller → UseCase → Service d’application → Domaine → Port → Adapter JPA → Base de données. Chaque bloc a un rôle précis ; c’est justement ce découpage qui évite de mélanger tout dans une seule classe.

Ce qu'il faut retenir

🎯 Les flèches de dépendance pointent toujours vers le domaine — jamais l'inverse.

🔵 Couche Domain

  • Zéro dépendance framework — ni Spring, ni JPA, ni Kafka.
  • Les entités (Loan, Book) encapsulent les règles métier — pas de setters publics.
  • Les Value Objects (LoanId, Isbn) apportent la sécurité de typage et la validation à la construction.
  • Les services de domaine gèrent la logique inter-agrégats (ex : quotas).
  • Les événements sont immuables, nommés au passé, POJO purs.

🟢 Couche Application

  • Les ports entrants (CreateLoanUseCase) décrivent les cas d’usage que l’application propose au monde extérieur.
  • Les ports sortants (LoanRepositoryPort) définissent ce dont la couche application a besoin pour faire son travail technique.
  • Le service d'application orchestre : il appelle le domaine + les ports, mais ne contient aucune logique métier.
  • Les Commands transportent une intention — elles sont immuables (records).

🟠 Couche Infrastructure

  • Les adapters JPA (JpaLoanRepositoryAdapter) implémentent les ports sortants — ils convertissent entre domaine et persistance.
  • L'entité JPA (LoanJpaEntity) est séparée de l'entité domaine — les annotations @Entity vivent ici.
  • Le contrôleur REST dépend du port entrant (interface), jamais directement d’un repository.
  • L'adapter Kafka publie les événements domaine vers l'extérieur.

Comment lire cette structure sans se perdre

  • domain/ = le métier pur : ici vivent les vraies règles.
  • application/ = les cas d’usage : cette couche orchestre, sans contenir la logique métier profonde.
  • infrastructure/ = la technique : JPA, Kafka, mapping, accès externes.
  • entrypoint/ = ce qui entre dans l’application, par exemple REST.
  • LibraryApplication.java reste à la racine du projet, car elle lance Spring Boot ; elle ne fait pas partie du métier.

⚠️ Les 3 erreurs les plus fréquentes des étudiants

  • Mettre @Entity dans domain/model/ → Violation d'architecture : le domaine ne connaît pas JPA. L'entité JPA vit dans infrastructure/persistence/.
  • Écrire la logique métier dans le repository → Le repository ne fait que persister et retrouver. Les règles métier sont dans l'agrégat ou le service de domaine.
  • Injecter un JpaRepository dans le service d'application → Il faut injecter le port (LoanRepositoryPort), pas l'implémentation concrète.

Quiz de fin

1. Pourquoi l'hexagonal peut-il être plus coûteux au début mais rentable sur la durée ?

Voir la réponse

Il demande plus de code au départ (ports, adapters, mappers). Ce coût est rentabilisé par des tests ultra-rapides (domaine sans Spring), une maintenabilité accrue (changer la BDD ne touche qu'un adapter) et une facilité de migration vers des microservices (le domaine est déjà isolé).

2. Quelle est la différence entre un port entrant et un port sortant ?

Voir la réponse

Un port entrant représente ce que le domaine offre au monde extérieur — c'est un use case (ex : CreateLoanUseCase). Un port sortant représente ce que le domaine requiert de l'infrastructure (ex : LoanRepositoryPort). Le domaine définit les deux ; l'infrastructure implémente les ports sortants.

3. Que signifie "Bounded Context" et comment l'identifier ?

Voir la réponse

Une frontière linguistique où chaque terme a un sens unique et non ambigu. On l'identifie en cherchant les ambiguïtés de langage : si "Client" n'a pas le même sens en comptabilité et au support, on a deux contextes. Pratiquement : parlez avec les experts métier et construisez un Ubiquitous Language par sous-domaine.

4. Pourquoi un repository ne doit-il jamais contenir de règles métier ?

Voir la réponse

Le repository a une seule responsabilité : persister et retrouver des objets. Des règles métier dans le repository violent le SRP, les rendent non testables sans base de données et ouvrent la porte aux contournements accidentels (si quelqu'un accède à la BD sans passer par ce repository, la règle est ignorée).

5. Pourquoi utiliser des Value Objects plutôt que des String ou des UUID bruts ?

Voir la réponse

Expressivité (signature auto-documentée), validation à la construction (impossible de créer un Isbn invalide), encapsulation du comportement et sécurité à la compilation (impossible de passer un BookId là où un LoanId est attendu). Ils éliminent toute une catégorie de bugs de confusion d'arguments.

6. Quelle est la différence entre une Command et une Query dans CQRS ?

Voir la réponse

Une Command exprime une intention de modifier l'état — elle ne retourne rien ou juste un ID. Une Query ne fait que lire l'état — elle ne modifie jamais rien. Cette séparation permet d'optimiser chaque côté indépendamment : modèle d'écriture riche avec agrégats, modèle de lecture avec vue SQL dénormalisée.

7. À quoi sert ArchUnit et pourquoi est-il préférable aux règles de revue de code manuelles ?

Voir la réponse

ArchUnit vérifie les règles d'architecture automatiquement à chaque build. Une revue manuelle peut rater une violation (fatigue, oubli, urgence). ArchUnit ne rate jamais et casse le build CI avec un message précis. Il transforme les règles implicites en tests exécutables vérifiés en continu — c'est du linting architectural.
