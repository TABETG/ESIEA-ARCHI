Qu'est-ce qu'un système distribué ?

En une phrase

Un système distribué = plusieurs services séparés qui coopèrent.

Problème

Le réseau remplace l'appel local.

À dire à l’oral

Ici, le mot clé, c'est réseau : dès qu'on sort du processus local, tout devient plus incertain.

Mot-clé

latence / panne / message

Ce que tu peux dire à l’oral

“Retenez juste ça : un monolithe fait surtout des appels mémoire, un système distribué fait des appels réseau. Et le réseau, lui, peut être lent, tomber, ou répondre en double.”

Cette section pose le vocabulaire de base : plusieurs processus, plusieurs machines, échanges réseau, autonomie de services et nouveaux types de pannes.

Junior → Expert

Un système distribué est un ensemble de composants exécutés sur plusieurs processus ou machines qui collaborent pour rendre un service unique à l'utilisateur. Les processus communiquent uniquement par échange de messages à travers un réseau.

Mode enfant 🧸

Au lieu d'avoir une seule grosse boutique qui vend tout, tu ouvres plusieurs petits magasins spécialisés (un pour les livres, un pour les DVD, un pour la livraison) qui doivent se parler correctement. Si l'un ferme, les autres continuent, mais ils doivent gérer l'absence de leur collègue.

📌 Où est le broker dans ce schéma ?

Le broker est le grand bloc sombre “BROKER / Kafka”, à droite. Le Loan Service y publie un événement, puis d’autres services le consomment ensuite.

  • Producer : service qui envoie un message au broker.
  • Broker : composant intermédiaire qui reçoit, stocke temporairement et redistribue les messages.
  • Consumer : service qui lit ces messages pour agir ensuite.

À dire à l’oral : “Le broker n’est pas une base de données métier. C’est la poste des événements.”

Mode pro 🎓

Le distribué introduit : latence non-nulle, pannes partielles, duplication de messages, cohérence asynchrone, sécurité réseau et complexité opérationnelle. En échange, il apporte autonomie de déploiement, scalabilité ciblée et alignement par domaine métier.

Les 8 fausses hypothèses du distribué (Fallacies of Distributed Computing)

Peter Deutsch (Sun Microsystems, 1994) a listé 8 croyances erronées que font les développeurs :

  1. Le réseau est fiable.
  2. La latence est nulle.
  3. La bande passante est infinie.
  4. Le réseau est sécurisé.
  5. La topologie ne change pas.
  6. Il n'y a qu'un seul administrateur réseau.
  7. Le transport est sans coût.
  8. Le réseau est homogène.

Chaque hypothèse fausse est une source potentielle de bugs de production.

À retenir

Passer de local à distribué change la nature des erreurs : on ne gère plus seulement des bugs métiers, mais aussi des incertitudes réseau.

Question utile

Pour chaque appel distant, demande-toi : que se passe-t-il s'il répond lentement, deux fois, ou pas du tout ?

Bonne pratique

Définis explicitement timeouts, retries, logs corrélés et comportement de repli avant la mise en production.

⚙️ Expert — Latence p50, p95, p99, p999

La moyenne cache les pics. En distribué, on regarde les percentiles pour voir ce que vivent la majorité des utilisateurs et les cas lents.

Explication simple

Imagine 1000 requêtes triées de la plus rapide à la plus lente :

  • p50 = la 500e requête
  • p95 = la 950e requête
  • p99 = la 990e requête
  • p999 = la 999e requête

Donc p99 ne parle pas de la majorité. Il parle des 1% les plus lents. C’est exactement là qu’on voit les bugs de production, les timeouts, les appels externes lents et les saturations.

Lecture visuelle de la distribution

Idée simple : la plupart des requêtes sont rapides, mais quelques-unes deviennent très lentes. Cette petite partie rare et lente, tout à droite, s'appelle la queue de distribution.

Lecture immédiate

  • Si p50, p95 et p99 restent proches : le système est globalement sain.
  • Si p50 reste bas mais p99 monte fort : la majorité va bien, mais une minorité subit un gros problème.
  • La queue de distribution = la partie rare mais très lente des requêtes.

Résoudre concrètement les causes de queue de latence — résumé + code commenté

But : avant de toucher au code, il faut comprendre ce qui bloque, pourquoi, puis appliquer la bonne correction. Ici, on part des causes les plus classiques : SQL sans index, HTTP externe lent, pool saturé, GC, retry agressif, cache absent, cascade synchrone.

1. SQL sans index

  • Problème : la base scanne trop de lignes.
  • Effet : certaines requêtes deviennent très lentes.
  • Solution : index + pagination + requêtes ciblées.

2. HTTP externe lent

  • Problème : ton service attend un autre service.
  • Effet : un service lent ralentit tout ton endpoint.
  • Solution : timeout + fallback + circuit breaker.

3. Pool saturé

  • Problème : trop de tâches, pas assez de threads.
  • Effet : les requêtes attendent dans une file.
  • Solution : pool borné + queue + rejet contrôlé.

4. GC / mémoire

  • Problème : trop d’objets temporaires créés.
  • Effet : pauses JVM et pics de latence.
  • Solution : streaming, moins d’allocations, profiling mémoire.

5. Retry mal réglé

  • Problème : trop de tentatives, trop vite.
  • Effet : on surcharge encore plus le service en panne.
  • Solution : 2–3 tentatives max, backoff + jitter.

6. Cache absent

  • Problème : on relit toujours les mêmes données.
  • Effet : DB ou API inutilement surchargée.
  • Solution : cache applicatif ou Redis selon le besoin.

7. Cascade synchrone

  • Problème : une requête attend plusieurs services.
  • Effet : la latence totale s’additionne.
  • Solution : paralléliser ou passer certains flux en asynchrone.

Réflexe global

Cas 1 — Requête SQL sans index

Pourquoi ça pose problème : la base doit parcourir beaucoup trop de lignes pour trouver le résultat. Plus la table grossit, plus la requête devient lente.

Comment résoudre : ajouter un index sur la colonne filtrée, éviter de remonter trop de lignes, paginer.

Avant

@Repository
public interface OrderRepository extends JpaRepository<OrderEntity, Long> {

    // Problème : si la colonne status n'est pas indexée,
    // la base risque de scanner une grande partie de la table.
    List<OrderEntity> findByStatus(String status);
}
-- Sans index, la base peut faire un scan complet.
SELECT * FROM orders WHERE status = 'PENDING';

Après

-- On indexe la colonne utilisée dans le WHERE.
CREATE INDEX idx_orders_status ON orders(status);
@Repository
public interface OrderRepository extends JpaRepository<OrderEntity, Long> {

    // Ici, on filtre, on trie et on pagine.
    // Résultat : moins de lignes lues et moins de données remontées.
    @Query("""
        select o from OrderEntity o
        where o.status = :status
        order by o.createdAt desc
    """)
    Page<OrderEntity> findRecentByStatus(
        @Param("status") String status,
        Pageable pageable
    );
}

// On ne charge qu'une petite page de résultats.
Page<OrderEntity> page = orderRepository.findRecentByStatus(
    "PENDING",
    PageRequest.of(0, 50)
);

Cas 2 — Appel HTTP externe lent

Pourquoi ça pose problème : ton thread attend la réponse d’un service externe. Si ce service est lent, ton endpoint devient lent lui aussi.

Comment résoudre : mettre des timeouts, éviter l’attente infinie, prévoir un fallback si possible.

Avant

@Service
public class PaymentService {

    // Mauvais réflexe : client HTTP sans timeout explicite.
    private final RestTemplate restTemplate = new RestTemplate();

    public PaymentResponse pay(PaymentRequest request) {
        // Si l'API partenaire ralentit, le thread reste bloqué.
        return restTemplate.postForObject(
            "https://api.partner.com/pay",
            request,
            PaymentResponse.class
        );
    }
}

Après

@Configuration
public class HttpClientConfig {

    @Bean
    public RestTemplate restTemplate(RestTemplateBuilder builder) {
        return builder
            // Temps max pour ouvrir la connexion.
            .setConnectTimeout(Duration.ofSeconds(1))
            // Temps max pour attendre les données.
            .setReadTimeout(Duration.ofSeconds(2))
            .build();
    }
}

@Service
@RequiredArgsConstructor
public class PaymentService {

    private final RestTemplate restTemplate;

    public PaymentResponse pay(PaymentRequest request) {
        try {
            return restTemplate.postForObject(
                "https://api.partner.com/pay",
                request,
                PaymentResponse.class
            );
        } catch (ResourceAccessException e) {
            // On remonte une erreur métier claire.
            throw new ExternalServiceTimeoutException("Timeout paiement", e);
        }
    }
}

Cas 3 — Pool de threads saturé

Pourquoi ça pose problème : trop de tâches arrivent en même temps et attendent qu’un thread se libère.

Comment résoudre : définir un pool clair, une file bornée et une stratégie de rejet compréhensible.

Avant

@Service
public class ReportService {

    public void generateReports(List<Long> ids) {
        // Pool petit et peu maîtrisé.
        ExecutorService executor = Executors.newFixedThreadPool(4);

        for (Long id : ids) {
            // Si beaucoup de tâches arrivent,
            // elles s'accumulent et attendent.
            executor.submit(() -> heavyTask(id));
        }
    }

    private void heavyTask(Long id) {
        // Traitement long
    }
}

Après

@Configuration
public class AsyncConfig {

    @Bean("reportExecutor")
    public ThreadPoolTaskExecutor reportExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();

        // Nombre minimal de threads actifs.
        executor.setCorePoolSize(8);

        // Nombre maximal de threads.
        executor.setMaxPoolSize(16);

        // Taille max de la file d'attente.
        executor.setQueueCapacity(100);

        // Préfixe utile pour lire les logs.
        executor.setThreadNamePrefix("report-");

        // Si saturation, l'appelant exécute lui-même la tâche.
        executor.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());

        executor.initialize();
        return executor;
    }
}

@Service
@RequiredArgsConstructor
public class ReportService {

    private final ThreadPoolTaskExecutor reportExecutor;

    public void generateReports(List<Long> ids) {
        for (Long id : ids) {
            reportExecutor.execute(() -> heavyTask(id));
        }
    }

    private void heavyTask(Long id) {
        // Traitement long
    }
}

Cas 4 — GC pause / pression mémoire

Pourquoi ça pose problème : trop d’objets temporaires créés, donc la JVM doit nettoyer plus souvent.

Comment résoudre : éviter de tout garder en mémoire, préférer le streaming quand c’est possible.

Avant

@Service
public class ExportService {

    public byte[] export(List<Data> data) throws Exception {
        // On stocke tout en mémoire.
        List<String> rows = new ArrayList<>();

        for (Data d : data) {
            // Création de grosses chaînes temporaires.
            rows.add(buildHugeString(d));
        }

        // On reconcatène tout à la fin.
        return String.join("
", rows).getBytes(StandardCharsets.UTF_8);
    }

    private String buildHugeString(Data d) {
        return d.toString().repeat(1000);
    }
}

Après

@Service
public class ExportService {

    public void export(List<Data> data, OutputStream os) throws IOException {
        // On écrit au fil de l'eau,
        // au lieu de garder tout le fichier en mémoire.
        try (BufferedWriter writer = new BufferedWriter(new OutputStreamWriter(os))) {
            for (Data d : data) {
                writer.write(formatLine(d));
                writer.newLine();
            }
            writer.flush();
        }
    }

    private String formatLine(Data d) {
        // Chaîne simple, peu coûteuse.
        return d.id() + ";" + d.name();
    }
}

Cas 5 — Retry mal réglé

Pourquoi ça pose problème : si tout le monde retente trop vite, on aggrave une panne déjà présente.

Comment résoudre : réduire le nombre de tentatives, ajouter un backoff exponentiel et du jitter.

Avant

@Service
public class InventoryClient {

    public StockResponse getStock(UUID productId) {
        for (int i = 0; i < 10; i++) {
            try {
                // Mauvais : retry immédiat et agressif.
                return callRemote(productId);
            } catch (Exception e) {
                // Ici, on ne filtre pas les vraies erreurs transitoires.
            }
        }
        throw new RuntimeException("Inventory down");
    }

    private StockResponse callRemote(UUID productId) {
        return null;
    }
}

Après

resilience4j:
  retry:
    instances:
      inventoryClient:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
        randomizedWaitFactor: 0.25
@Service
public class InventoryClient {

    @Retry(name = "inventoryClient")
    public StockResponse getStock(UUID productId) {
        // Le framework gère les retries de manière plus saine.
        return callRemote(productId);
    }

    private StockResponse callRemote(UUID productId) {
        return null;
    }
}

Idée simple : avec le jitter, les retries ne repartent pas tous exactement au même moment.

Cas 6 — Cache absent

Pourquoi ça pose problème : on lit toujours les mêmes données depuis la base ou depuis une API alors qu’elles changent peu.

Comment résoudre : mémoriser les résultats les plus relus et invalider le cache quand la donnée change.

Avant

@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;

    public ProductDto findById(Long id) {
        // Chaque appel repart en base.
        ProductEntity entity = productRepository.findById(id)
            .orElseThrow();

        return map(entity);
    }
}

Après

@Configuration
@EnableCaching
public class CacheConfig {
    // Active le support du cache Spring.
}
@Service
@RequiredArgsConstructor
public class ProductService {

    private final ProductRepository productRepository;

    @Cacheable(value = "products", key = "#id")
    public ProductDto findById(Long id) {
        // Premier appel : DB
        // Appels suivants : cache
        ProductEntity entity = productRepository.findById(id)
            .orElseThrow();

        return map(entity);
    }

    @CacheEvict(value = "products", key = "#id")
    public void delete(Long id) {
        // Si la donnée change, on invalide le cache.
        productRepository.deleteById(id);
    }
}

Cas 7 — Trop d’appels synchrones en cascade

Pourquoi ça pose problème : la requête attend plusieurs services l’un après l’autre.

Comment résoudre : paralléliser ce qui est indépendant, ou déplacer certains traitements en asynchrone.

Avant

@Service
@RequiredArgsConstructor
public class CheckoutService {

    private final UserClient userClient;
    private final CartClient cartClient;
    private final StockClient stockClient;
    private final PaymentClient paymentClient;

    public CheckoutResponse checkout(Long userId) {
        // Tout est fait séquentiellement.
        UserDto user = userClient.getUser(userId);
        CartDto cart = cartClient.getCart(userId);
        StockDto stock = stockClient.check(cart);
        PaymentDto payment = paymentClient.pay(cart.total());

        return new CheckoutResponse(user, cart, stock, payment);
    }
}

Après

@Service
@RequiredArgsConstructor
public class CheckoutService {

    private final UserClient userClient;
    private final CartClient cartClient;
    private final StockClient stockClient;
    private final PaymentClient paymentClient;
    private final Executor executor;

    public CheckoutResponse checkout(Long userId) {

        // Ces deux appels sont indépendants,
        // donc on peut les lancer en parallèle.
        CompletableFuture<UserDto> userFuture =
            CompletableFuture.supplyAsync(() -> userClient.getUser(userId), executor);

        CompletableFuture<CartDto> cartFuture =
            CompletableFuture.supplyAsync(() -> cartClient.getCart(userId), executor);

        UserDto user = userFuture.join();
        CartDto cart = cartFuture.join();

        // Puis on exécute ce qui dépend du panier.
        StockDto stock = stockClient.check(cart);
        PaymentDto payment = paymentClient.pay(cart.total());

        return new CheckoutResponse(user, cart, stock, payment);
    }
}

Cas 8 — Tracing trop pauvre

Pourquoi ça pose problème : si les logs n'ont pas de traceId ni de spanId, tu vois qu'une requête est lente, mais tu ne sais pas où elle bloque.

Comment résoudre : propager un identifiant de trace entre services, créer des spans autour des étapes importantes et afficher ces identifiants dans les logs.

Avant

@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    public void processOrder() {
        // Log trop pauvre :
        // impossible de relier cet appel
        // aux autres services du parcours.
        log.info("Start request");

        callDb();
        callExternalApi();
    }

    private void callDb() {
        // accès base
    }

    private void callExternalApi() {
        // appel HTTP externe
    }
}

Problème : si callExternalApi() devient lent, tu le verras peut-être dans la latence globale, mais pas clairement dans les logs corrélés entre services.

Après

@Service
@RequiredArgsConstructor
@Slf4j
public class OrderService {

    // Tracer fourni par Micrometer Tracing / Brave / OpenTelemetry
    private final Tracer tracer;

    public void processOrder() {
        // On ouvre un span métier pour suivre cette opération.
        Span span = tracer.nextSpan().name("process-order").start();

        // Le scope injecte le contexte de trace
        // dans les logs et dans les appels suivants.
        try (Tracer.SpanInScope ws = tracer.withSpan(span)) {

            log.info("Processing order");

            // Chaque méthode appelée ensuite peut être reliée
            // à cette même trace.
            callDb();
            callExternalApi();

        } catch (Exception e) {
            // On enrichit la trace avec l'erreur utile au diagnostic.
            span.tag("error", e.getMessage());
            throw e;
        } finally {
            // Toujours fermer le span.
            span.end();
        }
    }

    private void callDb() {
        log.info("Calling database");
    }

    private void callExternalApi() {
        log.info("Calling external API");
    }
}
logging:
  pattern:
    # On affiche l'application, le traceId et le spanId dans chaque log.
    level: "%5p [${spring.application.name},%X{traceId},%X{spanId}]"

Résultat : tu peux suivre une même requête de bout en bout, relier les logs entre microservices et repérer le span le plus lent.

Ce qu’il faut retenir sur le tracing

  • Un log sans traceId aide peu en distribué.
  • Le span décrit une étape précise du traitement.
  • Le bon réflexe : comparer les spans SQL, HTTP externe, cache, broker et application.

Résumé final — symptôme → cause probable → solution

  • p50 bon mais p99 mauvais → cause rare mais coûteuse → tracing, timeout, index, cache, retry plus sain.
  • p50 / p95 / p99 tous mauvais → saturation globale → scaling, pool, SQL, réduction du travail par requête.
  • Beaucoup d’attente → pool saturé ou cascade synchrone → parallélisation, asynchrone, meilleure config.
  • Pics aléatoires → GC, externe lent, DNS, failover → profiler, tracer, réduire les allocations.

Appeler un service distant sans timeout ni gestion d'erreur. Un service qui ne répond jamais bloque indéfiniment le thread appelant et épuise le pool → votre service devient indisponible en cascade (Cascading Failure).

Théorème CAP — et au-delà avec PACELC

En une phrase

Quand deux serveurs ne se parlent plus, il faut choisir entre répondre juste ou répondre vite.

Problème

On ne peut pas avoir les trois en même temps : cohérence, disponibilité, tolérance aux pannes réseau.

À dire à l'oral

CAP ne dit pas "tout est impossible", il dit qu'il faut arbitrer.

Mot-clé

CP · AP · EL · EC

Mid Senior

Le scénario de base 🧸

Imagine deux bibliothèques (Serveur A et Serveur B) qui partagent le même catalogue. Elles se synchronisent par réseau. Un jour, le câble entre les deux est coupé — c'est ça une partition réseau (P). Un étudiant arrive à la bibliothèque A et veut emprunter un livre. Que fait le Serveur A ?

  • Option CP (Cohérence) : "Je refuse, parce que je ne sais pas si le Serveur B vient de prêter le dernier exemplaire."
  • Option AP (Disponibilité) : "Je te le prête quand même, mais je risque de dire oui alors que le livre est déjà pris."

C'est ça le théorème CAP : quand le réseau coupe, on doit choisir entre la vérité (C) et le service (A).

Les trois lettres de CAP

Définitions

LettreNomCe que ça veut dire concrètement
CConsistency (Cohérence)Tous les nœuds renvoient la même donnée au même moment. Si j'écris "stock = 0", tout le monde lit "stock = 0" immédiatement.
AAvailability (Disponibilité)Chaque requête reçoit une réponse (pas d'erreur, pas de timeout), même si la donnée n'est pas parfaitement à jour.
PPartition toleranceLe système continue de fonctionner même si le réseau entre les nœuds est coupé. En réseau réel, les partitions arrivent (câble coupé, switch en panne, datacenter isolé) — on ne peut pas les empêcher.

⚠️ Pourquoi P est inévitable ?

Sur un réseau réel (internet, datacenter, cloud), les pannes réseau arrivent : un switch tombe, un câble est coupé, une zone cloud est isolée. On ne peut pas construire un système distribué qui ignore les partitions. Donc P est toujours dans l'équation, et le vrai choix est : quand P arrive, est-ce que je sacrifie C ou A ?

CAP en une formule

En réseau réel, les partitions (P) finissent toujours par arriver. Quand elles arrivent, on a deux options :

ChoixOn sacrifieConséquenceBon pour
CP la disponibilité (A) On refuse de répondre si on n'est pas sûr que la donnée est à jour Banque, réservation, stock critique
AP la cohérence (C) On répond toujours, même si la donnée est peut-être un peu ancienne Catalogue, fil d'actualité, analytics

PACELC — le complément indispensable

Pourquoi CAP ne suffit pas ?

CAP ne parle que du moment de crise (partition). Mais 99% du temps, le réseau fonctionne. Et même dans ce cas normal, on doit choisir :

  • L (Latency) — je réponds vite, quitte à lire depuis un cache ou un réplica pas encore synchronisé.
  • C (Consistency) — je réponds juste, quitte à attendre que tous les nœuds soient d'accord.

C'est la formule PACELC (Abadi, 2012) :

SI partition → choisir C ou A    (comme CAP)
SINON       → choisir L ou C    (arbitrage du quotidien)

La plupart des systèmes web modernes choisissent PA/EL — rapide et disponible — sauf quand l'argent ou les réservations sont en jeu."

⚙️ Expert — Niveaux de cohérence Cassandra

Cassandra permet de choisir le curseur L ↔ C par requête. C'est PACELC rendu configurable :

// Cassandra Driver Java — choisir le Consistency Level
import com.datastax.oss.driver.api.core.ConsistencyLevel;

SimpleStatement stmt = SimpleStatement
    .builder("SELECT balance FROM accounts WHERE id = ?")
    .setConsistencyLevel(ConsistencyLevel.QUORUM)
    // ONE    → EL : 1 nœud suffit (plus rapide, moins cohérent)
    // QUORUM → entre EL et EC : majorité doit répondre
    // ALL    → EC : tous les nœuds (max cohérence, min vitesse)
    .build();

Row row = session.execute(stmt).one();

Avec N=3 réplicas : QUORUM = 2 nœuds. Écriture QUORUM + Lecture QUORUM garantit la lecture-after-write.

Cas CP — Créer un emprunt (loan-service)

Pourquoi CP : on ne doit jamais prêter un livre qui n'est pas disponible. On préfère refuser (indisponible) que répondre avec une donnée fausse. Si catalog-service ne répond pas, on refuse l'emprunt.

@Service
@RequiredArgsConstructor
public class LoanApplicationService {

    private final CatalogClient catalogClient;
    private final LoanRepository loanRepository;

    public LoanDto createLoan(CreateLoanRequest request) {

        // 1. Vérifier la disponibilité — appel SYNCHRONE obligatoire
        AvailabilityResponse availability;
        try {
            availability = catalogClient
                .getAvailability(request.bookId());
        } catch (FeignException | ResourceAccessException e) {
            // CP : si le service ne répond pas, on REFUSE.
            // On préfère l'indisponibilité temporaire à une donnée fausse.
            throw new ServiceUnavailableException(
                "Impossible de vérifier la disponibilité du livre. "
                + "Réessayez dans quelques instants.", e);
        }

        // 2. Règle métier stricte
        if (!availability.available()) {
            throw new BookNotAvailableException(request.bookId());
        }

        // 3. Réserver le livre (appel synchrone CP)
        catalogClient.reserveBook(
            request.bookId(),
            new ReservationRequest(request.studentId())
        );

        // 4. Créer l'emprunt
        Loan loan = Loan.create(request.bookId(), request.studentId());
        loanRepository.save(loan);
        return LoanMapper.toDto(loan);
    }
}

Idempotence, retries et timeouts

En une phrase

Refaire la même demande ne doit pas créer deux effets métier.

Problème

Les retries peuvent créer des doublons.

À dire à l’oral

Si on retente un POST, on doit avoir une clé d'idempotence.

Mot-clé

Idempotency-Key

Junior Mid Senior

Définition

Une opération idempotente peut être exécutée plusieurs fois sans effet supplémentaire indésirable. Formellement : f(f(x)) = f(x).

  • ✅ GET, PUT, DELETE — idempotents par convention REST.
  • ❌ POST — ne l'est pas nativement → utiliser l'Idempotency-Key.

Côté client — JavaScript

const idempotencyKey = crypto.randomUUID(); // UUID v4 unique par intention

const response = await fetch('/loans', {
  method: 'POST',
  headers: {
    'Content-Type':   'application/json',
    'Idempotency-Key': idempotencyKey   // transmis tel quel à chaque retry
  },
  body: JSON.stringify(loanRequestData)
});

Côté serveur — Spring Boot avec Redis

@PostMapping("/loans")
public ResponseEntity<LoanResponse> create(
        @RequestHeader("Idempotency-Key") String idempotencyKey,
        @Valid @RequestBody CreateLoanRequest request) {

    // 1. Vérifier si la clé a déjà été traitée (Redis)
    Optional<LoanResponse> cached =
        idempotencyStore.findByKey(idempotencyKey);
    if (cached.isPresent()) {
        return ResponseEntity.ok(cached.get());   // même réponse idempotente
    }

    // 2. Verrouillage distribué pour éviter la double exécution concurrent
    //    (race condition si deux retries arrivent en même temps)
    String lockKey = "idempotency-lock:" + idempotencyKey;
    boolean acquired = redisLock.tryLock(lockKey, 5, TimeUnit.SECONDS);
    if (!acquired) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
            .header("Retry-After", "1")
            .build();
    }

    try {
        // Re-check après lock (double-checked locking pattern)
        cached = idempotencyStore.findByKey(idempotencyKey);
        if (cached.isPresent()) return ResponseEntity.ok(cached.get());

        // 3. Traiter la requête
        LoanResponse loan = loanApplicationService.createLoan(request);

        // 4. Persister la réponse pour les éventuels retries
        idempotencyStore.save(idempotencyKey, loan, Duration.ofHours(24));

        return ResponseEntity.status(HttpStatus.CREATED).body(loan);
    } finally {
        redisLock.unlock(lockKey);
    }
}

✅ Stratégie de retry recommandée (AWS Best Practices)

  • Exponential backoff : attendre 100ms, 200ms, 400ms… pour ne pas aggraver une surcharge.
  • Jitter : variation aléatoire ±25% pour éviter le thundering herd.
  • Max retries limité : 3 à 5 maximum.
  • Ne retenter que sur des erreurs transitoires (timeout, 503) — jamais sur un 400 ou 422 (erreur du client).
  • Toujours associer retry + idempotency-key pour les opérations non idempotentes.

Communication synchrone vs asynchrone

En une phrase

Synchrone = j'attends. Asynchrone = je publie puis je continue.

Problème

Le synchrone couple le temps de réponse des services.

À dire à l’oral

REST pour la simplicité, messaging pour le découplage.

Mot-clé

REST / gRPC / Kafka

Ce que tu peux dire à l’oral

“Quand j’ai besoin d’une réponse tout de suite, je prends du synchrone. Quand je veux découpler et absorber de la charge, je passe en asynchrone.”

Choisir entre synchrone et asynchrone n’est pas qu’une question technique : cela change la latence perçue, la robustesse du système, la traçabilité et la manière de raisonner sur la cohérence.

Junior Mid Senior Expert

🔁 Synchrone

L'appelant envoie et attend activement. Le thread est bloqué jusqu'au retour ou timeout.

Exemples : REST/HTTP, gRPC.

✅ Simple, résultat immédiat.
⚠️ Couplage temporel — si le service cible est down, l'appelant échoue aussi.

📨 Asynchrone

L'appelant publie dans un broker et continue immédiatement. Le consommateur traite quand il est prêt.

Exemples : Kafka, RabbitMQ, AWS SQS.

✅ Découplage temporel, résilience, absorption des pics.
⚠️ Cohérence éventuelle, débogage plus complexe.

@Component
public class JwtAuthFilter implements GlobalFilter, Ordered {

    private final ReactiveJwtDecoder jwtDecoder;

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        String authHeader = exchange.getRequest()
                                    .getHeaders()
                                    .getFirst(HttpHeaders.AUTHORIZATION);

        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        String token = authHeader.substring(7);
        return jwtDecoder.decode(token)
            .flatMap(jwt -> {
                // Propager les claims vers les services downstream
                ServerHttpRequest mutated = exchange.getRequest().mutate()
                    .header("X-User-Id",    jwt.getSubject())
                    .header("X-User-Roles", String.join(",", jwt.getClaimAsStringList("roles")))
                    .build();
                return chain.filter(exchange.mutate().request(mutated).build());
            })
            .onErrorResume(e -> {
                exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
                return exchange.getResponse().setComplete();
            });
    }

    @Override public int getOrder() { return -1; }  // avant tous les autres filtres
}

@Component
@RequiredArgsConstructor
public class RateLimitFilter extends OncePerRequestFilter {

    private final BucketProxyManager<String> bucketManager;

    // Limite : 100 req/min par API key
    private final Bandwidth bandwidth = Bandwidth.classic(
        100, Refill.greedy(100, Duration.ofMinutes(1))
    );

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) throws IOException, ServletException {

        String apiKey = request.getHeader("X-Api-Key");
        if (apiKey == null) {
            response.setStatus(HttpStatus.UNAUTHORIZED.value());
            return;
        }

        // Bucket par API key — stocké dans Redis pour la distribution
        Bucket bucket = bucketManager.builder()
            .addLimit(bandwidth)
            .build(apiKey);

        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);

        if (probe.isConsumed()) {
            // Headers standards RFC 6585
            response.addHeader("X-Rate-Limit-Remaining",
                String.valueOf(probe.getRemainingTokens()));
            chain.doFilter(request, response);
        } else {
            long waitSeconds = probe.getNanosToWaitForRefill() / 1_000_000_000;
            response.addHeader("X-Rate-Limit-Retry-After-Seconds",
                String.valueOf(waitSeconds));
            response.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());  // 429
        }
    }
}

@Component
public class SlidingWindowRateLimiter {

    private final StringRedisTemplate redis;
    private static final int MAX_REQUESTS = 100;
    private static final int WINDOW_SECONDS = 60;

    public boolean isAllowed(String clientId) {
        long now = Instant.now().toEpochMilli();
        long windowStart = now - (WINDOW_SECONDS * 1000L);
        String key = "rate-limit:" + clientId;

        // Script Lua atomique — pas de race condition
        String luaScript = """
            local key = KEYS[1]
            local now = tonumber(ARGV[1])
            local window_start = tonumber(ARGV[2])
            local max_requests = tonumber(ARGV[3])
            local window_ms = tonumber(ARGV[4])

            -- Supprimer les entrées hors de la fenêtre
            redis.call('ZREMRANGEBYSCORE', key, 0, window_start)

            -- Compter les requêtes dans la fenêtre
            local count = redis.call('ZCARD', key)

            if count < max_requests then
                redis.call('ZADD', key, now, now)
                redis.call('EXPIRE', key, window_ms / 1000 + 1)
                return 1
            else
                return 0
            end
            """;

        Long result = redis.execute(
            new DefaultRedisScript<>(luaScript, Long.class),
            List.of(key),
            String.valueOf(now),
            String.valueOf(windowStart),
            String.valueOf(MAX_REQUESTS),
            String.valueOf(WINDOW_SECONDS * 1000)
        );

        return Long.valueOf(1L).equals(result);
    }
}

Le script Lua est exécuté de manière atomique par Redis. Pas besoin de verrou distribué car Redis est mono-threadé pour l'exécution des scripts.

// Les événements sont immuables et typés précisément
public sealed interface LoanEvent permits
    LoanRequestedEvent, LoanApprovedEvent, LoanReturnedEvent,
    LoanRenewedEvent, LoanOverdueEvent {}

public record LoanRequestedEvent(
    UUID loanId, UUID studentId, UUID bookId, Instant at) implements LoanEvent {}

public record LoanApprovedEvent(
    UUID loanId, Instant dueDate, Instant at) implements LoanEvent {}

public record LoanReturnedEvent(
    UUID loanId, Instant returnedAt) implements LoanEvent {}

// Agrégat reconstruit depuis les événements
public class Loan {
    private UUID id;
    private LoanStatus status;
    private Instant dueDate;
    private List<LoanEvent> uncommittedEvents = new ArrayList<>();

    // Factory — reconstruction depuis l'event store
    public static Loan reconstitute(List<LoanEvent> events) {
        Loan loan = new Loan();
        events.forEach(loan::apply);
        return loan;
    }

    // Commande — génère des événements
    public void approve(Instant dueDate) {
        if (status != LoanStatus.REQUESTED) {
            throw new IllegalStateException("Loan is not in REQUESTED state");
        }
        LoanApprovedEvent event = new LoanApprovedEvent(id, dueDate, Instant.now());
        apply(event);
        uncommittedEvents.add(event);  // à persister dans l'event store
    }

    // Apply — état interne muté par l'événement
    private void apply(LoanEvent event) {
        switch (event) {
            case LoanRequestedEvent r -> {
                this.id     = r.loanId();
                this.status = LoanStatus.REQUESTED;
            }
            case LoanApprovedEvent a -> {
                this.status  = LoanStatus.APPROVED;
                this.dueDate = a.dueDate();
            }
            case LoanReturnedEvent ignored -> this.status = LoanStatus.RETURNED;
            case LoanRenewedEvent  r       -> this.dueDate = r.newDueDate();
            case LoanOverdueEvent  ignored -> this.status = LoanStatus.OVERDUE;
        }
    }
}

⚙️ Expert — Snapshots pour éviter la reconstruction coûteuse

// Sans snapshot : rejouer 10 000 événements à chaque lecture = lent
// Avec snapshot : rejouer depuis le dernier snapshot seulement

@Component
public class LoanRepository {

    private final EventStore eventStore;
    private final SnapshotStore snapshotStore;
    private static final int SNAPSHOT_THRESHOLD = 50; // snapshot tous les 50 events

    public Loan findById(UUID loanId) {
        // 1. Charger le dernier snapshot (s'il existe)
        Optional<LoanSnapshot> snapshot = snapshotStore.findLatest(loanId);

        long fromVersion = snapshot.map(LoanSnapshot::version).orElse(0L);
        Loan loan = snapshot.map(LoanSnapshot::toLoan).orElseGet(Loan::new);

        // 2. Rejouer uniquement les événements après le snapshot
        List<LoanEvent> events = eventStore.findEventsAfter(loanId, fromVersion);
        events.forEach(loan::apply);

        return loan;
    }

    public void save(Loan loan) {
        long version = eventStore.appendEvents(loan.getId(), loan.getUncommittedEvents());

        // 3. Créer un snapshot si le seuil est atteint
        if (version % SNAPSHOT_THRESHOLD == 0) {
            snapshotStore.save(new LoanSnapshot(loan.getId(), version, loan.toState()));
        }

        loan.clearUncommittedEvents();
    }
}

⚠️ Quand utiliser Event Sourcing ?

L'Event Sourcing est puissant mais complexe. À réserver aux domaines où l'audit et l'historique complet sont critiques (finance, compliance, logistique). Pour un CRUD simple, c'est un over-engineering qui complique tout.

Consumer-Driven Contract Testing

En une phrase

Le consumer décrit ce qu'il attend ; le provider le vérifie.

Problème

Un service peut casser un autre sans le voir.

À dire à l’oral

Le contrat rend les dépendances explicites et testables.

Mot-clé

Pact / contrat

SeniorExpert

Dans un système distribué, comment s'assurer qu'un changement côté provider ne casse pas un consumer ? Le Contract Testing (Pact / Spring Cloud Contract) formalise les attentes des consommateurs en contrats vérifiables automatiquement.

Principe

  1. Le consumer écrit les interactions attendues (requête → réponse).
  2. Ces interactions génèrent un contrat Pact (JSON).
  3. Le provider joue le contrat contre sa vraie implémentation — en CI.
  4. Si le provider casse le contrat, le build échoue avant le déploiement.

Côté Consumer — Test Pact (loan-service → catalog-service)

@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "catalog-service", port = "8081")
class CatalogClientContractTest {

    @Pact(consumer = "loan-service")
    public RequestResponsePact availabilityPact(PactDslWithProvider builder) {
        return builder
            .given("book d290f1ee exists and is available")
            .uponReceiving("GET availability for book d290f1ee")
                .path("/internal/books/d290f1ee-6c54-4b01-90e6-d701748f0851/availability")
                .method("GET")
            .willRespondWith()
                .status(200)
                .headers(Map.of("Content-Type", "application/json"))
                .body(new PactDslJsonBody()
                    .booleanValue("available", true)
                    .integerType("copies", 3))
            .toPact();
    }

    @Test
    @PactTestFor(pactMethod = "availabilityPact")
    void testGetAvailability(MockServer mockServer) {
        CatalogClient client = new CatalogClient(mockServer.getUrl());
        AvailabilityResponse response = client.getAvailability(
            UUID.fromString("d290f1ee-6c54-4b01-90e6-d701748f0851")
        );

        assertThat(response.available()).isTrue();
        assertThat(response.copies()).isEqualTo(3);
    }
}

@PactBroker(url = "http://pact-broker:9292")

        context.setTarget(new HttpTestTarget("localhost", port));

    @TestTemplate
    @ExtendWith(PactVerificationInvocationContextProvider.class)

        context.verifyInteraction(); // rejoue le contrat du consumer

✅ Workflow recommandé en CI/CD

  1. Consumer publie le contrat Pact dans le Pact Broker.
  2. Le pipeline du Provider tire le contrat et joue la vérification.
  3. Le Provider peut être déployé uniquement si can-i-deploy passe (pact-broker can-i-deploy).

Résultat : vous pouvez déployer chaque service indépendamment avec la confiance que les contrats sont respectés.

En pratique

Un système distribué fiable n’est pas celui qui “n’échoue jamais”, mais celui qui rend les échecs visibles, bornés et récupérables.

Checklist architecture

Timeouts, retries contrôlés, idempotence, tracing, contrats, versioning et observabilité doivent être pensés ensemble.

Erreur classique

Multiplier les technos de communication sans raison. Commence simple, puis introduis gRPC ou Kafka quand le besoin est réel.

Ce qu'il faut retenir — Jour 3

  • Chaque appel réseau peut échouer, ralentir ou être dupliqué.
  • Le distribué impose des choix : cohérence, disponibilité, latence.
  • La résilience repose sur timeout, retry maîtrisé, idempotence et observabilité.
  • Le bon choix dépend toujours du besoin métier, pas de la mode technique.

🎯 Le distribué n'est pas un choix gratuit — chaque appel réseau est une source potentielle de panne, de latence et d'incohérence.

⚠️ Les pièges du distribué

  • Les 8 fallacies : le réseau n'est ni fiable, ni rapide, ni gratuit.
  • CAP : en cas de partition, on choisit cohérence OU disponibilité.
  • PACELC : même sans partition, latence vs cohérence.
  • Un retry sans backoff + jitter aggrave les pannes.

🔗 Communication

  • REST : simple, standard, niveaux de maturité Richardson.
  • gRPC : binaire, performant, streaming, contract-first.
  • Kafka : asynchrone, fan-out, absorption de pics, résilience.
  • Idempotence : clé pour les retries sûrs (Idempotency-Key header).

🏗️ Infrastructure

  • API Gateway : point d'entrée unique (auth, routing, rate limit).
  • Service Discovery : Eureka/Consul pour le routage dynamique.
  • Rate Limiting : Token Bucket + Redis pour la protection.
  • Distributed Tracing : Trace ID + Span ID pour le debug.

📋 Bonnes pratiques

  • Versioning d'API : URL path (/v1/) ou header.
  • Contract Testing (Pact) : vérifier les interfaces en CI.
  • Event Sourcing : stocker les événements, pas l'état.
  • Mesurer en percentiles (p99), jamais en moyenne.

Quiz de fin — Jour 3

1. Pourquoi un retry peut-il aggraver un incident ?

Voir la réponse

Si un service est déjà en surcharge, des retries massifs et simultanés empirent la situation : c'est le thundering herd problem. Solution : backoff exponentiel avec jitter pour étaler la charge dans le temps.

2. Dans quel cas le messaging asynchrone est-il préférable à REST ?

Voir la réponse

Quand l'émetteur ne doit pas attendre le récepteur (fire-and-forget), pour absorber des pics de charge, ou quand plusieurs consommateurs doivent réagir au même événement (fan-out). Exemple : après création d'un prêt, déclencher notification + analytics + audit en parallèle.

3. Pourquoi le versioning est-il central dans un système distribué ?

Voir la réponse

Les services sont déployés indépendamment. À un instant T, plusieurs versions d'un même service peuvent coexister. Sans versioning des API et des événements, une mise à jour peut casser les consommateurs encore sur l'ancienne version.

4. Quelle est la différence entre un Trace ID et un Span ID ?

Voir la réponse

Le Trace ID est unique pour l'ensemble de la requête utilisateur, du début à la fin. Un Span ID identifie une étape précise dans cette trace (ex: appel HTTP vers catalog-service). Une trace est composée d'arbres de spans.

5. Quelle "fallacy" du distribué explique qu'on oublie souvent de gérer les timeouts ?

Voir la réponse

La 1ère et la 2ème : "Le réseau est fiable" et "La latence est nulle". En développement local tout fonctionne vite et sans erreur ; on oublie que sur un vrai réseau, les appels peuvent échouer ou prendre un temps arbitraire.

6. Quelle est la différence entre PACELC et CAP ? Donnez un exemple d'application de chaque.

Voir la réponse

CAP raisonne uniquement en cas de partition réseau. PACELC dit que même sans partition, on fait un arbitrage entre latence (L) et cohérence (C). Exemple CAP : choisir CP pour un système bancaire (refuser plutôt que répondre faux). Exemple PACELC : DynamoDB sacrifie la cohérence (EL) pour la basse latence au quotidien.

7. Qu'est-ce que le Consumer-Driven Contract Testing et quel problème résout-il ?

Voir la réponse

Le Consumer-Driven Contract Testing (Pact) permet au consumer de définir les interactions attendues avec un provider sous forme de contrat JSON. Le provider vérifie ce contrat en CI. Cela résout le problème du couplage implicite entre services : on peut déployer indépendamment en ayant la garantie que les interfaces sont respectées.

8. (Expert) Pourquoi le script Lua est-il utilisé pour le Rate Limiting avec Redis ?

Voir la réponse

Redis exécute les scripts Lua de manière atomique — pas d'autre opération n'est exécutée pendant le script. Cela permet de lire le compteur, l'incrémenter et le comparer au seuil en une seule transaction, sans race condition, même avec plusieurs instances de votre service en parallèle.
