Qu’est-ce que l’architecture logicielle ?

L’architecture logicielle est l’ensemble des décisions qui structurent durablement un système : découpage, interactions, responsabilités, flux de données, contraintes et règles d’évolution.

Définition simple

Architecture = comment on organise le système. Design = comment on détaille un morceau. Code = comment on implémente.

Exemple concret

Dans une plateforme e-commerce, décider qu’il existe un module catalogue, un module commande et un module paiement relève de l’architecture. Décider des méthodes d’une classe OrderService relève du design.

Mode enfant

L’architecte dessine le plan de la maison, le designer choisit l’emplacement précis des meubles, le développeur pose réellement les briques.

Mode pro

Une architecture réussie permet des changements métier rapides, des déploiements sûrs, une maintenance prévisible et une maîtrise du coût total de possession.

Qualités logicielles essentielles

QualitéQuestion à se poserExemple
MaintenabilitéEst-ce facile à modifier ?Ajouter un nouveau type d’emprunt sans casser l’existant
ScalabilitéPeut-on absorber plus de charge ?Monter de 1 000 à 20 000 étudiants

SécuritéLes accès et les données sont-ils protégés ?JWT pour API + contrôle de rôles

Bonne pratique

Toute décision architecturale doit se relier à une qualité recherchée. Sinon, elle risque d’être gratuite ou décorative.

Couplage, cohésion et séparation des responsabilités

Un bon système cherche une forte cohésion dans chaque composant et un faible couplage entre composants.

Bonne cohésion

Le composant LoanService s’occupe uniquement des règles d’emprunt.

Couplage excessif

Le contrôleur appelle directement le repository, envoie un mail et calcule les règles métier dans la même méthode.

// Mauvais exemple : trop de responsabilités dans le contrôleur
@PostMapping("/loans")
public ResponseEntity<?> create(@RequestBody LoanRequest request) {{
    // validation manuelle
    // accès BD
    // règles métier
    // envoi de notification
    // mapping de réponse
    return ResponseEntity.ok().build();
}}
// Meilleur exemple : responsabilités séparées
@PostMapping("/loans")
public ResponseEntity<LoanResponse> create(@Valid @RequestBody LoanRequest request) {{
    LoanResponse response = loanApplicationService.createLoan(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(response);
}}

Architecture en couches

Une architecture en couches sépare typiquement présentation, application, domaine et infrastructure.

web/controller  → reçoit HTTP
application     → orchestre les cas d’usage
domain          → porte les règles métier
infrastructure  → base de données, email, broker, clients externes

Mode enfant

La couche web est le guichet, la couche métier décide, la couche infrastructure va chercher les outils et les données.

Mode pro

La séparation réduit l’effet domino des changements, améliore les tests et prépare une évolution vers des patterns plus stricts comme l’hexagonal.

Monolithe vs distribué

CritèreMonolitheSystème distribué
DéploiementSimplePlus complexe
DebugPlus directPlus difficile
Scalabilité cibléeLimitéeMeilleure
LatenceFaible en internePrésente entre services
Autonomie d’équipePlus faiblePlus forte si bien découpé

Attention

Un système distribué n’est pas “plus moderne” par nature. Il déplace des problèmes internes vers le réseau, l’observabilité, la sécurité et l’exploitation.

Exemple Spring Boot commenté

// DTO d'entrée : l'API reçoit un objet simple et validé
public record BookRequest(
    @NotBlank String title,
    @NotBlank String author,
    @Positive int stock
) {{}}
// Contrôleur : rôle = interface HTTP, pas logique métier
@RestController
@RequestMapping("/api/books")
@RequiredArgsConstructor
public class BookController {{

    private final BookApplicationService bookApplicationService;

    @PostMapping
    public ResponseEntity<BookResponse> create(@Valid @RequestBody BookRequest request) {{
        BookResponse created = bookApplicationService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }}
}}
// Service d'application : orchestre le cas d'usage
@Service
@RequiredArgsConstructor
public class BookApplicationService {{

    private final BookRepository bookRepository;
    private final BookMapper bookMapper;

    public BookResponse create(BookRequest request) {{
        Book book = bookMapper.toEntity(request);
        Book saved = bookRepository.save(book);
        return bookMapper.toResponse(saved);
    }}
}}

Bonne pratique

Le service d’application orchestre ; le domaine décide ; l’infrastructure exécute ; le contrôleur expose.

Quiz de fin

  1. Pourquoi la séparation des responsabilités améliore-t-elle la maintenabilité ?
  2. Dans quel cas un monolithe reste-t-il un bon choix ?
  3. Quelle différence entre couplage fort et forte cohésion ?
Corrigé synthétique

Elle limite l’impact d’un changement. Un monolithe est adapté pour une équipe réduite, un domaine simple ou une phase de démarrage. Le couplage concerne les dépendances entre composants ; la cohésion concerne l’unité interne d’un composant.
