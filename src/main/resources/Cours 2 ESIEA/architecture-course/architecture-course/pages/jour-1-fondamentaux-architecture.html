Qu’est-ce que l’architecture logicielle ?

L’architecture logicielle est l’ensemble des décisions difficiles et coûteuses à modifier une fois implémentées. Elle définit la structure du système, la répartition des responsabilités, les flux de données et les règles d’évolution.

La métaphore du bâtiment (Mode enfant)

L’architecte décide où placer les murs porteurs, l'arrivée d'eau et le réseau électrique. Le designer choisit la couleur de la peinture et l'emplacement des meubles. Si la peinture ne plaît pas, c'est facile à changer. Casser un mur porteur est un cauchemar.

La Loi de Conway (Mode pro)

"Les organisations qui conçoivent des systèmes sont contraintes de produire des designs qui sont des copies de la structure de communication de leur organisation." L'architecture technique d'une entreprise est souvent le miroir de son organigramme.

Les Attributs de Qualité (Les "-ilities")

Une architecture ne se juge pas à sa beauté, mais à sa capacité à satisfaire des besoins non-fonctionnels. Or, maximiser une qualité dégrade souvent une autre (Trade-off).

Attribut Question clé Trade-off courant (Le prix à payer)
Maintenabilité Combien de temps pour ajouter une feature sans tout casser ? Demande plus de temps de conception (abstraction, interfaces).
Scalabilité Peut-on absorber 10x plus d'utilisateurs sans ralentir ? Complexifie le système (nécessite du distribué, des caches).
Performance Quel est le temps de réponse sous charge (ex: < 200ms) ? S'oppose souvent à la portabilité ou au code générique.
Sécurité Le système résiste-t-il aux attaques (Zero Trust) ? Dégrade la performance (chiffrement) et l'expérience utilisateur.

Couplage & Cohésion : Le cœur du métier

Le Saint Graal de l'architecte se résume en une phrase : Forte Cohésion et Faible Couplage.

Forte Cohésion (Ce qu'on veut)

Les éléments d'un même module sont fortement liés et ont une vocation unique. (Exemple : Un module Billing ne gère que les factures, pas l'envoi de mails promotionnels).

Couplage Fort (Le danger)

Le changement dans un module A force un changement dans un module B. (Exemple : Si on modifie la table SQL "Users", l'application Mobile crashe car l'API renvoie une erreur).

L'Architecture en Couches (N-Tiers)

Pour réduire le couplage, le standard de l'industrie est l'architecture en couches. La règle d'or est la dépendance unidirectionnelle (une couche supérieure ne peut appeler qu'une couche inférieure).

Flux standard d'une architecture N-Tiers
[ Controller / API ]  → Reçoit la requête HTTP, valide le JSON (Couche Présentation)
       ↓
[ Service Métier ]    → Orchestre la logique, applique les règles (Couche Application)
       ↓
[ Repository / DAO ]  → Traduit l'objet en SQL, gère la BDD (Couche Infrastructure)

Monolithe vs Distribué : Les illusions

Un système distribué (ex: Microservices) n’est pas "mieux" qu'un Monolithe. Il résout des problèmes d'échelle humaine (équipes) au prix d'une immense complexité technique.

Les 8 illusions de l'informatique distribuée (L. Peter Deutsch)

Quand on passe au distribué, les développeurs supposent souvent à tort que :

  • 1. Le réseau est fiable.
  • 2. La latence est nulle.
  • 3. La bande passante est infinie.
  • 4. Le réseau est sûr.
  • 5. La topologie ne change pas.
  • 6. Il y a un seul administrateur.
  • 7. Le coût de transport est nul.
  • 8. Le réseau est homogène.

Implémentation "Clean" avec Spring Boot

Voici comment séparer proprement les responsabilités (DTO, Contrôleur, Service) pour garantir une bonne cohésion.

BookRequest.java (Présentation - Validation)
// DTO d'entrée : l'API reçoit un objet immuable et validé
public record BookRequest(
    @NotBlank(message = "Le titre est obligatoire") String title,
    @NotBlank(message = "L'auteur est obligatoire") String author,
    @Positive(message = "Le stock doit être > 0") int stock
) {}
BookController.java (Présentation - Routage HTTP)
@RestController
@RequestMapping("/api/books")
@RequiredArgsConstructor
public class BookController {

    private final BookApplicationService bookApplicationService;

    @PostMapping
    public ResponseEntity create(@Valid @RequestBody BookRequest request) {
        // Le contrôleur ne fait aucune règle métier. Il délègue.
        BookResponse created = bookApplicationService.create(request);
        return ResponseEntity.status(HttpStatus.CREATED).body(created);
    }
}
BookApplicationService.java (Application - Orchestration)
@Service
@RequiredArgsConstructor
public class BookApplicationService {

    private final BookRepository bookRepository;
    private final BookMapper bookMapper;

    @Transactional
    public BookResponse create(BookRequest request) {
        // 1. Mapping
        Book book = bookMapper.toEntity(request);
        // 2. Règle métier (déléguée au domaine si complexe)
        book.generateIsbn();
        // 3. Persistance
        Book saved = bookRepository.save(book);
        // 4. Retour
        return bookMapper.toResponse(saved);
    }
}

Quiz : Validez vos acquis

  1. Pourquoi maximiser la "Performance" peut-il réduire la "Maintenabilité" ?
  2. Si l'équipe A (Frontend) et l'équipe B (Backend) ne s'entendent pas, quel sera l'impact sur l'API (selon Conway) ?
  3. Pourquoi utiliser un "DTO" (Data Transfer Object) au lieu de renvoyer directement l'Entité JPA/Hibernate dans le contrôleur ?
Voir les réponses détaillées
  • L'optimisation extrême des performances nécessite souvent des hacks de code (cache manuel, requêtes SQL natives complexes, bits manipulation) qui rendent le code très difficile à lire et à maintenir pour les autres développeurs.
  • Selon la loi de Conway, l'API conçue sera probablement chaotique, mal documentée, et l'intégration sera douloureuse, car elle reflétera le manque de communication entre les deux équipes.
  • Renvoyer une Entité JPA crée un couplage fort entre la base de données et l'API publique. Si on ajoute un champ secret en BDD (ex: mot de passe), il risque de fuiter dans l'API. De plus, cela peut causer des problèmes de "Lazy Loading" (boucles infinies JSON).
