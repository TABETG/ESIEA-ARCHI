Patterns d’architecture

Un pattern d’architecture est une manière connue d’organiser un système pour répondre à certains besoins. Il ne s’agit pas d’une vérité universelle mais d’un compromis réutilisable.

HexagonalDomaine au centre, ports/adapters autourTestabilité, isolation du métierDemande de discipline

Hexagonal architecture

Définition simple

Le métier ne dépend pas de la base, du web ou d’un broker. Il expose des ports, et les adapters réalisent les détails techniques.

Mode enfant

Le métier est le cerveau. Les adapters sont les mains et les oreilles. Si on change d’outil, le cerveau garde ses règles.

Mode pro

L’hexagonal aide à découpler le domaine des frameworks et des protocoles. Il facilite les tests métier purs et limite l’enfermement technique.

domain/
  model/
  service/
application/
  port/in/
  port/out/
infrastructure/
  persistence/
  web/
  messaging/
// Port de sortie : le métier exprime son besoin sans connaître JPA
public interface BookPersistencePort {{
    Book save(Book book);
    Optional<Book> findById(UUID id);
}}
// Adapter JPA : détail technique branché sur le port
@Component
@RequiredArgsConstructor
public class BookPersistenceAdapter implements BookPersistencePort {{

    private final SpringDataBookRepository repository;
    private final BookEntityMapper mapper;

    @Override
    public Book save(Book book) {{
        BookEntity entity = mapper.toEntity(book);
        BookEntity saved = repository.save(entity);
        return mapper.toDomain(saved);
    }}
}}

Inversion de dépendance et ports/adapters

L’inversion de dépendance signifie que la logique métier dépend d’abstractions stables, pas d’implémentations instables.

Bonne pratique

Quand tu écris la logique métier, pose-toi la question : “Si je change de base de données ou de protocole, mon code métier doit-il changer ?” Si la réponse est oui, le couplage est trop fort.

DDD de base : bounded context, agrégats, services applicatifs

Le Domain-Driven Design aide à aligner le logiciel sur le langage métier.

Bounded Context

Zone où un mot a un sens précis. “Utilisateur” côté identité n’est pas forcément “lecteur” côté bibliothèque.

Agrégat

Groupe cohérent d’objets métier manipulés de façon consistante, avec une racine d’agrégat.

Exemple

Dans loan-service, l’agrégat Loan garantit qu’un exemplaire ne peut pas être prêté deux fois en même temps.

public class Loan {{
    private final UUID id;
    private final UUID bookId;
    private final UUID studentId;
    private LoanStatus status;

    public void returnBook() {{
        if (status == LoanStatus.RETURNED) {{
            throw new BusinessException("Le prêt est déjà clôturé");
        }}
        this.status = LoanStatus.RETURNED;
    }}
}}
