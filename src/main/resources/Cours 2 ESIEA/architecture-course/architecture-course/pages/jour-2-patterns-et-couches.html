L'Architecture Hexagonale (Ports & Adapters)

L'architecture en couches classique (présentée au Jour 1) a un défaut majeur : le domaine métier finit toujours par dépendre de la base de données (via l'ORM). L'architecture hexagonale résout cela par l'Inversion de Contrôle.

L'analogie de la console (Mode enfant)

Le cœur de l'application est comme une console de jeu. Les "Ports" sont les prises USB. Tu peux y brancher n'importe quelle manette ou écran (les "Adapters"). La console s'en fiche, tant que la prise rentre !

Agnosticisme technique (Mode pro)

Le domaine (le cœur) ne connaît ni Spring, ni SQL, ni le Web. Il expose des Ports (Interfaces). L'infrastructure implémente ces interfaces via des Adapters. Le métier devient 100% testable unitairement sans base de données.

Bases du Domain-Driven Design (DDD)

Inventé par Eric Evans, le DDD est une approche où la structure du code doit correspondre exactement au métier de l'entreprise.

Concept DDD Explication Exemple (Bibliothèque)
Ubiquitous Language Le vocabulaire partagé entre les développeurs et les experts métier. Aucun terme technique. On ne dit pas updateUserStatus() mais suspendLibraryCard().
Bounded Context Une frontière stricte autour d'un modèle métier. Un même mot peut avoir un sens différent selon le contexte. Un "Livre" dans le contexte Catalogue a un résumé et des auteurs. Dans le contexte Inventaire, c'est juste un code barre et un état (emprunté/disponible).
Aggregate Root L'entité principale qui garantit la cohérence des entités enfants lors d'une transaction. L'Emprunt (Aggregate Root) contrôle ses Lignes d'emprunt. On ne sauvegarde pas une ligne seule.

Introduction à CQRS

Le pattern Command Query Responsibility Segregation consiste à séparer complètement les modèles de mise à jour (Command) des modèles de lecture (Query).

Le problème du modèle unique

Dans un monolithe classique, on utilise la même entité JPA pour écrire en base et pour afficher à l'écran. Résultat : on ajoute des champs inutiles au métier juste pour le front-end, et on fait des jointures horribles (N+1 selects) pour l'affichage.

Avec CQRS, on a une BDD (ou des tables) optimisée pour l'écriture de règles métier complexes, et une autre optimisée pour la lecture (ex: ElasticSearch, ou des vues matérialisées SQL).

Implémentation d'un Port et d'un Adapter en Spring

Voyons comment inverser la dépendance vers la base de données.

1. Le Port (Dans le package 'Domain', pas de Spring ici)
public interface BookRepositoryPort {
    Optional findById(BookId id);
    void save(Book book);
}
2. Le Cas d'Usage (Dans le package 'Domain')
public class BorrowBookUseCase {

    // Le domaine dépend de l'interface, pas de l'implémentation !
    private final BookRepositoryPort bookRepository;

    public BorrowBookUseCase(BookRepositoryPort bookRepository) {
        this.bookRepository = bookRepository;
    }

    public void execute(BookId bookId) {
        Book book = bookRepository.findById(bookId)
            .orElseThrow(() -> new BookNotFoundException(bookId));

        book.borrow(); // Logique purement métier
        bookRepository.save(book);
    }
}
3. L'Adapter (Dans le package 'Infrastructure', lié à Spring/JPA)
@Repository
@RequiredArgsConstructor
public class JpaBookRepositoryAdapter implements BookRepositoryPort {

    private final SpringDataJpaBookRepository springRepository;
    private final BookEntityMapper mapper;

    @Override
    public void save(Book book) {
        // L'Adapter fait la traduction entre le Domaine pur et la BDD
        JpaBookEntity entity = mapper.toJpaEntity(book);
        springRepository.save(entity);
    }
    // ...
}

Dossier d’architecture : Rédiger un ADR

Les choix architecturaux doivent être documentés sous forme d'Architectural Decision Records (ADR). Voici ce que vous devrez produire pour le TP.

Exemple d'ADR pour le projet fil rouge

  • Titre : Adoption d'une Architecture Hexagonale Allégée
  • Contexte : Le monolithe de la bibliothèque commence à mélanger code métier et requêtes SQL. Les tests unitaires sont impossibles sans lancer un conteneur de base de données.
  • Décision : Nous introduisons le pattern Ports & Adapters pour le module Emprunt (cœur métier). Le module Catalogue (essentiellement de la lecture/affichage) restera en CRUD basique (CQRS léger).
  • Conséquences :
    + Le domaine Emprunt est testable en millisecondes.
    - Ajout de classes intermédiaires (Mappers, Interfaces), courbe d'apprentissage pour l'équipe.

Quiz : Validez vos acquis

  1. Pourquoi l’architecture hexagonale est-elle souvent jugée "trop coûteuse" au démarrage ?
  2. Qu'est-ce qu'un "Bounded Context" dans le DDD ?
  3. Si je veux afficher une page web qui regroupe les données de 5 tables différentes, pourquoi CQRS est-il utile ?
Voir les réponses détaillées
  • Elle nécessite d'écrire beaucoup de code "boilerplate" : des interfaces pour les ports, des classes d'adapters, et surtout des Mappers pour traduire les entités du Domaine vers les entités JPA de la base de données. C'est un surcoût initial pour un gain à long terme.
  • C'est une frontière explicite dans laquelle un modèle métier (et son vocabulaire) est strictement défini. Cela évite d'avoir une classe géante `Utilisateur` qui contient à la fois les données d'authentification, les factures et les préférences de notification.
  • Au lieu de forcer le domaine métier à faire des jointures complexes qui n'ont aucun sens métier (uniquement pour l'affichage), CQRS permet de créer un modèle de lecture (Query) dédié. Par exemple, une simple vue SQL ou un document NoSQL pré-calculé, mis à jour par des événements.
