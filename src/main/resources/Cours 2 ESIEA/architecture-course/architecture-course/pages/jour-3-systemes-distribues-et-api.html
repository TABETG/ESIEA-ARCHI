Qu’est-ce qu’un système distribué ?

Un système distribué est un ensemble de composants exécutés sur plusieurs processus ou machines qui collaborent pour rendre un service unique à l’utilisateur.

Mode enfant

Au lieu d’avoir une seule grosse boutique, tu ouvres plusieurs petits magasins spécialisés qui doivent se parler correctement.

Mode pro

Le distribué introduit latence, pannes partielles, duplication de données, cohérence asynchrone, sécurité réseau et complexité opérationnelle. Il apporte en échange autonomie, scalabilité ciblée et alignement avec plusieurs équipes.

Latence réseau et pannes partielles

Dans un monolithe, un appel de méthode échoue vite et localement. Dans un système distribué, un appel réseau peut être lent, se perdre, être dupliqué ou échouer après traitement partiel.

Attention

Le réseau n’est ni instantané ni fiable. Cette phrase doit devenir un réflexe architectural.

// Exemple OpenFeign côté loan-service
@FeignClient(name = "catalog-service")
public interface CatalogClient {{

    @GetMapping("/internal/books/{bookId}/availability")
    AvailabilityResponse getAvailability(@PathVariable UUID bookId);
}}

Erreur fréquente

Appeler un service distant comme si c’était une méthode locale, sans timeout ni gestion d’erreur.

CAP : cohérence, disponibilité, partitionnement

Le théorème CAP rappelle qu’en présence de partition réseau, on ne peut pas garantir simultanément cohérence forte et disponibilité totale.

ChoixConséquenceExemple
Favoriser cohérenceOn refuse certaines requêtes si le doute existeSolde bancaire critique
Favoriser disponibilitéOn répond parfois avec une donnée pas encore fraîcheCatalogue de produits

Exemple concret

Afficher un stock légèrement retardé sur un catalogue est souvent acceptable. Débiter deux fois une carte ne l’est pas.

Idempotence, retries et timeouts

Définition simple

Une opération idempotente peut être rejouée plusieurs fois sans effet supplémentaire indésirable.

// Idée : un identifiant de requête empêche les doublons
@PostMapping("/loans")
public ResponseEntity<LoanResponse> create(
        @RequestHeader("Idempotency-Key") String idempotencyKey,
        @Valid @RequestBody CreateLoanRequest request) {{
    return ResponseEntity.status(HttpStatus.CREATED)
            .body(loanApplicationService.createLoan(idempotencyKey, request));
}}

Bonne pratique

Utiliser retries uniquement sur des erreurs transitoires, avec backoff, et de préférence sur des opérations idempotentes.

Sérialisation et versioning d’API

Quand on distribue un système, on échange des contrats. Le contrat doit être stable, documenté et versionné.

Exemple de versioning

/api/v1/books pour l’API publique, ou versioning par header pour des usages plus avancés. Pour les événements, on documente le schéma et on évite les ruptures brutales.

Attention

Renommer un champ JSON “innocent” peut casser un autre service déployé à un rythme différent.
