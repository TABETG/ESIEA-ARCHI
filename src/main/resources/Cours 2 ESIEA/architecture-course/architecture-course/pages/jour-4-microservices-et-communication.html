Principes microservices

Le microservice n’est pas “un petit projet Spring Boot”. C’est une unité de déploiement et d’évolution autonome centrée sur une capacité métier.

Mode enfant

Au lieu d’une seule grande cuisine, tu as plusieurs cuisines spécialisées : dessert, pain, plats chauds. Chacune a son équipe et ses outils.

Mode pro

Les microservices cherchent à réduire la coordination entre équipes, aligner code et domaine, et permettre un scaling différencié. Ils ne sont rentables qu’avec une maturité d’exploitation suffisante.

Découpage fonctionnel

On découpe par capacités métier cohérentes, pas par couches techniques globales.

❌ Mauvais découpage
user-controller-service
user-repository-service
notification-repository-service

✅ Découpage métier
catalog-service
loan-service
identity-service
notification-service

Bonne pratique

Un microservice doit posséder son modèle et ses données sur son périmètre. Éviter la base partagée quand on veut une vraie autonomie.

          predicates:

Communication REST et événementielle

REST

Bon pour une réponse immédiate. Exemple : vérifier si un livre est disponible avant de créer un prêt.

Événementiel

Bon pour diffuser un fait métier. Exemple : après création du prêt, envoyer “loan-created” pour déclencher une notification.

Orchestration, chorégraphie, sagas et transactions distribuées

Dans un monolithe, une transaction locale suffit souvent. Dans le distribué, on travaille souvent avec cohérence éventuelle.

Exemple de saga d'emprunt
1. loan-service crée un prêt en statut PENDING
2. catalog-service réserve l'exemplaire
3. identity-service valide le profil étudiant
4. loan-service passe le prêt à CONFIRMED
5. si une étape échoue, compensation : annuler la réservation

Attention

Les transactions distribuées bloquantes à travers plusieurs services sont rarement une bonne idée dans les architectures modernes généralistes.

Anti-patterns microservices fréquents

  • Distributed Monolith : services séparés mais fortement couplés et déployés ensemble.
  • Chatty Communication : trop d’appels réseau pour un seul cas d’usage.
  • Shared Database : plusieurs services écrivent les mêmes tables.
  • Nano-services : découpage trop fin, coût opérationnel énorme.
  • Everything async : sur-utilisation de l’événementiel sans besoin réel.
