Jour 1 : Fondamentaux de l'Architecture

Notion 1.1 : Qualités Logicielles (Scalabilité & Disponibilité)

1. Définition : Les qualités logicielles (ou exigences non-fonctionnelles) définissent comment le système opère, plutôt que ce qu'il fait. La scalabilité est la capacité à absorber plus de charge. La disponibilité est la probabilité que le système soit opérationnel à un instant T.
2. Pourquoi c'est utile : Le code le plus propre du monde ne sert à rien si l'application s'effondre le jour du Black Friday ou si une mise à jour nécessite 4 heures de coupure.
3. Exemple concret : Netflix. S'ils déploient une nouvelle fonctionnalité de recommandation, cela ne doit pas empêcher les utilisateurs de lancer une vidéo (Priorité à la disponibilité sur la cohérence des données).
4. Mode enfant : Imagine un supermarché. La "scalabilité", c'est pouvoir ouvrir 10 caisses de plus quand il y a du monde. La "disponibilité", c'est s'assurer que le magasin ne ferme jamais, même si l'alarme incendie sonne dans un rayon.
5. Mode pro : La disponibilité se calcule souvent avec la formule du MTBF (Mean Time Between Failures) et du MTTR (Mean Time To Recovery). En architecture, on vise souvent les "4 nines" (99.99% d'uptime), ce qui signifie que l'architecture doit garantir que le système ne sera pas en panne plus de 52 minutes par an.

Formule mathématique de la disponibilité ($A$) : $$A = \frac{MTBF}{MTBF + MTTR}$$ L'architecte doit donc concevoir des systèmes qui réduisent le $MTTR$ (réparation rapide via auto-scaling ou redémarrage automatique).
6. Exemple technique : Le Load Balancing (répartition de charge). Un répartiteur reçoit 1000 requêtes HTTP et les distribue sur 5 instances de l'application Spring Boot.
7. Exemple de configuration (YAML) : 
# Configuration Kubernetes d'auto-scaling (HPA)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service-hpa
spec:
  minReplicas: 2 # Toujours au moins 2 instances (Disponibilité)
  maxReplicas: 10 # Jusqu'à 10 si forte charge (Scalabilité)
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80 # Scale up si CPU > 80%
8. Erreurs fréquentes : Penser que la scalabilité résout les problèmes de performance. Si une requête SQL met 5 secondes car il manque un index, ajouter 10 serveurs (scalabilité) ne fera que saturer la base de données 10 fois plus vite.
9. Bonnes pratiques : Concevoir des applications "Stateless" (sans état). Ne stockez jamais la session utilisateur dans la RAM du serveur web, sinon ce serveur ne peut pas être détruit/remplacé sans déconnecter l'utilisateur. Utilisez Redis pour les sessions.
10. Mini Quiz : Si mon application web crash toutes les 2 heures, mais redémarre instantanément en 1 seconde sans que l'utilisateur s'en aperçoive. Mon application a-t-elle une bonne scalabilité ou une bonne disponibilité ?
(Réponse : Une excellente disponibilité, même si la fiabilité est mauvaise).

Notion 1.2 : Couplage et Cohésion (Inversion de Dépendance)

1. Définition : Le couplage est le degré de dépendance entre deux modules. La cohésion est la force avec laquelle les responsabilités d'un module sont liées. Le Graal : Couplage faible, Cohésion forte.
2. Pourquoi c'est utile : Un couplage faible permet de modifier, tester et déployer une partie du système sans casser le reste.
3. Exemple concret : Une prise électrique. Ton chargeur d'ordinateur est "faiblement couplé" à la centrale nucléaire. La prise murale est une interface. Si EDF passe de l'énergie nucléaire à l'éolien, tu n'as pas besoin de racheter un chargeur.
4. Mode enfant : Si tes lacets de chaussures sont attachés ensemble (fort couplage), tu vas tomber en marchant. Si chaque lacet est attaché à sa propre chaussure (forte cohésion), tu peux courir.
5. Mode pro : L'inversion de dépendance (le 'D' de SOLID) dicte que les modules de haut niveau (Règles métier) ne doivent pas dépendre des modules de bas niveau (BDD, API). Les deux doivent dépendre d'abstractions (Interfaces).
6. Exemple technique : Ne pas instancier directement une classe technique dans un service métier. Utiliser l'injection de dépendance via le constructeur.
7. Code commenté : 
package com.myapp.domain;

// L'Interface appartient au domaine (haut niveau)
public interface PaymentGateway {
    void processPayment(Order order);
}

@Service
public class OrderCheckoutService {
    private final PaymentGateway paymentGateway;

    // Injection via constructeur (Faible couplage)
    // Le service ne sait pas si c'est Stripe, Paypal ou un Mock de test !
    public OrderCheckoutService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }

    public void checkout(Order order) {
        paymentGateway.processPayment(order);
    }
}
8. Erreurs fréquentes : Utiliser des variables globales, des Singletons codés en dur, ou passer le contexte HTTP (HttpServletRequest) directement dans la couche métier.
9. Bonnes pratiques : Si vous ne pouvez pas écrire un test unitaire de votre classe métier sans lever une base de données de test, votre code est trop couplé. Mockez les interfaces !
10. Mini Quiz : Quel design pattern est utilisé nativement par le framework Spring pour résoudre le problème de couplage fort ?
(Réponse : Dependency Injection / IoC Container).

Jour 2 : Patterns d'Architecture & DDD

Notion 2.1 : L'Architecture Hexagonale (Ports & Adapters)

1. Définition : Une architecture qui place le domaine métier au centre absolu. Elle isole ce cœur de tout mécanisme de livraison (Web, Console) et de toute infrastructure (BDD, API externes) via des "Ports" (Interfaces) et des "Adapters" (Implémentations).
2. Pourquoi c'est utile : Elle retarde les choix techniques. Vous pouvez commencer à coder et tester tout le métier d'une application bancaire pendant 3 mois, avant même d'avoir décidé si vous utiliserez PostgreSQL ou MongoDB.
3. Exemple concret : Le port USB de votre ordinateur. Le "Port" définit la forme du connecteur. L'"Adapter" est la clé USB, la souris ou le clavier que vous branchez. L'ordinateur (le métier) n'a pas besoin de savoir à l'avance ce que vous allez brancher.
4. Mode enfant : C'est comme un château fort avec le roi au milieu (le métier). Le roi ne sort jamais. Pour parler aux paysans (Base de données) ou aux marchands (Utilisateurs Web), il utilise des messagers (Ports). Si un messager change, le roi s'en moque, il donne toujours les mêmes ordres.
5. Mode pro : Les dépendances pointent toujours vers l'intérieur. L'infrastructure dépend du domaine, mais le domaine ne dépend de RIEN. Cela évite le syndrome du Vendor Lock-in (être prisonnier d'un framework ou d'un ORM comme Hibernate).
6. Exemple technique : Un "Port d'Entrée" (Driving Port) est une interface appelée par le contrôleur REST. Un "Port de Sortie" (Driven Port) est une interface implémentée par le Repository JPA.
7. Code commenté : 
/* ---------------------------------
   COUCHES DOMAINE (AUCUNE ANNOTATION SPRING/JPA ICI)
   --------------------------------- */
package hex.domain.ports;

// Port Sortant (Driven Port)
public interface AccountRepository {
    Account findById(String accountId);
    void save(Account account);
}

/* ---------------------------------
   COUCHE INFRASTRUCTURE (ADAPTERS)
   --------------------------------- */
package hex.infrastructure.adapters;

@Repository
public class JpaAccountAdapter implements AccountRepository {
    private final SpringDataJpaRepo db; // Dépendance à Spring

    @Override
    public Account findById(String id) {
        return db.findById(id).map(entity -> mapper.toDomain(entity)).orElseThrow();
    }
}
8. Erreurs fréquentes : Renommer son architecture "Hexagonale" mais laisser des imports `javax.persistence.*` ou `org.springframework.*` dans la couche `domain`. C'est une violation stricte du pattern.
9. Bonnes pratiques : Utilisez des objets du domaine purs (POJO en Java) et utilisez des Mappers explicites pour transformer vos Entités JPA en Objets de Domaine avant qu'ils ne rentrent dans le centre de l'hexagone.
10. Mini Quiz : Dans une architecture hexagonale, qui définit le contrat (l'interface) d'accès à la base de données : la couche Infrastructure ou la couche Domaine ?
(Réponse : La couche Domaine. L'infrastructure ne fait que s'y conformer).

Jour 3 : Systèmes Distribués

Notion 3.1 : Le Théorème CAP & Pannes Réseaux

1. Définition : Dans tout système distribué stockant des données, il est impossible de garantir simultanément ces 3 propriétés : Cohérence (C), Disponibilité (A), et Tolérance au Partitionnement (P). Il faut en choisir deux.
2. Pourquoi c'est utile : Cela force les architectes à arrêter de chercher la solution parfaite et à prendre des décisions basées sur les exigences métiers. Préfère-t-on bloquer un client ou risquer d'avoir un léger décalage de stock ?
3. Exemple concret : Le distributeur de billets. Le réseau avec la banque centrale est coupé (Partition). Choix CP : Le distributeur affiche "Hors service" (Dispo sacrifiée) pour garantir que votre solde est exact. Choix AP : Le distributeur vous laisse retirer 50€ max (Cohérence sacrifiée) en notant la transaction hors-ligne pour plus tard, pour garantir le service client.
4. Mode enfant : Tu joues au téléphone arabe avec 3 amis dans 3 pièces différentes. Si les portes se ferment (Partition), vous ne pouvez plus vous parler. Soit vous arrêtez de jouer (CP, vous attendez d'être sûrs), soit vous inventez la suite de l'histoire chacun de votre côté pour continuer à jouer, mais à la fin l'histoire sera différente (AP).
5. Mode pro : Sur les réseaux informatiques géographiquement répartis, le 'P' (Partition) va inévitablement se produire (Split-Brain syndrome). Le choix architectural réel n'est donc pas entre C, A et P, mais entre CP et AP lors d'une partition réseau. Cassandra est typiquement AP (Eventual Consistency), PostgreSQL configuré en multi-noeud strict est CP.
6. Exemple technique : Le concept de Eventual Consistency (Cohérence à terme). Au lieu d'utiliser une transaction distribuée bloquante, on accepte le changement localement et on émet un événement Kafka pour synchroniser les autres bases de données avec quelques millisecondes de retard.
7. Code commenté : 
// Implémentation de la "Cohérence Éventuelle" via Asynchronisme
@Service
public class OrderService {
    private final KafkaTemplate<String, OrderEvent> kafka;

    @Transactional
    public void createOrder(Order order) {
        // 1. Écriture locale très rapide (Favorise A - Availability)
        orderRepo.save(order);

        // 2. Envoi d'un message au système de facturation (Fire & Forget)
        // Le système de facturation sera à jour d'ici quelques ms/secondes (Favorise AP)
        kafka.send("orders-topic", new OrderEvent(order.getId()));
    }
}
8. Erreurs fréquentes : Vouloir recréer des transactions ACID classiques sur plusieurs bases de données de microservices distants via le protocole Two-Phase Commit (2PC). C'est le meilleur moyen de paralyser tout votre système à la moindre lenteur réseau.
9. Bonnes pratiques : Dans un système distribué, embrassez l'asynchronisme. Utilisez le pattern SAGA pour gérer les transactions longues avec des étapes de compensation (si l'étape 3 échoue, j'annule explicitement l'étape 1 et 2 via des requêtes contraires).
10. Mini Quiz : Amazon vous laisse mettre un article dans votre panier même si leur base de données centrale d'inventaire est momentanément injoignable. Quel côté du théorème CAP ont-ils favorisé ?
(Réponse : AP - Availability and Partition tolerance, quitte à vous envoyer un email 1h plus tard pour dire "Désolé, rupture de stock").
