Architecture Logicielle & Systèmes Distribués

Ce cours est conçu pour des étudiants de niveau Master 2. L'objectif n'est pas d'apprendre à coder, mais d'apprendre à concevoir. Nous allons passer d'une vision locale (comment écrire une fonction) à une vision globale (comment faire communiquer des dizaines de services sans que le système s'effondre).

🎯 Objectifs Pédagogiques

  • Comprendre les enjeux de l'architecture logicielle face aux besoins métiers.
  • Maîtriser les différents styles d'architecture (Monolithe, Clean, Microservices).
  • Appréhender les contraintes des systèmes distribués (Théorème CAP, réseaux faillibles).
  • Savoir sécuriser, monitorer et rendre résilient un écosystème complexe.
  • Être capable de justifier ses choix via un Dossier d'Architecture Technique (DAT).

Le mantra de l'architecte

"En architecture, il n'y a pas de bonnes ou de mauvaises réponses. Il n'y a que des compromis (Trade-offs)."

Jour 1 : Les Fondamentaux de l'Architecture

1. Qu'est-ce que l'Architecture Logicielle ?

Définition

L'architecture logicielle est l'ensemble des décisions de conception fondamentales concernant un système, qui sont les plus difficiles (et coûteuses) à modifier une fois implémentées.

👶 Mode Enfant

Imagine que tu construis une maison en briques (Lego). L'architecture, c'est décider où mettre les murs porteurs et les tuyaux d'eau. Si tu te trompes sur la couleur du canapé (le code), tu peux la changer demain. Si tu oublies de mettre des tuyaux d'eau dans les murs, tu vas devoir tout casser pour réparer ton erreur. L'architecte s'occupe des tuyaux et des murs porteurs.

👔 Mode Pro

L'architecture est la traduction technique des Exigences Non-Fonctionnelles (NFRs). Le métier demande qu'un calcul de panier soit juste (Fonctionnel), mais l'architecte s'assure que ce calcul puisse se faire pour 100 000 utilisateurs simultanés avec un temps de réponse < 200ms et une disponibilité de 99.99% (Non-Fonctionnel).

2. Qualités Logicielles (Les "Ilities")

Une bonne architecture se juge sur ces critères principaux :

  • Maintenabilité : Le code est-il facile à faire évoluer pour de nouveaux développeurs ?
  • Scalabilité : Le système peut-il gérer plus de charge en ajoutant du matériel (Vertical) ou des serveurs (Horizontal) ?
  • Disponibilité (Availability) : Le système est-il résistant aux pannes ? (Mesuré en "Nines" : 99.9% d'uptime = ~8h de panne par an).
  • Sécurité : Les données sont-elles protégées contre les accès non autorisés ?

3. Couplage et Cohésion

C'est la règle d'or de la conception : Faible Couplage (Low Coupling), Forte Cohésion (High Cohesion).

💡 Exemple Concret

  • Forte Cohésion : La classe `Facture` gère le total, la TVA et les remises. Elle ne s'occupe PAS d'envoyer un email. Tout ce qui la compose a du sens ensemble.
  • Faible Couplage : Le module "Paiement" communique avec le module "Facturation" via une interface simple, sans connaître les détails internes de sa base de données.

⚠️ Erreur Fréquente

Créer des classes "God Object" (ex: SystemManager) qui font tout : base de données, logique métier, et formattage d'affichage. Cela crée une forte cohésion technique (tout le code est au même endroit), mais une cohésion métier catastrophique.

4. Séparation des Responsabilités (Separation of Concerns)

L'architecture en couches (Layered Architecture) est l'approche classique :

[ UI / Web Layer ] <-- Contrôleurs REST, Vues ↓ [ Business Layer ] <-- Logique Métier, Services ↓ [ Data Access ] <-- Repositories, ORM, SQL ↓ [ Database ] <-- MySQL, PostgreSQL

💻 Live Coding : Monolithe vs Distribué

Code Java (Spring) - Exemple de fort couplage à éviter :

@Service
public class OrderService {
    // ❌ MAUVAIS : Instanciation directe, couplage fort à l'implémentation H2
    private H2DatabaseConnection db = new H2DatabaseConnection();

    public void createOrder(Order order) {
        db.insert(order);
    }
}

Correction (Inversion de Contrôle / Injection de Dépendance) :

@Service
public class OrderService {
    // ✅ BON : Couplage faible via une Interface. Spring injectera l'implémentation.
    private final OrderRepository repository;

    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public void createOrder(Order order) {
        repository.save(order);
    }
}

Jour 2 : Patterns d'Architecture et DDD

1. Les limites de l'architecture en couches classique

Dans l'architecture vue au Jour 1, le Métier dépend de la base de données. Si on change la BDD, on impacte le métier. C'est le problème que résolvent l'Architecture Hexagonale, la Clean Architecture (Uncle Bob) et l'Onion Architecture.

2. L'Architecture Hexagonale (Ports & Adapters)

Définition

Le principe est de placer la logique métier pure au centre du système. Les dépendances vont de l'extérieur (Web, BDD) vers l'intérieur (Métier). Le métier ne dépend de rien (Inversion de Dépendance).

👶 Mode Enfant

Ton cerveau (le métier) sait comment faire une addition. Qu'on te pose la question à l'oral (API REST), sur un papier (Fichier Excel), ou par SMS (RabbitMQ), ton cerveau s'en moque. Il fait juste l'addition. L'architecture hexagonale, c'est mettre des "traducteurs" (Adapters) autour de ton cerveau pour qu'il ne se concentre que sur les maths.
[ REST Adapter ] (Primary/Driving) ↓ appelle [ PORT IN ] (Interface Java) ↓ implémente (( DOMAINE MÉTIER )) <-- Ne connaît RIEN de Spring ou du Web ↓ appelle [ PORT OUT ] (Interface Java) ↓ implémente [ SQL Adapter ] (Secondary/Driven)

3. Domain-Driven Design (DDD) - Les Bases

Le DDD aligne le code sur la réalité du métier.

  • Ubiquitous Language : Développeurs et experts métiers utilisent les mêmes mots. Si le métier dit "Panier", on ne code pas `CartManager`, on code `Panier`.
  • Bounded Context : Un même mot peut avoir des sens différents. Un "Produit" pour l'équipe Vente (prix, description) n'a pas les mêmes propriétés qu'un "Produit" pour l'équipe Logistique (poids, dimensions). On sépare ces contextes.
  • Entité vs Value Object : Une Entité a une identité (ex: User avec un ID). Un Value Object n'en a pas (ex: une adresse postale. Deux adresses "10 rue de Paris" sont strictement identiques, on s'en fiche de leur ID).

DTO, Mapper et Repository

Ne sortez jamais une Entité JPA au niveau de votre contrôleur REST. Utilisez un DTO (Data Transfer Object) pour maîtriser ce qui est exposé (pour éviter d'exposer un mot de passe hashé par exemple).

💻 Live Coding : Mapper avec MapStruct

// 1. L'Entité interne (JPA - Infrastructure)
@Entity
public class UserEntity {
    private Long id;
    private String passwordHash;
    private String email;
}

// 2. Le DTO exposé (Web)
public record UserResponseDto(String email) {}

// 3. Le Mapper (MapStruct)
@Mapper(componentModel = "spring")
public interface UserMapper {
    UserResponseDto toDto(UserEntity entity);
}

Jour 3 : Fondamentaux des Systèmes Distribués

1. Qu'est-ce qu'un système distribué ?

Définition

Un système distribué est un ensemble d'ordinateurs indépendants qui apparaissent à l'utilisateur comme un système unique. Ils communiquent par passage de messages sur un réseau.

⚠️ Les 8 fausses croyances du réseau (Fallacies of distributed computing)

En passant d'un monolithe à du distribué, les juniors pensent que : 1. Le réseau est fiable (Faux : des câbles sont coupés, des switchs rebootent). 2. La latence est nulle (Faux : la lumière met du temps à traverser l'Atlantique). 3. La bande passante est infinie (Faux). 4. Le réseau est sécurisé (Faux). ...

2. Le Théorème CAP (Crucial)

Proposé par Eric Brewer. Dans un système distribué, vous ne pouvez choisir que 2 propriétés parmi 3 :

  • C (Consistency - Cohérence) : Tous les nœuds voient la même donnée en même temps.
  • A (Availability - Disponibilité) : Le système répond toujours, même si certains nœuds sont en panne.
  • P (Partition Tolerance - Tolérance au partitionnement) : Le système continue de fonctionner même si la communication réseau entre les nœuds est coupée.

👔 Mode Pro : La réalité de CAP

Sur internet, le "Partitionnement" (P) n'est pas un choix, c'est une fatalité (le réseau plantera). Donc, vous devez toujours choisir entre CP (Cohérence forte, ex: Base de données bancaire) ou AP (Disponibilité forte, ex: Flux Twitter, Panier Amazon).

3. Idempotence, Retries et Timeouts

Si le réseau coupe, votre requête HTTP a peut-être échoué, ou bien la réponse a été perdue. Que faire ? On recommence (Retry).

💡 L'importance de l'Idempotence

Une API est idempotente si l'appeler 1 fois ou 100 fois produit le même résultat côté serveur.
- DELETE /users/1 : Idempotent. (Le user 1 est supprimé. Si je rappelle, il est toujours supprimé).
- POST /transfer?amount=100 : NON Idempotent. (Si je retry suite à un timeout réseau, je risque de virer 200€ au lieu de 100€).
Solution : Utiliser des UUID de corrélation (ex: Idempotency-Key dans le Header).

4. Synchrone vs Asynchrone

  • Synchrone (REST, gRPC) : Le client bloque et attend la réponse. Facile à coder, mais couplage temporel fort (si B est lent, A devient lent).
  • Asynchrone (Messaging, Kafka, RabbitMQ) : Le client poste un message dans un Broker et continue sa vie (Fire and Forget). Idéal pour les systèmes résilients.

Jour 4 : Microservices et Communication Inter-services

1. Principes des Microservices

Un microservice est un service déployable indépendamment, centré sur un seul domaine métier (Bounded Context), avec sa propre base de données.

👶 Mode Enfant

Le monolithe, c'est un couteau suisse : ça fait tout, mais c'est lourd dans la poche. Les microservices, c'est une caisse à outils avec un marteau, un tournevis, une scie. Si le marteau se casse, tu peux toujours scier. Et tu peux confier le marteau à Pierre, et la scie à Paul.

2. Les Composants Critiques de l'Écosystème

  • API Gateway : Le point d'entrée unique. Gère le routage, la sécurité (JWT), le Rate Limiting. Le front-end ne connaît pas les microservices, il ne connaît que la Gateway.
  • Service Discovery (ex: Eureka, Consul) : L'annuaire. Les services s'enregistrent dynamiquement car dans le cloud, les adresses IP changent tout le temps.
  • Configuration Distribuée : Centraliser les fichiers application.yml dans un repo Git.

3. Transactions Distribuées : Le Pattern Saga

Dans un monolithe, vous faites un @Transactional. Dans les microservices, avec 3 bases de données différentes, c'est impossible (le protocole 2PC est trop lent).

Le Pattern SAGA

Une transaction métier longue est découpée en transactions locales. Si une étape échoue, on déclenche des transactions de compensation (l'équivalent d'un "Undo") pour annuler les étapes précédentes.
[ Service Commande ] --(Créée)--> [ Service Stock ] --(Réservé)--> [ Service Paiement ] (Échec: Solde Insuffisant) | v [ Service Stock ] <--(Compensation : Libérer Stock) | v [ Service Commande ] <--(Compensation : Commande Annulée)

⚠️ Anti-Pattern : Le Monolithe Distribué

Si vos microservices communiquent massivement en REST synchrone les uns avec les autres de manière circulaire, vous avez créé un Monolithe Distribué. Vous combinez la complexité du réseau avec l'inflexibilité du monolithe. C'est le pire des deux mondes.

Jour 5 : Résilience, Observabilité et Sécurité

1. Design for Failure (Concevoir pour la panne)

Dans un système distribué, la question n'est pas "Est-ce que ça va planter ?" mais "Quand ça va planter, comment limiter les dégâts ?"

Le Pattern Circuit Breaker (Disjoncteur)

Si le Service B est en panne, le Service A qui l'appelle va accumuler des threads bloqués (Timeouts) et finir par crasher à son tour (Effet domino). Le Circuit Breaker empêche cela.

  • Closed (Fermé) : Tout va bien, les requêtes passent.
  • Open (Ouvert) : Trop d'erreurs détectées. Le disjoncteur saute. Les appels échouent instantanément sans interroger le Service B (qui a ainsi le temps de respirer/redémarrer).
  • Half-Open (Demi-ouvert) : On laisse passer 1 ou 2 requêtes pour voir si B est revenu à la vie.

💻 Live Coding : Resilience4j

@CircuitBreaker(name = "inventoryService", fallbackMethod = "inventoryFallback")
public InventoryResponse checkStock(String productId) {
    return restTemplate.getForObject("http://inventory-service/stock/" + productId, InventoryResponse.class);
}

// Fallback : Que faire si le service est en panne ?
public InventoryResponse inventoryFallback(String productId, Exception e) {
    // Stratégie de repli : On assume qu'il y a du stock pour ne pas bloquer la vente, 
    // quitte à gérer une rupture manuellement plus tard (Trade-off métier !).
    return new InventoryResponse(productId, true, "FALLBACK_MODE");
}

2. Observabilité : Logs, Métriques, Traces

Le monitoring classique dit "Le CPU est à 90%". L'observabilité dit "La requête X a planté car le microservice C a mis 4 secondes à répondre".

  • Logs Centralisés (ELK - Elasticsearch, Logstash, Kibana) : Ne jamais lire de logs dans un terminal serveur.
  • Métriques (Prometheus / Grafana) : Nombre de requêtes/sec, taux d'erreur HTTP 500.
  • Distributed Tracing (Zipkin / Jaeger) : Chaque requête reçoit un TraceID. Ce TraceID traverse tous les microservices. On peut ainsi dessiner un diagramme de Gantt du temps passé dans chaque service.

3. Sécurité Inter-Services : Le JWT

JSON Web Token (JWT)

Un jeton signé cryptographiquement contenant les informations de l'utilisateur (Claims). L'API Gateway le valide, puis le transmet aux microservices en aval qui peuvent lui faire confiance sans interroger la base de données (Stateless).

Jour 6 : Cloud, Déploiement et Gouvernance

1. Conteneurisation et Orchestration

  • Docker : Package le code et ses dépendances (OS, librairies) dans un livrable immuable (L'image Docker). Résout le problème du "Ça marche sur ma machine".
  • Kubernetes (K8s) : L'orchestrateur. Il gère des milliers de conteneurs. Si un conteneur crash, K8s en relance un. S'il y a un pic de charge, K8s fait du Scaling Horizontal (passe de 2 à 10 pods).

👔 Mode Pro : Stratégies de Déploiement Zero-Downtime

Mettre à jour un système critique sans couper le service.

Blue/Green Deployment : Vous avez l'environnement Bleu (v1, prod actuelle). Vous déployez l'environnement Vert (v2, caché). Vous testez Vert. Si OK, le routeur bascule 100% du trafic de Bleu vers Vert d'un coup. (Rollback immédiat si souci).
Canary Release : Vous déployez la v2 et vous lui envoyez seulement 5% des vrais utilisateurs (les "canaris"). Si les métriques d'erreurs n'explosent pas, vous montez à 20%, puis 100%.

2. Infrastructure as Code (IaC)

On ne clique plus dans des interfaces web d'AWS pour créer des serveurs. On écrit du code (Terraform) qui décrit l'infrastructure. Si le datacenter brûle, on lance le script et on recrée l'infra identique ailleurs en 5 minutes.

3. Gouvernance d'Architecture (L'Urbanisation du SI)

Versionning d'API

Une API publique est un contrat. Si vous cassez le contrat (changer un nom de champ), vos clients crashent. Toujours versionner : /api/v1/users vers /api/v2/users.

TP 1 : Base Architecturale Propre (Clean Monolith)

🎯 Objectif du TP

Créer une application de e-commerce "E-Shop" (catalogue de produits, commandes) avec une architecture en couches propre, préparant le terrain pour l'éclatement en microservices de demain.

Énoncé & Étapes Détaillées

  1. Initialisation : Spring Initializr (Web, JPA, H2, Lombok, Validation).
  2. Découpage Package : Créer une structure par "Feature" (Domaine) plutôt que par technique. 
    com.eshop
├── catalog
│   ├── domain (Product, Category)
│   ├── infrastructure (ProductRepository, Entities)
│   └── web (ProductController, DTOs)
└── order
    ├── domain (Order, OrderLine)
    ├── infrastructure
    └── web
  3. Implémentation du Domaine : Créer l'entité `Product` (id, name, price, stock).
  4. Contrat d'API (DTOs) : Créer un `ProductCreateRequest` et un `ProductResponse`. Ne liez jamais l'entité au Web.
  5. Gestion d'erreurs : Implémentez un @RestControllerAdvice. Si on demande le produit ID 999 inexistant, l'API doit retourner un beau JSON HTTP 404 standardisé, pas une stacktrace Java hideuse.

Pièges fréquents

- Laisser du System.out.println (utiliser SLF4J/Logback).
- Mettre la logique métier dans le contrôleur. Le contrôleur ne fait QUE valider le JSON et appeler le Service.

TP 2 : L'Éclatement Distribué

🎯 Objectif du TP

Découper le monolithe du TP1 en deux services distincts (`catalog-service` et `order-service`) et les faire communiquer derrière une API Gateway.

Énoncé & Étapes Détaillées

  1. Séparation : Créez deux projets Spring Boot distincts. Ils tournent sur des ports différents (ex: 8081 et 8082).
  2. Mise en place de Spring Cloud Gateway :
    • Créer un 3ème projet "gateway".
    • Configurer le application.yml pour router /api/catalog/** vers 8081 et /api/orders/** vers 8082.
  3. Communication Inter-Services (Synchrone) :
    • Quand une commande est créée dans `order-service`, il doit vérifier le prix du produit dans `catalog-service`.
    • Utilisez Spring Cloud OpenFeign pour créer un client REST déclaratif.

💻 Extrait de Code Attendu (OpenFeign)

@FeignClient(name = "catalog-service", url = "http://localhost:8081")
public interface CatalogClient {

    @GetMapping("/api/catalog/{id}")
    ProductDto getProductById(@PathVariable("id") Long id);
}

👔 Ce que l'étudiant doit comprendre

En divisant le projet, on a créé un problème de latence réseau. Si le `catalog-service` est lent, la création de commande devient lente. C'est l'impact direct du système distribué.

TP 3 : Résilience et Observabilité

🎯 Objectif du TP

Rendre le système du TP2 "Production-Ready". Nous allons simuler des pannes et ajouter du monitoring.

Énoncé & Étapes Détaillées

  1. Simulation de panne : Ajoutez un `Thread.sleep(3000)` aléatoire dans `catalog-service` pour simuler une dégradation réseau. Constatez que `order-service` plante avec des Timeouts.
  2. Ajout de Resilience4j :
    • Ajoutez le Circuit Breaker autour du FeignClient du TP2.
    • Créez une méthode Fallback. Si le catalogue est injoignable, refusez la commande proprement avec un message "Service momentanément indisponible" plutôt qu'une erreur 500 générique.
  3. Observabilité (Actuator & Micrometer) :
    • Ajoutez spring-boot-starter-actuator.
    • Exposez l'endpoint /actuator/health.
    • Activez le traçage distribué (Zipkin/Brave) pour voir le `traceId` se propager dans les logs entre la Gateway, Order et Catalog.

Critères d'évaluation

Le TP est validé si je peux éteindre brutalement le `catalog-service` et que le `order-service` survit en renvoyant une réponse fonctionnelle gracieuse (Fallback) en moins de 500ms (grâce au Circuit Breaker ouvert).

Créer un Dossier d'Architecture Technique (DAT)

Le livrable d'un architecte n'est pas (seulement) du code. C'est un document qui fige les décisions, explique le "Pourquoi" (Trade-offs) et guide les équipes de développement. Il doit être concis, visuel et orienté prise de décision.

Checklist d'un bon DAT

  • 1. Contexte Métier : À quel besoin répondons-nous ?
  • 2. Besoins Non Fonctionnels : SLA (99.9%), Temps de réponse cible, Volumes (Nb utilisateurs).
  • 3. Schémas d'Architecture : Logique (Composants, API), Physique (Réseau, Cloud), et Flux de données (Séquence).
  • 4. Choix Technologiques : Ne dites pas juste "On prend Kafka". Dites "On prend Kafka PARCE QUE besoin de rejouer les messages. Alternative rejetée : RabbitMQ car file d'attente éphémère".
  • 5. Sécurité : Authentification, Chiffrement (TLS), Gestion des secrets (Vault).
  • 6. ADRs (Architecture Decision Records) : Historique des choix structurants.

Exemple de format ADR

Titre: ADR-005 Utilisation de PostgreSQL pour le service Order
Statut: Accepté
Date: 2026-03-12

Contexte :
Le service Order doit stocker des données hautement transactionnelles.

Décision :
Nous choisissons une base de données relationnelle (PostgreSQL) plutôt qu'une base NoSQL (MongoDB).

Trade-offs (Conséquences) :
- Positif : Cohérence forte (ACID) garantie pour les paiements.
- Négatif : Scalabilité horizontale plus complexe qu'avec du NoSQL.

Glossaire Expert & Anti-Patterns

🚫 Top 3 des Anti-Patterns (Les erreurs à ne pas faire)

  1. Anemic Domain Model : Des entités qui ne contiennent que des Getters/Setters sans aucune règle métier, déplaçant toute la logique dans des `Services` obèses.
  2. Distributed Monolith : Des microservices tellement couplés via des appels synchrones que la mise à jour d'un service nécessite le déploiement simultané des autres.
  3. God Class / Big Ball of Mud : Un code source sans frontières claires, où tout le monde appelle tout le monde (Couplage fort).

Définitions rapides

TermeDéfinition M2
IdempotencePropriété d'une opération mathématique ou informatique qui a le même effet qu'elle soit appliquée une ou plusieurs fois. Crucial en REST (PUT, DELETE).
CQRSCommand Query Responsibility Segregation. Séparer le modèle d'écriture (Commandes - Insert/Update) du modèle de lecture (Queries - Select), parfois avec des bases de données distinctes.
Event SourcingStocker non pas l'état actuel d'une entité, mais la séquence d'événements qui l'ont amenée à cet état (comme un relevé de compte bancaire).
